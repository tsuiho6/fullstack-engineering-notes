# 资源、方法与 API 契约

## 一、是什么

业务 API 是客户端与服务端共同遵守的契约：路径指向资源，HTTP 方法表达操作，状态码和响应 body 表达结果。

## 二、为什么需要

清晰的契约能让前后端独立开发，也让客户端知道何时重试、何时提示用户。随意改变响应字段或方法语义会破坏调用方。

## 三、核心用法

先从资源命名，而不是从数据库表名或函数名开始：

~~~text
GET    /v1/notes          列表
POST   /v1/notes          创建
GET    /v1/notes/{id}     详情
PATCH  /v1/notes/{id}     局部修改
DELETE /v1/notes/{id}     删除
~~~

列出契约时回答：

| 项目 | 例子 |
| --- | --- |
| 输入 | JSON body、path 参数、query 参数、认证身份 |
| 成功 | 状态码、响应字段、分页信息 |
| 失败 | 参数错误、未认证、无权限、不存在、冲突、内部错误 |
| 重试 | 操作是否幂等，客户端超时后能否安全重试 |
| 演进 | 可选字段、兼容旧客户端的策略 |

## 四、核心原理

- 路径中的名词表达资源层级；HTTP 方法承担动作语义。
- 资源地址是外部契约；Go 函数名和数据库表名属于内部实现。
- REST 风格强调围绕资源操作，但命令型业务可以用明确的 action endpoint，不必为纯 REST 牺牲可理解性。
- 对外 API 的字段和状态码会被客户端依赖；上线后删除或改义需要兼容策略。

## 五、常见场景

- 详情、列表、创建、更新和删除优先用资源路径与标准方法。
- 大列表使用分页、排序白名单和过滤条件；稳定排序避免翻页时重复或漏项。
- 需要执行长任务时先返回任务资源与 ID，再提供状态查询，而不是让 HTTP 请求无限等待。

## 六、踩坑点

- 在 URL 中放密码、token 或其他秘密。
- 用动词堆路径但不说明资源，例如 /getNote、/deleteNote。
- 允许任意字段作为排序列，导致 SQL 注入或不可控查询。
- 通过改已有字段类型破坏旧客户端解析。
- 假设 PUT/PATCH 在所有项目中语义天然一致；契约应写清楚。

## 七、项目中的实际使用

新增 endpoint 前先写请求/响应样例，再实现 Handler。为公开契约维护 OpenAPI 文档或至少一份机器和人都能读懂的 API 说明。

教学演示可以把数据存在内存里，专注练 HTTP 契约；接数据库时保持 API 语义不变，让存储实现成为内部细节。

## 八、一句话总结

**先定义调用方可依赖的资源契约，再选择 Go 函数、表结构和框架实现。**

## 九、核心问答

### 1. 为什么 API 路径不应直接暴露数据库表名？

存储结构可以重构；API 是对调用方的长期承诺，两者不应强绑定。

### 2. API 版本号解决什么问题？

它给不兼容变更提供迁移边界；小的向后兼容新增字段通常不需要新版本。

### 3. 列表 API 为什么要限制排序字段？

它控制查询成本，并避免把不可信字符串直接拼进 SQL。

### 4. REST 风格是否要求每个操作都必须是 CRUD？

不要求。重点是明确、稳定的资源和操作语义；有些业务命令适合明确的 action endpoint。
