# 错误、权限、幂等与 API 闭环

## 一、是什么

业务 API 不只要处理成功路径，还要清楚表达输入错误、身份错误、权限拒绝、状态冲突、重复提交和意外故障。

## 二、为什么需要

线上调用存在超时、重复请求、过期数据和恶意输入。若服务没有明确策略，调用方无法安全恢复，数据也可能重复或越权。

## 三、核心用法

建议使用稳定的错误响应 shape：

~~~json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "title is required",
    "request_id": "req-..."
  }
}
~~~

服务端始终重新检查：

~~~text
身份是否有效
→ 是否有权操作目标资源
→ 输入是否符合边界约束
→ 当前状态是否允许操作
→ 是否已经处理过同一个幂等请求
~~~

## 四、核心原理

- 认证和授权是两步；对象级权限要针对目标资源检查，不能只检查用户登录。
- 稳定业务错误码便于客户端分支；内部日志记录完整错误链，外部消息避免泄露 SQL、堆栈和秘密。
- 幂等键把多次重试映射到同一次逻辑操作。键应绑定调用者、操作范围和结果，不能只靠进程内 map。
- 分页需要明确 page size 上限、排序字段和稳定次序。游标分页通常比大 offset 更适合持续变化的大列表。

## 五、常见场景

- 创建订单或触发付费动作：设计幂等键和重复请求返回行为。
- 修改资源：检查用户对该资源是否有权限，并考虑版本冲突。
- 不可信输入：设置 body 大小、字符串长度、分页上限和过滤白名单。
- 慢任务：返回任务 ID 和查询状态接口，让客户端能够轮询或订阅进度。

## 六、踩坑点

- 只在创建时检查权限，读取、更新和删除却漏检。
- 返回数据库错误原文，泄露表名、查询条件或内部结构。
- 幂等键作用域太宽，导致不同用户或不同操作互相撞键。
- 分页不限制 page size，调用方可轻易触发资源耗尽。
- 认为 JWT 验签成功就足以授权访问所有 user-owned 数据。

## 七、项目中的实际使用

开始项目时先定义错误映射表，集中管理 HTTP 状态码和公开错误码。写操作通常按“认证 → 授权 → 校验 → 事务/幂等 → 修改 → 返回结果”执行。

推荐渐进闭环：

1. 先完成不依赖数据库的 Handler + service，写单元和 Handler 测试。
2. 接入数据库后，增加 schema 迁移和关键查询集成测试。
3. 对重复提交或状态竞争的操作加入唯一约束、事务或幂等记录。
4. 在 Linux 环境运行服务，检查错误日志、请求耗时和端口。
5. 用 Git 分支完成修改和 review，再合并回主分支。

## 八、一句话总结

**把失败路径当成 API 契约的一部分，服务端每次都验证身份、权限、输入和当前状态。**

## 九、核心问答

### 1. 登录成功为什么仍可能返回 403？

登录证明身份有效；该身份仍可能没有访问特定资源的权限。

### 2. 幂等键解决什么问题？

它让超时重试能安全地复用第一次处理结果，降低重复执行副作用的风险。

### 3. 服务端能否把所有内部错误原样返回？

不能。内部错误用于排查，公开响应应稳定且不泄露敏感实现细节。

### 4. Offset 与 cursor 分页如何选择？

小型静态列表可用 offset；数据量大且持续变化时，稳定排序下的 cursor 往往更可控。

2. 幂等记录为什么要有过期、作用域和并发保护？
3. 你会怎样设计一个不会任意扫描全部数据的列表接口？
4. 资源读取接口是否也需要授权检查？

1. 认证 → 资源授权 → 输入校验 → 幂等键去重/并发保护 → 事务写入 → 稳定响应。
2. 防止存储无限增长、跨用户冲突和并发请求重复执行；过期策略按业务风险定义。
3. 限制 page size，固定排序字段，提供过滤白名单；大列表用稳定游标。
4. 需要。读取私有资源同样可能泄露数据。
