# HTTP 消息、方法与连接

## 一、是什么

HTTP 是客户端与服务端交换请求和响应的应用层协议。方法、目标地址、headers、状态码和 body 一起构成消息契约。

## 二、为什么需要

一致的 HTTP 语义让客户端知道“要做什么”和“结果怎样”。随意使用状态码、方法或 body 会造成重试错误、缓存错误和客户端兼容问题。

## 三、核心用法

### 请求与响应 shape

~~~text
Request  = Method + Target + Headers + Optional Body
Response = Status + Headers + Optional Body
~~~

| 方法 | 典型含义 | 安全 | 幂等 |
| --- | --- | --- | --- |
| GET | 读取资源 | 是 | 是 |
| POST | 创建资源或执行命令 | 否 | 通常否 |
| PUT | 替换资源 | 否 | 通常是 |
| PATCH | 局部更新 | 否 | 取决于设计 |
| DELETE | 删除资源 | 否 | 通常是 |

常见状态码：

- 200：成功并返回内容；201：创建成功；204：成功但无响应体。
- 400：请求形状或字段错误；401：缺少有效认证；403：身份有效但无权限；404：资源不存在。
- 409：状态冲突；429：请求过多；500：服务端未预期失败；503：当前不可用。

## 四、核心原理

- 安全方法表达不会改变目标资源的业务状态；幂等方法重复执行，目标状态应等价于执行一次。
- HTTP 状态码说明协议结果；body 可以带稳定的机器可读业务错误码和人类可读说明。
- HTTP/1.1 的持久连接减少重复握手；HTTP/2 在单连接多路复用请求。应用不应依赖一个请求占用一个连接。
- HTTP 本身无状态；登录会话、限流、幂等记录等状态由 Cookie、token、服务端存储或业务系统提供。

## 五、常见场景

- 读取详情用 GET；创建资源常用 POST；替换与部分修改要明确 PUT/PATCH 语义。
- 资源不存在返回 404，资源版本冲突可用 409。
- 请求体声明 Content-Type；协商响应格式可使用 Accept。
- 流式响应要定义好协议边界，例如 SSE event 或明确的 JSON Lines，不要让客户端猜字符串格式。

## 六、踩坑点

- 把 401 与 403 混用：前者是认证无效/缺失，后者是授权拒绝。
- 让 GET 产生扣款等副作用，导致预取、缓存或重试触发意外行为。
- 把业务失败一律返回 200，再靠任意文本判断。
- 假定 POST 自动幂等；客户端超时重试可能重复创建。
- 忘记读取并关闭响应体，导致连接无法复用或资源泄漏。
- 仅凭状态码语义推断具体业务原因；服务契约还需要稳定错误码。

## 七、项目中的实际使用

设计每个 endpoint 前先写一行契约：

~~~text
POST /v1/notes
请求：application/json，字段 title 必填，长度有上限
成功：201 + 新建 note
失败：400 + VALIDATION_ERROR；401/403；409 + CONFLICT
~~~

对外服务要记录 request ID、方法、路由模板、状态码和耗时，避免记录 token、密码或完整敏感 body。流式接口与普通 JSON 接口要分开定义超时和响应协议。

## 八、一句话总结

**HTTP 方法表达意图，状态码表达协议结果，headers 和 body 完成机器可读的契约。**

## 九、核心问答

### 1. 安全和幂等有什么区别？

安全表示业务状态不被改变；幂等表示重复执行的最终状态与执行一次相同。GET 通常两者都满足，DELETE 通常幂等但不安全。

### 2. PUT 和 PATCH 的差异是什么？

PUT 通常表达整体替换，PATCH 表达部分修改；实际语义必须由 API 契约规定。

### 3. 401 和 403 如何区分？

401 表示请求没有有效认证；403 表示已识别身份但不允许访问该资源。

### 4. 为什么 POST 重试可能产生重复数据？

POST 通常非幂等；服务端若没有幂等键或去重规则，会把重试当作新操作。

1. 删除会改变状态，但重复删除后目标仍是“不存在”，最终效果相同。
2. 使用客户端提供的幂等键，在服务端按用户和操作范围持久化去重结果。
3. 请求格式合法，但与当前资源版本或业务状态冲突时，例如重复占用或乐观锁版本不匹配。
4. 多个请求可以共享一条连接，应用不能把连接数量等同于并发请求数量。
