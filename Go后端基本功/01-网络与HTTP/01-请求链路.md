# 一次请求的链路：DNS、TCP、TLS

## 一、是什么

一次 HTTPS 请求通常先把域名解析为 IP，再通过 TCP 建立连接、通过 TLS 建立加密且可验证身份的通道，最后在通道中交换 HTTP 消息。

## 二、为什么需要

服务端问题常被描述成“接口不通”或“请求很慢”。把请求拆层后，才能判断失败在解析、连接、证书、HTTP 路由、业务处理还是下游依赖。

## 三、核心用法：先看阶段，再看症状

~~~text
URL
  → DNS：域名解析成一个或多个地址
  → TCP：客户端与目标地址端口建立可靠字节流
  → TLS：协商加密参数，验证服务端证书和域名
  → HTTP：发送 method / path / headers / body
  → Handler：应用处理请求并返回状态、headers、body
~~~

最小排查命令：

~~~bash
getent hosts api.example.com
curl -v --connect-timeout 2 --max-time 5 https://api.example.com/health
ss -lntp
~~~

## 四、核心原理

- DNS 解决“目标名字对应哪个地址”。缓存、多个地址和代理会让结果不一定只有一个。
- TCP 提供可靠、有序的字节流。一次 Write 和一次 Read 不构成应用消息边界。
- TLS 在 HTTP 之前完成安全协商；证书要能验证请求域名，系统时间错误也可能导致证书验证失败。
- HTTP 定义消息语义，而不是底层路由和连接建立。HTTP/1.1 常复用连接，HTTP/2 可在连接上多路复用请求。

直观记忆：DNS 找地址，TCP 建通道，TLS 确保通道可信，HTTP 说明要做什么。

## 五、常见场景

- 域名能解析但连接失败：检查目标端口、路由、防火墙和服务监听。
- TCP 已连通但证书失败：检查域名、证书链、系统时间和代理证书。
- 收到 HTTP 404/500：网络已到达 HTTP 服务，继续检查路由或应用逻辑。
- 请求耗时高：拆分 DNS、连接、TLS、首字节、响应体和下游处理时间。

## 六、踩坑点

- 把 TCP 当作“一个 Write 对应一个完整请求”。
- 看到 ping 成功就认定 HTTP 服务可用；ICMP 与 TCP 端口是不同路径。
- 看到 404/500 就判断网络不通；有 HTTP 状态码通常说明已经收到 HTTP 响应。
- 忽略代理、负载均衡、DNS 缓存和连接池等中间层。
- 把 TLS 理解成只加密 body；TLS 也保护 HTTP headers 和请求路径。

## 七、项目中的实际使用

1. 先记录客户端的 DNS、连接和 TLS 阶段耗时。
2. 再用服务日志的 request ID 关联 Handler 与下游调用。
3. 在机器上检查监听地址和端口；容器内的 localhost 只指当前容器。
4. 只对确实需要的请求开放网络端口，并通过 HTTPS 保护公网流量。

教学演示可以用本机 localhost；真实部署要额外考虑反向代理、容器网络、服务发现和 TLS 终止位置。

## 八、一句话总结

**排网络问题按 DNS → TCP → TLS → HTTP → Handler 的顺序找证据。**

## 九、核心问答

### 1. TCP 为什么不保留 HTTP 请求边界？

TCP 只提供有序字节流。应用必须靠 HTTP 的语法和长度规则解析消息。

### 2. HTTPS 证书错误说明什么？

TLS 未能验证所连接服务的身份或证书链；不能简单关闭验证来“修复”。

### 3. HTTP 500 说明 TCP 一定健康吗？

它说明客户端收到了一条 HTTP 响应，但不能证明网络路径完全健康；响应也可能由代理或网关生成。

### 4. 如何区分连接慢和业务处理慢？

分别测连接建立、TLS 握手、首字节和响应体阶段，并与服务端日志的处理耗时对照。

2. 为什么 TCP Read 可能只读到请求的一部分？
3. 域名解析失败、连接拒绝、证书错误和 HTTP 404 分别应先查哪一层？
4. 为什么 ping 通不能证明 API 可用？

<details>
<summary>参考答案</summary>

1. DNS → TCP → TLS → HTTP 消息发送 → 服务端 Handler。
2. TCP 是流式传输，数据如何分段由缓冲和调度决定，不等同于应用消息。
3. DNS；监听端口/网络策略；证书与域名；HTTP 路由和资源。
4. ping 验证的是 ICMP 可达性，不验证 TCP 端口、TLS、HTTP 或应用逻辑。
