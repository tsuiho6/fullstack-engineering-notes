# Go 网络调用、超时取消与排障

## 一、是什么

Go 的 net 与 net/http 提供 TCP、域名解析、HTTP 客户端和服务端能力。请求的连接、读写、取消和资源释放需要由应用明确管理。

## 二、为什么需要

没有期限的网络调用可能永久等待；每次临时创建 Client/Transport 会失去连接池收益；忽略状态码和响应体会把服务端错误误判为成功。

## 三、核心用法

~~~go
var sharedClient = &http.Client{
    Timeout: 5 * time.Second,
}

func fetch(ctx context.Context, url string) ([]byte, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, fmt.Errorf("build request: %w", err)
    }

    resp, err := sharedClient.Do(req)
    if err != nil {
        return nil, fmt.Errorf("send request: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode < 200 || resp.StatusCode >= 300 {
        return nil, fmt.Errorf("unexpected status: %s", resp.Status)
    }

    body, err := io.ReadAll(io.LimitReader(resp.Body, 1<<20))
    if err != nil {
        return nil, fmt.Errorf("read response: %w", err)
    }
    return body, nil
}
~~~

常用 imports：context、fmt、io、net/http、time。实际项目应按协议解码 JSON，并约束响应体大小。

## 四、核心原理

- context deadline 是调用链的最晚完成时间；把它传给 HTTP 请求，客户端可在期限或父级取消后中断等待。
- http.Client 的 Timeout 覆盖整个请求过程，包括读取响应体；长流式接口不应盲目套很短的全程 timeout。
- Client/Transport 可以并发复用，Transport 管理连接池；不要每个请求都 new 一个。
- HTTP 非 2xx 通常不会让 Client.Do 返回 error；网络错误与业务状态码是两类结果。
- 响应体是流，关闭它是资源生命周期的一部分；读到结束通常有助于复用连接。

## 五、常见场景

- 服务调用外部 API：父 context 向下传递；设置总期限和合理重试边界。
- HTTP Server：设置 ReadHeaderTimeout，避免慢速发送 header 占住资源。
- 收到 SIGTERM：停止接收新请求，在期限内等待已有请求完成。
- 调用超时：区分 DNS、建立连接、TLS、首字节、读取响应体和下游处理时间。

## 六、踩坑点

- 设置很大的全局 timeout 代替理解每个调用的期限。
- 只有客户端超时，没有让数据库、RPC 和 goroutine 感知取消。
- 只检查 err，不检查 resp.StatusCode。
- 不关闭 Body；或为了复用连接无限制地把超大 body 全读入内存。
- 对所有请求自动重试；非幂等写请求可能重复执行。
- 为流式接口设置过短的全程 Client.Timeout，导致生成中途被切断。

## 七、项目中的实际使用

HTTP 调用推荐流程：

1. 从入口 request context 派生期限，向下游传递。
2. 复用共享 Client，配置符合服务能力的连接池。
3. 检查网络 error、HTTP status、响应体上限和解码 error。
4. 只对可重试且幂等的操作重试，并限制次数、总时长和退避。
5. 记录目标服务、状态码、耗时和 request ID；日志不写认证凭据。

HTTP 服务端应使用显式的 http.Server timeout。优雅关闭使用 signal context 调用 Server.Shutdown；流式响应需单独评估写超时和代理缓冲。

## 八、一句话总结

**复用 Client，传播 Context，检查状态，关闭 Body，并把总耗时拆成可观察的阶段。**

## 九、核心问答

### 1. Client.Do 返回 nil error 是否代表 HTTP 成功？

不代表。它只说明 HTTP 交换成功完成；还要检查状态码和响应 body。

### 2. http.Client 和 Transport 为什么要复用？

Transport 保存连接池与连接复用状态；重复创建会增加握手和资源开销。

### 3. context 超时为什么不等于服务端已经停止？

它传递的是取消信号。服务端和下游只有在监听并响应取消后才会停止工作。

### 4. 为什么有些写请求不能自动重试？

网络错误发生时，客户端可能不知道服务端是否已提交操作；重试可能重复执行非幂等副作用。

1. 写一个 GET 调用最少要检查哪些错误并释放什么资源？
2. HTTP 503 会让 Client.Do 返回 error 吗？
3. HTTP Client 的 Timeout 为什么可能不适合 SSE 流？
4. 怎样避免所有 goroutine 各自无限等待下游？

<details>
<summary>参考答案</summary>

1. 检查建请求和 Do 的 error，检查状态码，限制并解码响应体，关闭 Body。
2. 通常不会；503 是有效收到的 HTTP 响应，需由应用解释。
3. Timeout 覆盖整个请求过程，长时间流式响应可能超过短期限。
