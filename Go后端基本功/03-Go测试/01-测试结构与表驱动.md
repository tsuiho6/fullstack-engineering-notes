# Go 测试结构与表驱动

## 一、是什么

Go 测试是可重复执行的程序，用来约束公开行为和重要边界。测试文件以 <code>_test.go</code> 结尾，普通测试函数以 <code>Test</code> 开头。

## 二、为什么需要

手动点一遍只能证明某个时刻看起来正常。自动测试能在重构、修 bug 和改依赖后快速检查行为是否回退。

## 三、核心用法

表驱动测试适合相同规则下的多个输入：

~~~go
func TestNormalizeTitle(t *testing.T) {
    tests := []struct {
        name  string
        input string
        want  string
    }{
        {name: "trim spaces", input: "  Go  ", want: "Go"},
        {name: "empty stays empty", input: " ", want: ""},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := NormalizeTitle(tt.input)
            if got != tt.want {
                t.Fatalf("NormalizeTitle(%q) = %q, want %q", tt.input, got, tt.want)
            }
        })
    }
}
~~~

运行常用命令：

~~~bash
go test ./...
go test -run TestNormalizeTitle ./...
go test -race ./...
~~~

## 四、核心原理

- 每个测试声明输入和期望行为；失败应指出条件、实际值和期望值。
- 测试应观察外部行为，不要为了覆盖率测试私有实现细节。
- 子测试提供独立名称与结果；表驱动让一组边界样例保持同一结构。
- 测试应确定性、可重复、运行足够快，不依赖真实时间、网络和随机全局状态。

## 五、常见场景

- 纯函数或规则：正常输入、边界输入、非法输入。
- 错误处理：底层 error 是否包装和保留；可以配合 errors.Is/As。
- 并发组件：共享状态约束、取消、关闭和泄漏行为。
- 公共函数：测试协议行为与结果，不测每个内部 helper。

## 六、踩坑点

- 只测 happy path，遗漏空值、边界、重复调用和错误返回。
- 测试之间共享可变全局状态，运行顺序改变后结果不稳定。
- 用 sleep 等待 goroutine，导致测试慢且容易偶发失败。
- 用超大测试函数覆盖所有功能，失败原因难以定位。
- 把覆盖率当正确性分数；执行过一行代码不代表断言了它的行为。

## 七、项目中的实际使用

先测纯业务规则；每次修 bug 先写能重现问题的用例，再修实现。对错误使用 errors.Is 或类型断言，不比较不稳定的完整错误字符串。

表驱动不是强制模板：有复杂 setup 或不同验证逻辑时，分成多个具名测试更清楚。

## 八、一句话总结

**测试把“我以为它会这样”变成每次改动后都能重新检查的行为约束。**

## 九、核心问答

### 1. 表驱动测试适合什么情况？

多组输入共享同一执行和断言逻辑时；差异流程很大时，拆成独立测试更清楚。

### 2. 测试为什么不应依赖运行顺序？

顺序依赖会隐藏共享状态和资源清理问题，也会让单独运行时结果不同。

### 3. 覆盖率高为什么仍可能有 bug？

代码行被执行不代表关键结果被断言，也不代表未覆盖的输入和并发时序正确。

### 4. 修 bug 时测试应先写还是后写？

优先先写能稳定重现问题的测试，再修实现并确认它通过。

## 十、自测与答案

1. 给标题规范化函数列出正常、空白和极长输入用例。
2. 什么情况下应使用独立测试而不是增加 table row？
3. 为什么依赖 sleep 的并发测试容易不稳定？
4. 如何判断测试是否过度依赖内部实现？

<details>
<summary>参考答案</summary>

1. 前后空格、空字符串、全空白、超过最大长度、含 Unicode 字符等。
2. 每种情况 setup、动作和断言差异较大，或名称需要表达独立行为时。
3. 调度和机器负载变化会改变 sleep 醒来时状态，无法保证目标事件已经发生。
4. 重构内部结构但公开行为不变时，测试仍应通过；若频繁改测试只为适配重构，可能测了实现细节。
