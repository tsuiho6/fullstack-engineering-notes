# 集成、竞态与验证闭环

## 一、是什么

集成测试检查多个真实组件如何协作；竞态检测检查并发访问中的数据竞争；基准测试比较代码在指定负载下的性能表现。

## 二、为什么需要

单元测试无法证明数据库驱动、schema、事务和真实并发行为正确。分层验证能把快而精准的反馈与真实依赖验证结合起来。

## 三、核心用法

常用验证：

~~~bash
go test ./...
go test -race ./...
go test -cover ./...
go vet ./...
go test -bench=. -benchmem ./path/to/package
~~~

基准测试应有可重复的输入和基线；性能比较尽量在相同机器、工具链和数据下进行。

## 四、核心原理

- 单元测试运行快，定位准；集成测试运行成本高但覆盖真实边界。
- race detector 只对实际执行到的并发路径进行检测；无报告不证明不存在竞态。
- benchmark 反映特定环境与负载，不等于线上性能。先确定瓶颈，再比较改动。
- 测试环境与线上不完全相同；配置、数据库版本和数据规模需要有意识地对齐。

## 五、常见场景

- 数据库读写、事务和迁移：对测试数据库做少量集成测试。
- worker pool、缓存和共享状态：使用 race detector 和确定性同步。
- 性能优化：为目标 workload 设置 benchmark，观察 ns/op、B/op、allocs/op。
- 关键请求链路：端到端测试验证路由、数据库和外部契约是否接通。

## 六、踩坑点

- 把所有用例都做成端到端测试，反馈变慢且失败定位困难。
- 集成测试共用污染状态，依赖执行顺序。
- 为让测试通过而吞掉数据库或网络错误。
- 根据覆盖率数字追求无意义的测试行数。
- benchmark 输入每轮不断变大，测量对象随时间改变。

## 七、项目中的实际使用

建议验证闭环：

1. gofmt 和静态检查。
2. go test ./... 跑快测。
3. go test -race ./... 覆盖并发敏感包。
4. 集成测试连接独立测试数据库，使用可重复 fixture 并清理数据。
5. 关键优化单独 benchmark，记录优化前后环境、输入和结果。
6. CI 执行稳定、无需个人密钥和手工服务的检查。

并非每次本地改动都要运行最慢的端到端测试；提交或发布前按项目约定执行完整验证。

## 八、一句话总结

**单测定位规则，集成测真实边界，race 查数据竞争，benchmark 比可重复的工作负载。**

## 九、核心问答

### 1. race detector 没报错能证明并发安全么？

不能。它只分析测试实际执行到的路径和时序。

### 2. 为什么单元测试不能替代数据库集成测试？

fake 不执行真实 SQL、约束、事务和驱动行为。

### 3. benchmark 为什么必须稳定输入？

否则不同测量阶段执行的工作不同，结果不可比较。

### 4. 高覆盖率是否等于高质量？

不等于。关键是断言行为、边界和失败路径，而非只执行代码行。

## 十、自测与答案

1. 更新一段事务 SQL，至少需要哪类验证？
2. 为什么 CI 中运行 race detector 有价值但仍不足以证明无竞态？
3. 如何保证集成测试不依赖其他测试的运行顺序？
4. 什么时候应该写 benchmark？

<details>
<summary>参考答案</summary>

1. 纯业务规则单测、对 SQL/事务的数据库集成测试；高并发共享状态另跑 race。
2. 它能捕获已执行路径上的数据竞争，但不会覆盖所有输入和调度时序。
3. 使用独立 fixture/事务或独立测试资源，清理自己创建的数据，不依赖全局共享状态。
4. 有明确性能问题或要比较候选实现时；先有稳定 workload 和基线。
