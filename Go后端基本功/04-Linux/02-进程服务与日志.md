# 进程、服务与日志

## 一、是什么

进程是正在运行的程序实例；服务管理器负责按策略启动、停止、重启和记录服务状态。日志记录程序在运行期间观察到的事件。

## 二、为什么需要

部署后常见问题不是编译失败，而是进程退出、配置错误、端口冲突或依赖不可达。需要先确认程序是否在运行，再沿日志和资源检查。

## 三、核心用法

~~~bash
ps -ef
pgrep -af my-service
systemctl status my-service
journalctl -u my-service --since '10 minutes ago'
kill -TERM 12345
~~~

优雅终止流程：

~~~text
服务管理器发送 SIGTERM
  → 程序停止接收新请求
  → 当前请求在期限内完成
  → 关闭连接池、文件等资源
  → 超时后由管理器强制结束
~~~

## 四、核心原理

- 进程拥有 PID、环境、文件描述符和资源限制。
- SIGTERM 请求程序自行退出；SIGKILL 由内核强制结束，程序无法清理资源。
- systemd 只适用于使用 systemd 的系统；容器通常由容器运行时管理主进程。
- 容器应用常把日志写到 stdout/stderr，由平台采集；不要假设容器内日志文件会持久化。

## 五、常见场景

- 服务频繁重启：查状态、退出码、启动日志和配置。
- 进程存在但不响应：查线程/CPU/内存情况及请求日志。
- 发布停止服务：先发送 TERM 并等待优雅退出，再按策略升级处理。
- 定位单次请求：使用 request ID 关联接入层和业务日志。

## 六、踩坑点

- 直接 kill -9，跳过清理和优雅停机。
- 看到旧日志就判断当前请求路径正常；要确认时间、实例和 request ID。
- 在多个地方重复记录同一错误，增加噪声。
- 日志写入 token、密码、完整 Cookie 或敏感请求 body。
- 假定 systemctl 和 journalctl 在所有容器或发行版都存在。

## 七、项目中的实际使用

Go HTTP 服务应响应 SIGTERM，停止接收新工作，给现有请求设置关闭宽限时间并关闭数据库/消息连接。日志优先结构化，包含时间、级别、服务名、request ID、路由模板和耗时。

系统与容器的服务管理流程不同：在 VM 上查 systemd unit；在容器中检查主进程和平台日志，不要再嵌套启动一套服务管理器。

## 八、一句话总结

**确认进程状态，用日志关联请求，优雅停止优先于强杀。**

## 九、核心问答

### 1. SIGTERM 与 SIGKILL 的区别是什么？

SIGTERM 可被程序处理并清理；SIGKILL 由内核强制结束，程序不能捕获。

### 2. 服务管理器显示 active 是否说明接口健康？

不一定。进程可能活着但线程阻塞、依赖失败或 API handler 出错。

### 3. 容器日志通常从哪里查看？

通常由容器平台收集 stdout/stderr；实际位置和查询方式看部署平台。

### 4. request ID 有什么用？

把入口日志、服务日志和下游调用关联到同一请求，便于定位时序。
