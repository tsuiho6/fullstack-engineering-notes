# 资源、网络与故障排查

## 一、是什么

Linux 排障是通过症状、指标和日志逐层缩小范围的过程。先确认进程、端口、资源和网络，再检查应用与依赖。

## 二、为什么需要

CPU 忙、内存不足、磁盘写满、端口被占用或 DNS 失败都会表现成“服务不可用”。只重启可能暂时掩盖症状，也丢掉现场证据。

## 三、核心用法

~~~bash
top
free -h
df -h
df -i
ss -lntp
curl -v --max-time 5 http://127.0.0.1:8080/health
getent hosts example.com
ip route
~~~

症状到证据：

| 症状 | 优先检查 |
| --- | --- |
| 无法启动 | 进程状态、退出码、启动日志、配置 |
| 连接被拒绝 | 服务是否监听目标地址/端口、端口是否被占用 |
| 域名访问失败 | DNS 解析结果、代理和路由 |
| 磁盘写失败 | 文件系统容量、inode、日志增长 |
| 请求变慢 | CPU/内存、连接数、服务处理耗时、下游耗时 |

## 四、核心原理

- 端口监听只证明某进程在该地址接受连接，不代表业务依赖都健康。
- 磁盘空间和 inode 是不同资源；空间还够时也可能因 inode 耗尽无法新建文件。
- 主机内存、容器内存限制和 Go runtime 指标不是同一口径。
- 排障遵循“观察 → 假设 → 单变量验证 → 修复 → 回归”，一次改很多配置会丢失因果证据。

## 五、常见场景

- Go 服务本机健康检查正常，外部访问失败：检查监听地址、防火墙、容器端口映射和代理。
- 磁盘使用率突然上升：定位大目录和日志轮转，不要直接删除未知文件。
- p99 延迟升高：比对 CPU、GC、连接池、队列和下游依赖延迟。
- 文件创建失败但 df 看起来有空间：再检查 inode 和权限。

## 六、踩坑点

- 将服务绑定到 127.0.0.1，却期待容器外或其他机器访问。
- 把 curl -v 的网络成功误认为业务操作一定成功。
- 对全盘运行高开销递归扫描，给故障机器增加负载。
- 直接清空生产日志或缓存，丢失证据或造成业务损坏。
- 只看平均延迟，忽略 p95/p99 和错误比例。

## 七、项目中的实际使用

标准排障记录包含时间范围、机器/容器、请求 ID、现象、已检查证据和改动。先保存日志与关键指标，再做修复；修复后验证健康检查、代表性业务请求和错误率。

Go 服务最低应暴露可区分“进程存活”和“依赖就绪”的健康检查；不要让 readiness 总是成功掩盖数据库不可用。

## 八、一句话总结

**先拿现场证据，再逐层排除进程、端口、资源、网络和依赖。**

## 九、核心问答

### 1. df -h 与 df -i 分别看什么？

前者看文件系统容量，后者看 inode 数量。

### 2. 端口监听为什么不能证明 API 健康？

连接能到进程，但业务 Handler、数据库或下游仍可能失败。

### 3. 127.0.0.1 在容器中指向哪里？

当前容器自身，不是宿主机或其他容器。

### 4. 为什么要保留故障现场再修复？

日志和指标提供因果证据；重启或清理可能改变现场，使根因难以复现。

## 十、自测与答案

1. 服务无法从外部访问，但本机 curl 成功，下一步查什么？
2. 磁盘空间充足却无法创建文件，可能检查什么？
3. 某服务 p99 上升但 CPU 很低，哪些方向值得检查？
4. 一次故障修复结束后，至少要验证哪些结果？

<details>
<summary>参考答案</summary>

1. 监听地址、主机防火墙、容器端口发布、反向代理和网络策略。
2. inode、目录权限、只读挂载和文件系统状态。
3. 锁/队列等待、网络和磁盘 I/O、下游慢、连接池耗尽、GC 或限流。
4. 健康检查、代表性业务请求、错误率/延迟和资源趋势，并记录根因证据。
