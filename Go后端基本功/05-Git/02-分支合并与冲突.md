# 分支、合并与冲突

## 一、是什么

分支让一组提交可以独立演进；合并把另一条开发线的历史与改动整合到当前分支。

## 二、为什么需要

直接在共享主分支工作会让未完成改动影响他人。短期功能分支可以隔离开发，完成后再通过 PR 或合并审查。

## 三、核心用法

~~~bash
git switch -c feature/note-validation
git status
git add -p
git commit -m "validate note title"
git fetch origin
git switch main
git pull --ff-only
git switch feature/note-validation
git rebase main
~~~

如果团队使用 merge commit，就按团队约定合并；不要混用工作流规则。

## 四、核心原理

- 分支名是指向提交的引用；新提交让当前分支引用向前移动。
- merge 产生合并结果，通常保留两条历史的共同祖先关系。
- rebase 把分支上的提交重新应用到新基底，会创建新的提交 ID，属于历史改写。
- 冲突表示 Git 无法自动决定同一区域的最终内容；开发者要结合双方意图手动解决。

## 五、常见场景

- 每项工作使用短期分支，持续同步主分支并尽早开 PR。
- 同文件相同区域发生编辑时，冲突后阅读两边上下文，重新运行相关测试。
- 主分支只接受通过 review 和验证的提交。

## 六、踩坑点

- 冲突标记删除了就提交，没有确认业务含义。
- rebase 后对已共享分支强推，重写同伴的历史。
- 分支长期不合并，最终积累大量冲突。
- 把 merge 与 rebase 描述成绝对优劣；团队协作政策优先。
- 只解决文本冲突，不运行受影响测试。

## 七、项目中的实际使用

推荐流程：

1. 更新主分支。
2. 从主分支创建短期 feature/fix 分支。
3. 小步提交，保持工作区可检查。
4. 拉取远端变化；按仓库约定 merge 或 rebase。
5. 解决冲突后检查完整 diff 并跑相关测试。
6. 开 PR，处理 review，再合入主分支。

## 八、一句话总结

**分支隔离变化，合并保留团队共同历史，冲突必须按意图解决并重新验证。**

## 九、核心问答

### 1. branch 与工作区副本有什么不同？

branch 通常只是一个引用，指向提交历史中的某个节点，并不复制全套文件。

### 2. rebase 为什么会改变提交 ID？

新提交包含不同父提交，提交对象内容随之改变，因此哈希 ID 也改变。

### 3. 冲突处理后为什么要再看 diff？

冲突标记被删除不代表结果正确；需要核对最终内容是否同时保留双方需要。

### 4. merge 和 rebase 该选哪个？

依团队历史策略选择。merge 保留分叉与合并节点，rebase 让个人分支历史线性但会改写提交。

2. rebase 与 merge 对提交历史的影响有何区别？
3. 合并冲突后应做哪些检查？
4. 为什么不能随意对共享分支执行强制推送？
