# 远端协作与安全撤销

## 一、是什么

远端协作用 fetch/pull/push 交换提交；撤销命令要根据改动是否已共享，选择保留工作区、移动本地引用或新增反向提交。

## 二、为什么需要

本地改错可调整本地历史；共享历史被他人依赖后，直接改写可能造成协作冲突或提交丢失。

## 三、核心用法

~~~bash
git fetch origin
git log --oneline --graph --decorate --all
git restore path/to/file
git restore --staged path/to/file
git revert <commit>
~~~

| 目标 | 常用手段 | 适用边界 |
| --- | --- | --- |
| 丢弃未暂存文件修改 | git restore file | 修改会丢失，先看 diff |
| 从暂存区撤回文件 | git restore --staged file | 文件改动保留在工作区 |
| 撤销已共享提交 | git revert commit | 新建一个反向提交 |
| 改写本地提交 | git commit --amend 或 reset | 仅本地且确认影响时使用 |

## 四、核心原理

- fetch 下载远端对象和引用，不自动修改当前工作区。
- pull 通常等于 fetch 后按配置整合；不同仓库可能采用 merge 或 rebase。
- revert 添加一个新提交来反向修改，不抹掉原提交，适合共享历史。
- reset 移动当前分支引用，并可能改变暂存区或工作区；hard 会丢弃未提交内容。

## 五、常见场景

- PR 评审：本地分支推到远端，开 PR，持续回应 review。
- 错误提交还未共享：检查 status 与 log，再用 amend/reset 修复本地历史。
- 错误提交已经共享：优先 revert，而不是改写大家依赖的历史。
- 误删或误改：先检查 reflog 和工作区状态，不要继续执行覆盖操作。

## 六、踩坑点

- 混淆 git restore、reset 和 revert，它们影响的状态和历史不同。
- 对共享分支执行 force push。
- 没确认远端和当前分支就执行 pull、push。
- 用 git reset --hard 解决不理解的冲突，丢掉未提交工作。
- 误以为 GitHub 等同于 Git；Git 是版本控制系统，GitHub 是托管和协作平台。

## 七、项目中的实际使用

推送前检查当前分支、远端、待推送提交和敏感文件；开 PR 时描述目的、行为变化、验证方法和风险。保护主分支，让改动通过 review 与 CI 后再合并。

安全顺序：先读 status/log/diff，再选择操作；任何会丢弃工作区或改写远端历史的命令前，先确认备份与协作影响。

## 八、一句话总结

**本地未共享历史可以谨慎改写，共享历史优先用新提交纠正。**

## 九、核心问答

### 1. fetch 和 pull 的区别是什么？

fetch 更新本地远端引用但不自动整合；pull 通常还会合并或 rebase 到当前分支。

### 2. revert 与 reset 的区别是什么？

revert 创建反向提交；reset 移动当前分支引用并可改变 index/worktree。

### 3. 为什么 restore --staged 不会丢掉文件修改？

它把文件从暂存区撤出，但保留工作区内容。

### 4. GitHub 上的 PR 是什么？

一种请求把分支变更合入目标分支的协作流程，通常包含 diff review、讨论和自动检查。

## 十、自测与答案

1. 错误提交已被同伴拉取，应该优先用 reset 还是 revert？
2. git fetch 后当前工作区发生了什么？
3. 误操作导致提交引用变化，接下来为什么不宜继续做清理操作？
4. 推送前至少检查哪些信息？

<details>
<summary>参考答案</summary>

1. 优先 revert，保留共享历史并追加修正提交。
2. fetch 更新远端引用和对象，不自动修改当前分支工作区。
3. 继续操作可能覆盖可恢复状态；先用 status、reflog 和 log 盘点现场。
4. 当前分支、远端、待推送 diff/commit、测试状态和是否含密钥。
