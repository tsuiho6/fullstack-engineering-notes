# 快照、暂存区与日常提交

## 一、是什么

Git 是分布式版本控制系统，用提交快照记录项目历史，并通过引用和分支组织不同开发线。

## 二、为什么需要

没有历史就难以知道改了什么、为什么改、如何回退或与同伴合并。Git 让变更可检查、可审阅和可协作。

## 三、核心用法

一次小改动的日常闭环：

~~~bash
git status
git diff
git add -p
git diff --cached
git commit -m "add note API validation"
git log --oneline --graph
~~~

## 四、核心原理

~~~text
工作区：当前文件
  → 暂存区：准备进入下一次提交的内容
  → commit：不可变项目快照
  → branch：指向某个 commit 的可移动名字
~~~

提交是快照，不是逐行补丁；分支通常只是轻量引用。暂存区让一个提交只包含选定的变更。

## 五、常见场景

- 每完成一个逻辑完整改动，检查并提交。
- 一个文件含多个独立改动时，用交互式暂存挑选部分内容。
- 用 log 和 show 找到历史原因；用 blame 定位最近改动者，再结合上下文确认。

## 六、踩坑点

- 不看 git diff 就直接 add 全部文件，误提交调试输出、密钥或生成物。
- 一个提交混入多个不相关功能，review 和回滚都困难。
- 把 branch 理解成完整复制仓库，误以为创建成本很高。
- 为了“历史漂亮”把工作内容拆成大量无意义提交。
- 把未经检查的 secrets 推到远端；删除文件并不能从历史中消除泄露。

## 七、项目中的实际使用

每次提交前检查 status 与 diff，确认提交范围、忽略本地配置和凭据。提交消息说明变化目的，必要时再写影响和验证方式。

一个可 review 的提交应尽量聚焦单一意图：例如新增输入校验及其测试，而不是顺手重排整仓格式。

## 八、一句话总结

**先看差异，再选入暂存区，最后把一个清晰意图保存成快照。**

## 九、核心问答

### 1. 工作区与暂存区的区别是什么？

工作区是当前改动；暂存区是下一次提交准备包含的精确内容。

### 2. git add 会创建提交吗？

不会。它把变更放入暂存区，提交需执行 git commit。

### 3. 为什么提交前看 staged diff？

普通 diff 查看未暂存变化；staged diff 检查真正要进入提交的内容。

### 4. 删除本地密钥文件能否消除泄露？

不能。它可能仍在 Git 历史和远端副本中；应轮换密钥并按泄露事件流程处理。

## 十、自测与答案

1. 如何查看未暂存和已暂存的差异？
2. 一个文件里有两个功能，如何只把其中一个放入当前提交？
3. 为什么短小聚焦的提交更容易 review？
4. .gitignore 是否会阻止已经被跟踪的文件提交？

<details>
<summary>参考答案</summary>

1. git diff 查看未暂存差异；git diff --cached 查看暂存差异。
2. 用 git add -p 选择区块，检查 staged diff 后提交。
3. 评审者更容易判断变更因果，也便于单独撤销。
4. 不会；已跟踪文件仍会跟踪，需要明确取消跟踪并保护敏感历史。
