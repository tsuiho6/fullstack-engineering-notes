# 服务端与编解码闭环：从字节流到一次方法调用

> 优先级：⭐ 必须掌握

## 一、是什么

GeeRPC 服务端做四件事：接收连接、协商协议、读取请求并调用服务、把结果编码回客户端。Codec 负责“字节 ↔ Go 值”，Server 负责“请求 ↔ 服务方法”。

## 二、为什么需要

如果把网络读取、协议解析、方法查找和业务调用揉成一个函数，代码很快会变成无法测试的循环。分层后，每层只回答一个问题：

```text
Listener：谁连进来了？
Option：双方说什么协议？
Codec：这一帧如何读写？
Server：请求应该交给哪个服务方法？
Service：反射调用得到什么结果？
```

## 三、核心用法

### 1. 接收连接

```go
func (s *Server) Serve(l net.Listener) error {
	for {
		conn, err := l.Accept()
		if err != nil {
			return err
		}
		go s.ServeConn(conn)
	}
}
```

输入：`net.Listener`。输出：每条连接一个服务协程。TCP 和 Unix socket 的上层处理可以共用这套结构。

项目写法要处理关闭语义：监听器被主动关闭时，应返回可识别的错误，而不是无限重试或把正常关闭记录成故障。

### 2. 连接级协议交换

```go
func (s *Server) ServeConn(conn net.Conn) {
	defer conn.Close()

	var opt Option
	if err := json.NewDecoder(conn).Decode(&opt); err != nil {
		return
	}
	if err := validateOption(opt); err != nil {
		return
	}

	cc, err := newCodec(opt.CodecType, conn)
	if err != nil {
		return
	}
	s.serveCodec(cc)
}
```

教学代码中 `Option` 固定使用 JSON，是为了让服务端在还不知道后续 Codec 时能先读懂协商信息；后续 Header/Body 再由 `CodecType` 决定。

### 3. 请求循环与并发处理

```go
func (s *Server) serveCodec(cc Codec) {
	var wg sync.WaitGroup
	var sending sync.Mutex
	defer wg.Wait()

	for {
		req, err := s.readRequest(cc)
		if err != nil {
			if errors.Is(err, io.EOF) {
				return
			}
			return // 头部无法解析时，继续读通常会失去帧边界
		}
		wg.Add(1)
		go s.handleRequest(cc, req, &sending, &wg)
	}
}
```

注意两个并发边界：

- `readRequest` 通常由一个读循环顺序执行，避免多个 goroutine 同时从同一连接读。
- `handleRequest` 可以并发；`sendResponse` 必须由 `sending` 锁保护完整响应帧。

### 4. 错误响应

```go
func (s *Server) sendError(cc Codec, h *Header, err error, sending *sync.Mutex) {
	h.Error = err.Error()
	sending.Lock()
	defer sending.Unlock()
	_ = cc.Write(h, struct{}{})
}
```

输入：原请求的 `Header` 和服务端错误。输出：保留 `Seq` 的错误响应。这样客户端仍能找到对应 `Call`，不会把一个服务错误误认为连接断开。

## 四、核心原理

### 1. 为什么只在 Header 解析失败时结束连接

Header 是后续 Body 的入口信息；如果 Header 都无法解析，服务端不知道 Body 应该读多少、属于哪个请求。继续读取可能把随机字节当成下一帧，错误会扩散。

但如果只是某个业务方法不存在或方法执行失败，服务端仍能构造带错误的响应，连接通常可以继续服务后续请求。

```text
协议层错误 → 连接状态不可信 → 关闭/终止
业务层错误 → Seq 仍然明确 → 返回错误响应
```

### 2. 为什么 `WaitGroup` 必须在连接退出前等待

读循环结束不代表处理协程已经结束。若直接关闭连接，仍在编码响应的协程会遇到写失败；更糟的是它可能访问连接上的已释放资源。

正确的生命周期是：

```text
停止读取 → 等待已启动的请求处理完成 → 关闭 Codec/连接
```

项目中是否等待所有请求，需要结合优雅关闭策略；至少要保证关闭顺序和文档语义一致。

### 3. Body 反序列化为什么必须传指针

解码器需要把数据写入目标值。传值只能得到一个副本，无法把结果写回调用者：

```go
var reply int
_ = cc.ReadBody(&reply) // 可写目标
```

反射代码中，参数可能本来就是 `*T`，也可能是 `T`。需要根据 `reflect.Type.Kind()` 创建正确形状，不能机械地再取一次地址。

## 五、常见场景

- **TCP**：跨机器默认选择，适合长连接和多次 RPC。
- **Unix socket**：同机进程间通信，通常有更低的网络开销和文件系统权限控制。
- **HTTP 入口**：需要复用 HTTP 端口、代理或调试页面时使用；底层 RPC 仍可保持二进制协议。
- **直接 HTTP JSON**：当对端是浏览器、第三方或公共 API 时，不要为了“像 RPC”而强行复用二进制 RPC。

## 六、踩坑点

1. **只加锁写 Header**：Body 仍可能和其他请求交错。
2. **多个 goroutine 同时 ReadBody**：同一字节流会被不同请求抢读，帧立刻失步。
3. **服务错误直接关闭连接**：把可恢复的业务错误升级成连接级故障。
4. **协议错误继续读**：无法确认下一帧边界时，继续读只会制造更多假错误。
5. **忘记 `defer conn.Close()`**：连接泄漏；客户端重试后服务端连接数不断增长。
6. **解码目标不是指针**：看起来没有报错，结果却没有写入调用者。
7. **在发送锁里执行业务调用**：会让慢请求阻塞所有响应；锁只保护写报文。
8. **`log.Fatal` 放进库代码**：库不应直接终止宿主进程，应返回错误交给调用方决定。

## 七、项目中的实际使用

推荐把服务端组织为：

```text
Serve(listener)
  └─ ServeConn(conn)
       ├─ readOption / validateOption
       ├─ newCodec
       └─ serveCodec
            ├─ readRequest
            ├─ findService
            ├─ handleRequest
            └─ sendResponse
```

项目补强项：

- 给每条连接配置最大帧大小、读写 deadline 和连接级日志字段。
- 业务方法发生 panic 时恢复并转为明确错误，避免整个服务进程被带崩。
- 统计连接数、请求数、处理耗时、编解码错误和主动关闭原因。
- 使用 `go test -race` 验证 response 写锁、服务注册表和连接状态。

## 八、一句话总结

**服务端的最小闭环是“一个读循环保证帧顺序，多个处理协程并发执行，一把发送锁保证响应完整”。**

## 九、核心问答

1. **为什么服务端可以并发处理请求，却通常只用一个读循环？**  
   读取同一字节流必须顺序进行；处理已拆出的请求可以独立并发。

2. **业务方法不存在时应该关闭连接吗？**  
   通常不必；方法名仍属于一个完整请求，可以返回带 `Seq` 的错误响应。

3. **为什么发送响应需要 `WaitGroup`？**  
   防止连接已关闭而处理协程仍在写响应，确保生命周期可控。

4. **Codec 的职责是否包括服务注册？**  
   不包括。Codec 只负责编码和解码；服务查找与方法调用属于 Server/Service 层。

## 十、自测与答案

### 题目

1. 如果两个请求的业务处理同时完成，服务端应如何写响应？
2. 哪类错误更可能要求终止连接：方法不存在，还是 Header 无法解析？为什么？
3. `ReadBody(&reply)` 与 `ReadBody(reply)` 的关键区别是什么？
4. 为什么发送锁不能包住 `req.svc.call(...)`？

<details>
<summary>展开答案</summary>

1. 可以并发完成，但每次写完整的 Header+Body 时必须持有同一把发送锁。
2. Header 无法解析时终止，因为后续帧边界不可信；方法不存在仍可按当前 Seq 返回业务错误。
3. 前者传入可写地址，解码结果能写回；后者传值，通常不能修改调用者持有的变量。
4. 业务调用可能很慢；锁应只保护响应字节写入，否则一个慢请求会阻塞所有响应。
