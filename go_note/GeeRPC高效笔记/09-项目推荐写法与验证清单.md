# GeeRPC 项目推荐写法与验证清单

> 优先级：⭐ 必须掌握

这篇不再新增机制，而是把教学实现翻译成真实项目会关心的工程约束。

## 一、是什么

GeeRPC 的教学代码是一条最小可运行骨架；项目推荐写法是在这条骨架上补齐模块边界、生命周期、错误分类、超时、协议演进、安全和测试。

## 二、为什么需要

“本地能调用”距离“服务可以长期运行”还有很大差距。真实系统会遇到：

- 连接中断、半开连接和服务重启；
- 请求乱序、迟到响应和重复重试；
- 版本不一致、异常大包和恶意输入；
- 注册中心短暂不可用、地址过期和实例抖动；
- 关闭时仍有请求、goroutine 泄漏和指标缺失。

项目化的目标不是无限加功能，而是把这些边界变成明确的接口、状态和测试。

## 三、核心用法

### 1. 推荐目录

```text
geerpc/
├─ go.mod
├─ codec/              # Header/Body 编解码与 framing
├─ protocol/           # Option、版本、错误码、最大帧
├─ server.go           # listener、ServeConn、生命周期
├─ service.go          # 注册和方法分发（教学反射实现）
├─ client.go           # Seq、pending、响应读循环
├─ xclient/             # Discovery、Picker、Client 缓存
├─ registry/            # 注册中心适配，不承载业务调用
├─ internal/            # 测试辅助和内部工具
└─ cmd/                 # 可执行程序和 demo
```

原文为了展示方便把多个版本放在不同目录；项目里应使用 Go module 和包边界，让核心库、示例和测试互不污染。

### 2. 推荐的调用接口

```go
func (c *Client) Call(ctx context.Context, method string, args, reply any) error
```

最少要定义：

- `ctx` 的 deadline/cancel 语义；
- `args` 和 `reply` 的所有权与并发约束；
- 方法名格式和版本策略；
- 连接关闭后的错误；
- 是否自动重试，以及哪些错误可重试。

### 3. 推荐的启动流程

```go
lis, err := net.Listen("tcp", addr)
if err != nil {
	return fmt.Errorf("listen: %w", err)
}

server := NewServer(
	WithMaxFrameSize(4<<20),
	WithLogger(logger),
)
if err := server.Register(userService); err != nil {
	return fmt.Errorf("register service: %w", err)
}

return server.Serve(lis)
```

库代码返回错误；由 `main` 决定是否记录并退出。不要在可复用包里直接 `log.Fatal`。

### 4. 推荐的验证命令

```text
gofmt / go vet
go test ./...
go test -race ./...
go test -run TestClientConcurrent ./...
go test -bench . ./...
```

重点不是“命令越多越专业”，而是每个命令对应一个可验证目标：编译/格式、静态问题、功能、数据竞争、性能基线。

## 四、核心原理

### 1. 教学实现到项目实现的迁移表

| 教学实现 | 保留的原理 | 项目推荐改写 |
|---|---|---|
| `Option` 用 JSON | 连接级协议交换 | 固定版本、Codec、最大帧和能力协商 |
| Gob 编解码 | Codec 可插拔 | 跨语言优先 schema + 生成代码 |
| 反射注册 | 名称到方法的映射 | 稳定 API 优先生成 stub；反射只放内部/教学层 |
| `context.WithTimeout` | 调用方可控 deadline | 全链路传递 context，错误保留 `errors.Is` 语义 |
| 单个 Client 缓存 | 长连接复用 | 按地址管理池、坏连接删除、限制规模 |
| 手写 Registry | 心跳和 TTL 机制 | 使用成熟注册中心或明确租约/安全协议 |
| `Broadcast` 返回第一个成功 | 并发 fan-out | 明确聚合/quorum/全成功语义，避免共享 reply |
| 全局默认 Server | 调用方便 | 项目优先显式构造和依赖注入 |

### 2. 资源生命周期图

```text
Server start
  ├─ listener
  ├─ registry lease
  └─ heartbeat

Server shutdown
  ├─ stop accepting
  ├─ stop heartbeat / revoke lease
  ├─ wait in-flight handlers
  └─ close connections

Client start
  └─ dial / negotiate / start input loop

Client close
  ├─ stop new calls
  ├─ fail pending calls
  ├─ close codec/connection
  └─ stop discovery refresh
```

每个箭头都要有测试或代码审查证据；最常见的长期 bug 不是算法错，而是退出路径忘了释放一个资源。

### 3. “形状检查”清单

虽然 GeeRPC 没有 tensor 的 `dtype/device`，仍可用同样的严谨方式检查：

| 检查维度 | 必问问题 |
|---|---|
| shape | `ServiceMethod`、`Seq`、args、reply、Header/Body 是否一一对应？ |
| type | `T`/`*T`/`**T` 是否正确？Codec 是否支持该类型？ |
| ownership | reply、slice、连接、body、ticker、context 谁创建、谁释放？ |
| device/transport | 数据正在 TCP、Unix 还是 HTTP 通道？协议是否匹配？ |
| lifecycle | 连接关闭、实例下线、请求超时后，状态如何收敛？ |
| concurrency | 哪把锁保护哪些字段？是否把网络调用放进锁？ |

## 五、常见场景

- **学习框架内部**：保留反射、Gob 和简易 Registry，配合单元测试理解机制。
- **Go-only 小型内网工具**：可以使用简化 RPC，但仍要有 context、错误、超时和版本约束。
- **多语言生产服务**：优先 gRPC/Protobuf 或组织标准 RPC，不建议自建协议。
- **公网/浏览器 API**：优先 HTTP/JSON 或明确的公共协议，RPC 内部模型不应直接暴露。

## 六、踩坑点

1. **把教学 demo 当生产库**：缺少鉴权、TLS、限流、最大帧、优雅关闭和可观测性。
2. **所有调用共享一个无限期 context**：请求取消无法传播，故障会堆积。
3. **自动重试没有幂等键**：网络超时会制造重复副作用。
4. **连接池只增不减**：地址变化或错误重连会造成资源泄漏。
5. **把注册中心当健康检查**：心跳和真实业务健康不是同一指标。
6. **错误都变成字符串**：上层无法判断是否超时、是否连接错误、是否可重试。
7. **测试只有成功路径**：真正的 bug 多在乱序、断连、超时、关闭和并发更新。
8. **为了“当前常用”盲目加抽象**：先保证最小闭环和可测试，再按瓶颈扩展。

## 七、项目中的实际使用

### 最小测试矩阵

| 类别 | 至少验证 |
|---|---|
| 协议 | 正常 Option、错误 magic、未知 Codec、截断帧、超大帧 |
| 服务注册 | 合法方法、非法方法、重复服务、找不到服务/方法 |
| 客户端 | 单次调用、并发调用、乱序响应、异步 Done、关闭 pending |
| 故障 | Dial 超时、写失败、读断开、迟到响应、服务端错误 |
| 取消 | deadline 到期、上游取消、服务端遵守 context、只响应一次 |
| HTTP | 正确 CONNECT、错误 method/path、非 200、连接劫持失败 |
| 发现 | 空列表、更新副本、随机/轮询、坏实例、关闭连接缓存 |
| 注册中心 | 注册、续租、过期删除、心跳停止、注册中心不可用 |

### 推荐的观测字段

一次调用至少应能关联：

```text
request_id / seq
service_method
server_addr
codec / protocol_version
start_time / duration
result: success | remote_error | timeout | transport_error
retry_count
```

`Seq` 适合做连接内关联键；跨服务链路要有独立的 trace/request ID，不要把二者混为一谈。

### 现代 Go 习惯

- 使用 `any` 表达空接口，但优先设计强类型 API；
- 使用 `context` 传递取消和 deadline，派生后 `defer cancel()`；
- 使用 Go module 管理依赖，提交 `go.mod`/`go.sum`；
- 用 `io.ReadAll` 等当前 API，避免把旧版 `ioutil` 写进新代码；
- HTTP 客户端复用 `http.Client`，每个 response body 都关闭；
- 库函数返回 error，不在内部 `os.Exit` 或 `log.Fatal`；
- 先 `gofmt`，再跑测试和 race detector。

## 八、一句话总结

**把教学 RPC 变成项目能力，关键不是再加几个功能，而是补上协议边界、生命周期、错误语义、并发验证和安全约束。**

## 九、核心问答

1. **为什么 `go test -race` 对 GeeRPC 特别重要？**  
   客户端 pending、服务列表、连接状态和响应写入都天然并发，普通功能测试不一定能发现数据竞争。

2. **为什么要把 Seq 和 trace/request ID 分开？**  
   Seq 只在一条连接内关联响应；trace/request ID 用于跨服务调用链，生命周期和传播范围不同。

3. **为什么生产优先生成代码？**  
   可以把接口、字段和调用形状前移到编译期，降低反射错误并改善跨语言兼容。

4. **注册中心不可用时，客户端最重要的选择是什么？**  
   是否继续使用最近快照，以及快照最多允许陈旧多久；这决定可用性和新鲜度的取舍。

5. **为什么不能把超时自动重试当成通用可靠性方案？**  
   超时不代表未执行，非幂等操作重试会造成重复副作用。

## 十、自测与答案

### 题目

1. 一个项目只增加了 TLS，就能把教学版 GeeRPC 变成生产级 RPC 吗？
2. 为什么客户端需要同时测试“乱序响应”和“连接断开”？
3. 哪些资源需要在 shutdown 路径上明确释放？
4. 如果测试通过但 `go test -race` 失败，应该如何判断？
