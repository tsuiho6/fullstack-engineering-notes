# 服务发现与负载均衡：先知道有哪些，再决定调用谁

> 优先级：⭐ 必须掌握

## 一、是什么

服务发现回答“当前有哪些服务实例地址”；负载均衡回答“本次请求选择哪个地址”。GeeRPC 用 `Discovery` 把地址来源和选择策略抽象出来，再由 `XClient` 复用每个地址的 `Client`。

## 二、为什么需要

多实例部署后，客户端不应把所有地址和实例生命周期硬编码在业务代码里。否则：

- 扩缩容需要修改客户端配置；
- 失效实例仍被持续调用；
- 每次调用都重新建连接，浪费握手和连接资源；
- 选择策略和业务调用纠缠，难以测试。

## 三、核心用法

### 1. Discovery 接口

```go
type SelectMode int

const (
	RandomSelect SelectMode = iota
	RoundRobinSelect
)

type Discovery interface {
	Refresh(ctx context.Context) error
	Update([]string) error
	Get(SelectMode) (string, error)
	GetAll() ([]string, error)
}
```

输入：地址列表、选择模式和可选刷新 context。输出：一个地址或全部地址。`MultiServersDiscovery` 只维护静态列表，不负责检测实例健康。

### 2. 轮询的最小实现

```go
func (d *MultiServersDiscovery) Get(mode SelectMode) (string, error) {
	d.mu.Lock()
	defer d.mu.Unlock()

	if len(d.servers) == 0 {
		return "", errors.New("rpc discovery: no available servers")
	}
	switch mode {
	case RandomSelect:
		return d.servers[d.random.Intn(len(d.servers))], nil
	case RoundRobinSelect:
		server := d.servers[d.index%len(d.servers)]
		d.index++
		return server, nil
	default:
		return "", fmt.Errorf("unsupported select mode %d", mode)
	}
}
```

`random` 若使用 `*rand.Rand`，必须由锁保护；不要把不具备并发安全保证的随机源放进多个 goroutine 共享。

### 3. XClient 的职责

```text
XClient.Call
  ├─ Discovery.Get(mode) → addr
  ├─ dial(addr) → 复用或创建 Client
  └─ Client.Call(ctx, method, args, reply)
```

按地址缓存连接：

```go
type XClient struct {
	d       Discovery
	mode    SelectMode
	opt     *Option
	mu      sync.Mutex
	clients map[string]*Client
}
```

当缓存 Client 不可用时，先关闭并删除，再重新建立；`Close` 时遍历所有缓存连接并释放。

## 四、核心原理

### 1. 负载均衡不是健康检查

轮询只保证“按顺序选择”；随机只保证“随机选择”。它们不知道实例是否已经宕机、延迟是否过高、是否过载。

```text
Discovery：地址集合
Selector：从集合选一个
Health：这个地址现在是否值得选
Retry：失败后是否换一个再试
```

四者可以组合，但不能相互冒充。

### 2. Round Robin 的核心公式

```text
selected = servers[index mod n]
index = index + 1
```

直观含义：用一个递增位置把请求均匀分摊到当前列表。列表更新后必须重新处理 `n` 变化，避免索引越界。

### 3. 为什么 `XClient` 要缓存 Client

建立连接包含 DNS、TCP、TLS、协议协商等成本。按地址缓存可以复用长连接和客户端后台读协程。缓存的代价是：必须清理坏连接、处理地址更新、限制连接数量。

### 4. Broadcast 的语义

广播把同一方法并发发给所有实例：

```text
servers = [A, B, C]
  ├─ Call(A)
  ├─ Call(B)
  └─ Call(C)
```

常见教学语义是：任意一个失败则返回一个错误；成功时将某一个成功结果写入 reply。项目中必须明确这不是 quorum、不是聚合，也不保证成功结果来自哪台实例。

## 五、常见场景

- **随机**：实例能力相近、简单分散流量。
- **轮询**：希望选择顺序可预测、实例能力相近。
- **加权轮询**：实例容量不同或有权重配置。
- **一致性哈希**：需要按 key 稳定路由，例如缓存或分片；GeeRPC 教程只提到，没有实现。
- **广播**：配置刷新、健康探测、幂等读；不适合未经设计的写操作。

## 六、踩坑点

1. **空地址列表直接取模**：`index % 0` 会 panic；先返回可判断错误。
2. **更新列表时不加锁**：读取和写入并发会数据竞争或读到半更新状态。
3. **`GetAll` 直接返回内部 slice**：调用方可能修改发现模块内部状态；返回副本。
4. **选择了坏实例却无限重试**：需要失败摘除、退避和最大尝试次数。
5. **Broadcast 共享同一个 reply**：多个 goroutine 会并发写同一地址。
6. **Broadcast 用于非幂等写**：同一副作用会执行多次。
7. **把轮询当成加权轮询**：实例能力不同会造成慢节点过载或快节点浪费。
8. **缓存 Client 永不清理**：实例地址变化后连接和 map 会持续增长。

## 七、项目中的实际使用

推荐把选择与调用分层：

```text
Resolver/Registry watcher → 当前实例快照
Picker                  → 选择候选实例
Client pool             → 按地址复用连接
Retry policy            → 只对安全错误重试
Call                    → 执行一次有 deadline 的 RPC
```

项目补强项：

- 记录选择结果、实例地址、尝试次数和最终错误；
- 选择前过滤明确不健康或熔断实例；
- 将刷新服务列表和调用请求解耦，避免每次调用同步访问注册中心；
- 让 `Broadcast` 使用每个实例独立 reply，聚合结果由上层显式定义；
- 不在发现锁里执行网络 Dial 或 RPC 调用。

## 八、一句话总结

**服务发现提供“候选集合”，负载均衡提供“选择规则”，XClient 负责把选择结果接到可复用的 RPC Client 上。**

## 九、核心问答

1. **服务发现和负载均衡的区别是什么？**  
   发现维护“有哪些地址”，均衡决定“本次选哪个地址”。

2. **轮询为什么仍可能把请求发给坏节点？**  
   轮询只看列表和索引，不知道实例健康；健康过滤或失败摘除是额外能力。

3. **为什么 `GetAll` 要返回副本？**  
   防止调用方修改内部 slice，破坏发现模块的共享状态。

4. **Broadcast 为什么不适合任意写操作？**  
   同一个副作用会在多个实例执行；除非操作幂等且业务明确需要全实例执行。

5. **为什么按地址缓存 Client？**  
   复用连接、避免重复握手，并让同一实例的并发调用共享一个响应分发器。
