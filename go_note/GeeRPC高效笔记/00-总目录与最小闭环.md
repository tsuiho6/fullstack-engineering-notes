# 7天用 Go 从零实现 GeeRPC：总目录与最小闭环

> 目标：把教程压缩成一条可以解释、写出、判断和排错的 RPC 主干。
>
> 笔记口径：保留原理；教学实现只保留最小闭环；项目写法补上现代 Go 的上下文、错误、并发、协议和可观测性边界。

## 一、先记住整条主线

```text
客户端调用 Foo.Sum
  ↓
选择/复用一个连接
  ↓ 发送 Option（协议协商）
  ↓ 为调用分配 Seq，并放入 pending[Seq]
  ↓ 发送 Header + Body
  ↓
服务端 Accept 连接
  ↓ 校验 Option，选择 Codec
  ↓ 读取 Header + Body
  ↓ ServiceMethod = "Foo.Sum"
  ↓ 注册表查找 Service 与 Method
  ↓ 反序列化 args → 反射调用 → 填充 reply
  ↓ 按 Seq 写回 Header + Body
  ↓
客户端后台读响应
  ↓ 按 Seq 找回 pending[Seq]
  ↓ 解码 reply / 设置 error / 通知 Done
  ↓ 返回结果
```

多实例只是把调用前面再接一层：

```text
Registry / 静态地址列表
  ↓ 服务发现得到 []Server
  ↓ 负载均衡选择一个地址
  ↓ XClient 按地址缓存 Client
  ↓ 复用上面的单连接 RPC 闭环
```

GeeRPC 真正的主干不是“七天写了多少代码”，而是连续回答七个问题：

1. **字节如何变成消息？** → Codec 与消息帧。
2. **消息边界在哪里？** → Option、Header、Body 的协议约定。
3. **字符串如何找到 Go 方法？** → Service 注册与反射。
4. **多个调用如何共用一条连接？** → Seq、pending、后台读协程。
5. **连接或处理卡住怎么办？** → Dial timeout、context、deadline。
6. **地址变化和多实例怎么办？** → Discovery 与负载均衡。
7. **客户端如何知道有哪些实例？** → Registry、心跳、过期清理。

## 三、最小闭环：做到这些就算学会主干

1. 能解释为什么 `net.Conn` 是字节流，不自带一条 RPC 消息的边界。
2. 能写出 `Option → Header → Body` 的一次请求，并说明哪些字段必须能定位响应。
3. 能画出服务端从 `ServiceMethod` 查到 `service` 和 `methodType` 的路径。
4. 能说明为什么客户端必须先把 `Call` 放入 `pending`，再写请求。
5. 能解释为什么“请求处理可以并发，但同一连接的报文写入必须串行”。
6. 能写出 `context.WithTimeout`，并知道取消调用不等于远程函数一定停止。
7. 能区分：服务发现是“有哪些地址”，负载均衡是“选哪个地址”，注册中心是“谁在报告自己活着”。
8. 能说清 `Broadcast` 为什么需要并发、取消和独立 reply，以及它为什么不适合任意写操作。

## 四、优先级与“原理—教学—项目”边界

| 内容 | 教学演示中的作用 | 当前学习口径 |
|---|---|---|
| TCP/Unix `net.Conn` | 展示 RPC 本质是字节流上的协议 | ⭐ 理解传输层与应用层边界 |
| `Option + GobCodec` | 用少量代码完成协议交换与序列化 | ⭐ 理解机制；跨语言项目优先 Protobuf 等明确 schema |
| 反射注册 | 让 `Foo.Sum` 自动映射到方法 | ⭐ 必须理解；生产 RPC 通常优先生成代码 |
| `Seq + pending` | 让一条连接支持并发、乱序响应 | ⭐ 必须能画出状态变化 |
| HTTP CONNECT | 在 HTTP 入口后切换成 RPC 字节流 | △ 了解适配机制；不要和 REST JSON 混为一谈 |
| Random / Round Robin | 展示最小服务选择器 | ⭐ 理解；生产还需健康状态、权重、重试策略 |
| 自制注册中心 | 展示注册、心跳和过期清理 | △ 理解机制；项目通常使用成熟协调系统 |
| 加权轮询、一致性哈希、压缩、动态配置推送 | 展示可能的扩展方向 | ○ 知道存在；先不进入主干复习 |
| `net/rpc` 方法约束 | 作为反射规则来源 | ⭐ 记住调用形状；`net/rpc` 本身已冻结 |

## 五、推荐学习顺序

### 第一轮：只追一条请求

阅读 `01 → 02 → 03 → 04`。先用一个 `Foo.Sum(args, *reply)` 追完请求，不要一开始钻注册中心和负载均衡。

### 第二轮：补齐可靠性

阅读 `05 → 06`。重点回答：连接失败如何返回？调用超时后 pending 如何处理？HTTP 只是传输入口还是改变了 RPC 消息格式？

### 第三轮：补齐多实例

阅读 `07 → 08`。重点区分三件事：发现地址、选择地址、判断地址是否仍然活着。

### 第四轮：项目化和回忆

阅读 `09`，独立画状态图并写最小测试，再用 `10` 的问题回忆。答不出时只回查对应章节。

## 六、全局代码检查口径

这个主题不是机器学习代码，没有 tensor 的 `dtype/device`；对应要检查的是 RPC 的数据形状、Go 类型、连接生命周期和并发所有权：

- **数据形状**：`ServiceMethod`、`Seq`、args、reply 是否一一对应；请求和响应是否使用相同的 Codec。
- **类型**：反射创建的是 `T`、`*T` 还是 `**T`；`reply` 是否真的是可写指针。
- **所有权**：谁负责关闭连接、response body、ticker、context cancel；谁负责调用 `Done`。
- **并发**：哪把锁保护 `pending`，哪把锁保护完整写入；是否把网络 I/O 放进了全局锁。
- **时序**：先注册 pending 再发送；先设置 HTTP header 再写状态码；先校验状态码再解码 body。
- **故障边界**：连接断开时所有 pending 是否都能收到错误；超时后迟到响应是否会被安全丢弃。
- **服务选择**：空列表、地址更新、重复地址、实例下线和选择器并发访问是否有明确语义。

## 八、一句话总结

**RPC 框架就是把“本地方法调用”拆成协议、编解码、调度、并发、超时和服务治理，再在客户端把它重新拼回一个可调用的接口。**
