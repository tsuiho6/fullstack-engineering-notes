## 三、跨章节综合问答

1. **一次 RPC 调用中，哪些状态属于连接级，哪些属于请求级？**  
   连接级包括 Option、Codec、连接关闭状态和后台读循环；请求级包括 `Seq`、ServiceMethod、args、reply、错误和完成通知。

2. **为什么一个服务端连接可以同时处理多个请求，却不能让多个 goroutine 同时读连接？**  
   请求一旦按字节流读出，就可以并发处理；但多个读者会破坏帧边界，必须由一个读循环统一解析。

3. **如果客户端 timeout 后服务端返回成功，客户端如何处理迟到响应？**  
   timeout 路径移除对应 pending；后台读循环发现 Seq 无对应 Call 时消费/丢弃 body，不把结果写入其他调用。

4. **为什么服务端方法注册和注册中心注册不能用同一个“注册表”理解？**  
   前者是进程内的“服务名 → 方法集合”，后者是系统级的“服务实例 → endpoint/租约”；作用域和生命周期不同。

5. **为什么负载均衡不能单独保证可用性？**  
   轮询/随机只决定选择顺序，不知道实例健康、延迟、熔断和重试安全性。

6. **为什么 `Broadcast` 的“任意一个成功就返回”不等同于可靠广播？**  
   其他实例可能仍在执行，返回一个成功结果不表示所有实例成功，也不表示副作用只执行一次。

7. **协议错误和业务错误为什么要区别处理？**  
   协议错误可能让连接无法继续解析；业务错误通常只影响当前 Seq，可以返回错误响应并复用连接。

8. **为什么 `context` 应贯穿 RPC 调用链？**  
   它把上游取消和 deadline 传播给下游，使无效工作有机会尽早停止；否则每层都可能继续占用资源。

9. **如果注册中心暂时不可用，为什么不能马上清空客户端地址列表？**  
   注册中心故障不等于所有业务实例故障；可以短暂使用最近快照，但需要陈旧上限和连接失败修正机制。

10. **GeeRPC 的哪些设计最值得迁移到其他框架？**  
    分层、明确消息边界、Seq 关联、单读循环、响应写锁、上下文取消、发现与调用解耦；具体 Gob/反射/header 协议不必原样迁移。

### C. 判断题

1. “TCP 有序可靠，所以不需要 Seq。”
2. “客户端 context 超时后，服务端函数一定已经停止。”
3. “注册中心能返回地址，所以它就是负载均衡器。”
4. “服务端处理慢时，只要把 handler timeout 设上就不会消耗资源。”
5. “`GetAll` 返回内部 slice 没问题，因为调用方只读。”

<details>
<summary>展开答案</summary>

1. 错。TCP 不提供逻辑调用身份，乱序完成需要 Seq。
2. 错。取消是否影响远端取决于服务端是否收到并遵守 context。
3. 错。注册中心维护实例信息，负载均衡负责从候选集合选择实例。
4. 错。超时可控制响应，但无法强杀不配合取消的业务 goroutine。
5. 不严谨。即使当前调用方只读，未来调用方或并发更新也可能破坏内部状态；应返回副本。

## 五、最终掌握标准

### 能解释

- 能不用文章原句解释完整请求流；
- 能区分协议、Codec、Server、Service、Client、Discovery、Registry；
- 能说明每把锁保护什么，以及为什么不能把网络调用放入锁内。

### 能写出

- 一个合法的 RPC 方法；
- `Option/Header/Codec` 的最小形状；
- `pending[Seq]` 注册与完成；
- context deadline、轮询选择和心跳停止逻辑。

### 能判断何时使用

- RPC、REST/JSON、gRPC/Protobuf 的适用边界；
- 反射与生成代码的取舍；
- 静态地址、注册中心、健康检查和负载均衡的边界。

### 能避开错误

- 不把 TCP Write 当消息边界；
- 不让多个 goroutine 同时读同一连接；
- 不把 timeout 当作回滚或远程停止；
- 不对未知幂等性的写操作盲目重试；
- 不把教学注册中心直接当生产基础设施。

## 六、一句话总结

**真正学会 GeeRPC，不是能背出 1000 行代码，而是能从请求流重建每个模块的必要性，并在异常路径上做出正确判断。**
