# 服务注册与反射调用：把 `Foo.Sum` 映射到 Go 方法

> 优先级：⭐ 必须掌握

## 一、是什么

服务注册把一个 Go 对象的可导出方法整理成运行时注册表；反射调用再根据请求中的 `ServiceMethod` 找到参数类型、创建值并执行方法。

```text
"Foo.Sum"
  ↓ 拆分
serviceMap["Foo"]
  ↓ 找方法
methodMap["Sum"]
  ↓ 反射调用
Foo.Sum(args, reply)
```

## 二、为什么需要

如果每新增一个 RPC 方法就手写一个 `switch` 分支，框架代码会和业务方法数量线性膨胀。反射让框架可以在启动时扫描方法，自动建立“名称 → 类型 → 函数”的映射。

代价是：类型检查推迟到运行时，错误信息更复杂，性能和可读性也不如生成代码。因此反射是理解框架的好工具，不一定是生产公共接口的首选。

## 三、核心用法

### 1. 可远程调用的方法形状

GeeRPC 参照 `net/rpc`，方法必须近似：

```go
func (f *Foo) Sum(args Args, reply *int) error
```

检查项：

- 方法名导出；
- receiver 类型导出；
- 两个业务参数，且类型为导出类型或内置类型；
- 第二个参数是指针，用于写回结果；
- 只有一个返回值，类型是 `error`。

### 2. 注册表的最小结构

```go
type methodType struct {
	method    reflect.Method
	argType   reflect.Type
	replyType reflect.Type
	numCalls  atomic.Uint64
}

type service struct {
	name    string
	receiver reflect.Value
	methods map[string]*methodType
}

type Server struct {
	services sync.Map // service name -> *service
}
```

注册输入：一个 receiver。注册输出：服务名和合法方法表。`atomic.Uint64` 是现代 Go 中比手动 `atomic.AddUint64` 更清晰的计数方式。

### 3. 查找与调用

```go
func (s *Server) findService(fullName string) (*service, *methodType, error) {
	dot := strings.LastIndexByte(fullName, '.')
	if dot <= 0 || dot == len(fullName)-1 {
		return nil, nil, fmt.Errorf("invalid service method %q", fullName)
	}
	serviceName, methodName := fullName[:dot], fullName[dot+1:]

	v, ok := s.services.Load(serviceName)
	if !ok {
		return nil, nil, fmt.Errorf("service %q not found", serviceName)
	}
	svc := v.(*service)
	m := svc.methods[methodName]
	if m == nil {
		return nil, nil, fmt.Errorf("method %q not found", fullName)
	}
	return svc, m, nil
}
```

输入：`"Service.Method"`。输出：`service + methodType`，供后续反序列化参数和反射调用使用。

### 4. 反射值的形状

```go
func (m *methodType) newArgv() reflect.Value {
	if m.argType.Kind() == reflect.Pointer {
		return reflect.New(m.argType.Elem()) // *T
	}
	return reflect.New(m.argType).Elem() // T
}

func (m *methodType) newReplyv() reflect.Value {
	return reflect.New(m.replyType.Elem()) // replyType 必须是 *T
}
```

解码时：

```go
argv := m.newArgv()
arg := argv.Interface()
if argv.Kind() != reflect.Pointer {
	arg = argv.Addr().Interface()
}
if err := cc.ReadBody(arg); err != nil { /* ... */ }
```

这里最容易错的是 `T`、`*T`、`**T` 的层级。`replyType` 本身是 `*T`，`newReplyv()` 返回一个可写的 `*T`。

## 四、核心原理

### 1. 为什么 receiver 会占反射参数的第 0 位

Go 方法在反射层可视为带 receiver 的函数：

```text
f.Call([receiver, argv, replyv])
```

因此方法类型检查看到的 `NumIn()` 是 3，不是用户书写的 2。第 0 个是 receiver，后两个才是 RPC 参数。

### 2. 为什么注册时就过滤方法

启动时过滤可以把类型错误提前暴露：

```text
注册阶段：跳过不合法方法
调用阶段：只处理已经验证过的签名
```

直观含义：把动态反射的风险集中在启动阶段，而不是等线上请求触发。

### 3. 反射和生成代码的取舍

| 方式 | 优点 | 代价 |
|---|---|---|
| 反射注册 | 代码短、直观、可动态扫描 | 运行时错误、调用成本、类型边界复杂 |
| 代码生成 | 编译期类型检查、性能稳定、跨语言 schema 友好 | 需要 IDL、生成流程和版本管理 |

GeeRPC 用反射是为了看懂框架本质；生产 RPC 通常优先生成代码。

## 五、常见场景

- **适合反射**：教学框架、插件系统、通用序列化/依赖注入、低频管理接口。
- **适合生成代码**：高频服务调用、跨语言接口、需要严格兼容和编译期检查的系统。
- **不适合暴露任意对象**：业务对象可能带不可序列化字段、隐藏状态或不安全方法；应显式定义 RPC API。

## 六、踩坑点

1. **receiver 写成未导出类型**：服务名或方法可能无法通过框架规则注册。
2. **方法返回 `(reply, error)`**：不符合 `net/rpc` 风格，框架会过滤或调用失败。
3. **reply 不是指针**：服务方法无法填充结果。
4. **ArgType 是 `*T` 却创建成 `**T`**：解码和调用的形状都错。
5. **忘记检查重复注册**：同名服务被覆盖，调用结果取决于注册顺序。
6. **直接用 `strings.Split(name, ".")`**：方法名格式异常或名称含点时边界不清；至少检查最后一个点。
7. **反射 map 并发读写无保护**：注册通常在启动期完成；若支持运行时注册，要有明确并发策略。
8. **把“注册成功”理解成“方法一定可执行”**：Codec 能否编码参数、业务错误和 panic 仍需运行时处理。

## 七、项目中的实际使用

项目推荐的服务边界是：

```go
type UserService struct{ repo UserRepository }

func (s *UserService) Get(ctx context.Context, req *GetUserRequest, resp *GetUserResponse) error {
	// 显式 API、显式依赖、显式错误
	return nil
}
```

如果采用生成式 RPC，不要把这个方法签名机械照搬到 `net/rpc`；应以所选框架的生成接口为准。无论反射还是生成代码，都要固定：

- 方法名和版本策略；
- request/response 的字段形状；
- 空值、错误码、部分成功和兼容演进规则；
- receiver 的依赖和生命周期。

## 八、一句话总结

**服务注册的核心是启动时建立“服务名—方法名—参数类型—函数”的索引，调用时只做查找、解码、反射执行和写回。**

## 九、核心问答

1. **为什么反射检查一个方法的入参数量是 3 而不是 2？**  
   第 0 个入参是 receiver，另外两个才是 args 和 reply。

2. **为什么 reply 必须是指针？**  
   服务方法需要通过它把结果写回框架持有的值。

3. **为什么注册阶段应该过滤非法方法？**  
   把动态错误提前到启动阶段，调用路径可以更简单，线上错误更可控。

4. **服务发现和服务注册是同一件事吗？**  
   不是。这里的服务注册是“一个进程暴露哪些方法”；服务发现是“客户端找到哪些服务实例”。

5. **什么时候不应使用反射调用？**  
   当接口稳定、调用频繁、跨语言或需要强编译期保证时，优先使用 schema + 生成代码。
