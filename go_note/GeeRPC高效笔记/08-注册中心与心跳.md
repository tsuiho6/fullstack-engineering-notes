# 注册中心与心跳：用租约维护“当前可用实例”

> 优先级：⭐ 必须掌握；简易 HTTP 实现为 △

## 一、是什么

注册中心保存服务实例的地址和存活状态。服务启动后注册并定期发送心跳；客户端查询仍在租约内的实例，再交给服务发现和负载均衡使用。

```text
服务端启动 → 注册地址
服务端周期性 → 心跳续租
注册中心 → 过期清理
客户端 → 刷新 live servers
XClient → 选择并调用
```

## 二、为什么需要

仅靠客户端硬编码地址无法自然处理：

- 扩容和缩容；
- 实例崩溃；
- 地址变化；
- 服务端重启；
- 临时不可用实例。

注册中心把“实例在哪里、还活着吗”的信息集中管理，让客户端不必直接认识每一个服务进程。

## 三、核心用法

### 1. 最小租约模型

```go
type ServerItem struct {
	Addr      string
	LastSeen  time.Time
}

type Registry struct {
	mu      sync.Mutex
	ttl     time.Duration
	servers map[string]ServerItem
}
```

注册/心跳都更新 `LastSeen`；读取列表时清理已过期项：

```go
func (r *Registry) Alive(now time.Time) []string {
	r.mu.Lock()
	defer r.mu.Unlock()

	servers := make([]string, 0, len(r.servers))
	for addr, item := range r.servers {
		if r.ttl > 0 && now.Sub(item.LastSeen) >= r.ttl {
			delete(r.servers, addr)
			continue
		}
		servers = append(servers, addr)
	}
	slices.Sort(servers)
	return servers
}
```

输入：实例地址和心跳时间。输出：当前未过期的地址快照。返回新 slice，避免暴露内部 map/slice。

### 2. 心跳循环

```go
func Heartbeat(ctx context.Context, registryURL, addr string, interval time.Duration) error {
	if interval <= 0 {
		interval = 30 * time.Second
	}

	if err := postHeartbeat(ctx, registryURL, addr); err != nil {
		return err
	}
	t := time.NewTicker(interval)
	defer t.Stop()

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-t.C:
			if err := postHeartbeat(ctx, registryURL, addr); err != nil {
				return err
			}
		}
	}
}
```

心跳周期必须小于 TTL，并且要考虑网络抖动、请求耗时和重试策略。不要让 ticker 在服务退出后继续运行。

### 3. 教学版 HTTP 注册协议

原文用 HTTP header 传递地址：`POST` 注册/续租，`GET` 获取逗号分隔的服务列表。这能展示机制，但不是生产协议的推荐形态。生产协议应明确版本、实例 ID、租约 ID、TTL、鉴权和错误响应。

## 四、核心原理

### 1. 注册中心是控制面，不是每次调用的数据面

```text
控制面：注册、续租、发现、配置同步
数据面：真正的 RPC 请求和响应
```

调用请求不应每次都同步询问注册中心，否则注册中心成为所有业务调用的单点瓶颈。客户端应缓存服务列表并定期刷新、订阅变更或使用 watcher。

### 2. TTL 与心跳的关系

设租约过期时间为 `T`，心跳周期为 `H`：

```text
H < T
```

直观含义：在正常网络延迟和一次心跳失败的情况下，实例仍有机会续租。实际要留出足够余量，例如 `H` 可以是 `T/3`，但具体值要依据网络和故障检测目标确定。

### 3. 注册中心不可用时怎么办

注册中心故障不应自动等于业务数据面立即全部不可用。常见策略是：

- 使用最近一次成功的地址快照继续调用一小段时间；
- 新实例无法及时加入，旧实例可能无法及时摘除；
- 结合连接失败、健康检查和熔断逐步修正；
- 对“无快照”和“快照过期”分别处理。

这是一种可用性与新鲜度的取舍，必须明确写进项目策略。

## 五、常见场景

- **适合注册中心**：实例动态扩缩容、部署频繁、地址不稳定、多语言服务互调。
- **静态配置足够**：单机、固定少量实例、部署环境已经提供可靠服务发现。
- **生产注册中心**：etcd、Consul、ZooKeeper 等成熟系统，通常带一致性、租约、watch、鉴权和集群能力。
- **不适合自制简易注册中心**：需要强一致配置、跨地域容灾、安全审计或大规模实例管理时。

## 六、踩坑点

1. **心跳周期大于 TTL**：实例会在正常运行时被误删。
2. **心跳 goroutine 不可停止**：服务退出后仍占用资源或不断请求注册中心。
3. **注册中心返回内部 slice/map**：客户端可能修改共享状态或读到并发写入。
4. **用地址作为唯一实例身份**：重启、端口复用或容器漂移时可能混淆，应区分 instance ID 和 endpoint。
5. **只依赖注册中心判断健康**：心跳只能证明实例能发请求，不一定代表业务端点健康。
6. **注册中心列表为空时反复无退避重试**：会造成控制面重试风暴。
7. **把逗号分隔 header 当作长期协议**：地址、版本、元数据和错误语义难以演进。
8. **缺少鉴权/TLS**：任意客户端都可能伪造实例注册或读取内部拓扑。

## 七、项目中的实际使用

推荐流程：

```text
服务启动
  ├─ 生成稳定 instance ID
  ├─ 启动 RPC listener
  ├─ 注册 endpoint + metadata + lease
  └─ 启动可停止的 heartbeat

客户端
  ├─ 通过 watcher/cache 获取实例快照
  ├─ 过滤过期/不健康实例
  ├─ 选择实例并调用
  └─ 失败时按幂等性和 deadline 决定重试
```

简易注册中心代码保留作理解“租约—心跳—过期清理”的练习；项目里优先使用成熟实现，并把注册中心客户端封装在 Discovery 后面，避免业务代码绑定具体产品。

## 八、一句话总结

**注册中心维护实例的动态目录，心跳续租证明实例仍在服务，Discovery 把这份目录转换成客户端可用的地址快照。**

## 九、核心问答

1. **注册中心、服务发现、负载均衡分别是什么？**  
   注册中心维护注册与存活信息；服务发现获取实例集合；负载均衡从集合选择一个。

2. **为什么心跳周期必须小于 TTL？**  
   否则实例还活着但来不及续租，就会被误判为不可用。

3. **注册中心不可用时能否继续调用？**  
   可以短暂使用最近快照，但要接受实例列表可能过期，并结合连接错误和健康策略处理。

4. **心跳成功能证明业务一定健康吗？**  
   不能；它只证明心跳请求能到达注册中心，业务依赖、线程池和真实 RPC 端点可能仍故障。

5. **为什么生产不应直接复制教学版 header 协议？**  
   缺少 schema、版本、实例身份、鉴权、租约和错误语义，难以安全演进。
