# 客户端并发与异步调用：用 `Seq + pending` 复用一条连接

> 优先级：⭐ 必须掌握

## 一、是什么

GeeRPC 客户端允许多个 goroutine 共用一个连接，同时发送多个请求并接收乱序响应。核心结构是：每个调用有一个 `Call`，每个 `Call` 有唯一 `Seq`，客户端用 `pending[Seq]` 找回它。

## 二、为什么需要

最简单的客户端是“发请求、读响应、返回”，一次只能处理一个调用。要提高连接利用率，就必须允许：

```text
发送 A ─┐
发送 B ─┼─ 共用一条连接
发送 C ─┘
        ↓
响应 B、C、A 乱序到达
```

没有 `Seq` 和后台读循环，调用方只能靠响应顺序猜测归属，结果会错写到别的 reply。

## 三、核心用法

### 1. `Call` 的数据形状

```go
type Call struct {
	Seq           uint64
	ServiceMethod string
	Args          any
	Reply         any
	Error         error
	Done          chan *Call
}
```

输入：方法名、args、reply 指针。输出：`Call.Error` 和写入后的 `Call.Reply`。`Done` 用于异步调用完成通知。

### 2. `Go` 与 `Call`

```go
func (c *Client) Go(method string, args, reply any, done chan *Call) *Call {
	if done == nil {
		done = make(chan *Call, 1)
	}
	call := &Call{
		ServiceMethod: method,
		Args: args,
		Reply: reply,
		Done: done,
	}
	c.send(call)
	return call
}

func (c *Client) Call(ctx context.Context, method string, args, reply any) error {
	call := c.Go(method, args, reply, make(chan *Call, 1))
	select {
	case done := <-call.Done:
		return done.Error
	case <-ctx.Done():
		c.removeCall(call.Seq)
		return ctx.Err()
	}
}
```

`Go` 返回后立即交还调用方；`Call` 只是等待 `Go` 的完成结果，并增加 context 取消。

### 3. 客户端的状态与两把锁

```go
type Client struct {
	cc       Codec
	sending  sync.Mutex        // 保护完整请求写入
	header   Header
	mu       sync.Mutex        // 保护 seq/pending/状态
	seq      uint64
	pending  map[uint64]*Call
	closing  bool
	shutdown bool
}
```

分工比“只有一把大锁”更重要：

- `sending`：保证一次请求的 Header+Body 不被其他请求打断。
- `mu`：保护 `seq`、`pending`、关闭状态；不能把慢网络操作长时间放在里面。

### 4. 注册、发送、响应分发

```text
send(call)
  ├─ 加 sending 锁
  ├─ registerCall → pending[seq] = call
  ├─ 写 Header(seq, method) + Body(args)
  └─ 写失败 → removeCall(seq) + done(error)

input()
  ├─ 读响应 Header(seq, error)
  ├─ removeCall(seq)
  ├─ error 非空 → 记录错误并消费 body
  ├─ call 不存在 → 丢弃迟到响应 body
  └─ 正常 → ReadBody(call.Reply) + done(call)
```

关键因果：**必须先注册 pending，再写请求**。否则响应可能快到，后台读循环查不到对应的 `Call`。

## 四、核心原理

### 1. 为什么后台读协程只有一个

多个 goroutine 同时读同一连接，会互相抢 Header/Body，导致一个调用读走另一个调用的数据。后台读协程集中读取，再按 `Seq` 分发，才能保持流解析唯一性。

### 2. 为什么请求可以乱序完成

客户端只要求每个响应带回正确的 `Seq`，不要求按发送顺序完成。这样慢请求不会阻塞快请求，连接的并发利用率更高。

### 3. 连接关闭时为什么要结束所有 pending

连接一旦不可用，未完成的调用不会再收到合法响应。如果不遍历 `pending` 通知它们，调用方会永久阻塞，造成 goroutine 和请求状态泄漏。

```text
连接级故障
  ↓
shutdown = true
  ↓
for every pending call: Error = ErrShutdown; done()
```

### 4. 取消和迟到响应的关系

调用方超时后可以先从 `pending` 删除调用；服务端可能仍在执行并稍后返回。此时客户端读到该 `Seq` 查不到 `Call`，应消费/丢弃 body，而不是把它当成协议错误。

## 五、常见场景

- **适合复用一条连接**：同一服务实例、调用频繁、需要减少连接建立成本。
- **适合异步 `Go`**：批量请求、并行 fan-out、调用方可自行等待或选择性收集。
- **适合同步 `Call`**：普通请求—响应业务逻辑。
- **不适合无限复用单连接**：单连接成为瓶颈、需要隔离租户或不同 deadline 时，应考虑连接池或按地址/策略分片。

## 六、踩坑点

1. **在写请求前没有放进 pending**：快响应会变成“未知 Seq”。
2. **`done` 是无缓冲 channel**：完成通知可能卡住后台读协程；至少要保证通知路径不会永久阻塞。
3. **context 超时后仍让 Call 等待**：调用方已经返回，后台仍应安全清理，不得重复写 reply。
4. **响应找不到 Call 就直接关闭连接**：迟到响应是正常竞态，不一定是协议损坏。
5. **多个写锁只保护 Header**：Body 交错仍会破坏帧。
6. **关闭时只标记 `closing` 不通知 pending**：所有调用方可能永久等待。
7. **把 reply 复用于多个并发 Call**：多个响应会竞争写同一个内存地址，结果不确定。
8. **用 `RWMutex` 保护包含写操作的状态**：注册/删除 pending 都是写，先保证正确再谈细分锁。

## 七、项目中的实际使用

项目推荐：

- `Client` 明确实现 `io.Closer`，调用方统一 `defer client.Close()`。
- `Call` 的完成通知只发送一次；可用内部状态或约定防止重复完成。
- 使用 `context` 做每次调用的 deadline；不要把一个全局 deadline 当成所有调用的唯一超时。
- 连接断开时返回可判断的 sentinel error 或 wrapped error，便于上层决定是否重试。
- 连接复用按远程地址缓存，但要在不可用时删除并重连；重连策略要有退避和上限。
- 对 args/reply 的复用写入并发约束写进 API 文档，必要时由调用方为每次调用创建独立 reply。

## 八、一句话总结

**客户端并发 RPC 的核心不是“开更多 goroutine”，而是用唯一 `Seq` 把乱序响应可靠地分发回对应的 pending Call。**

## 九、核心问答

1. **为什么发送请求和接收响应要拆成两个协程/路径？**  
   发送可以由多个调用并发触发，接收必须由一个读循环顺序解析，再按 Seq 分发。

2. **为什么先注册 pending 再写请求？**  
   避免服务端快速返回时，响应已经到达但客户端还没建立 Seq 到 Call 的映射。

3. **Call 超时后服务端一定停止执行吗？**  
   不一定。客户端取消只代表本地不再等待；远端是否停止取决于服务端是否收到并遵守取消信号。

4. **为什么连接级故障要通知所有 pending？**  
   这些调用已经不可能从该连接得到正常响应，必须被唤醒并收到错误。

5. **什么时候该使用异步而不是同步调用？**  
   当调用方能明确管理并发、收集结果或做 fan-out 时；简单链路优先同步 `Call`，可读性更好。

## 十、自测与答案

### 题目

1. A 的响应先到，但 `pending` 中只有 B，客户端应该怎么处理？
2. 为什么客户端不能让每个 goroutine 自己 `ReadHeader`？
3. `Client.Close()` 后，已经在等待的 `Call` 应该发生什么？
4. `send` 失败后，为什么必须把 Call 从 pending 删除？
