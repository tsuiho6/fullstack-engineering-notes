# 超时、取消与错误边界：让 RPC 不把系统拖死

> 优先级：⭐ 必须掌握

## 一、是什么

超时是“最多等多久”的约束；取消是“这项工作已经不需要继续”的信号；错误边界是把连接、协议、业务和超时分别表达出来。三者相关，但不是同一个概念。

## 二、为什么需要

没有超时，一个故障服务或半开连接可能让：

- 调用 goroutine 永久阻塞；
- 连接和 pending 状态持续占用；
- 上游请求堆积，最终线程、连接、内存耗尽；
- 重试风暴把本来不健康的服务压得更坏。

RPC 的一次调用至少要考虑：建立连接、写请求、等待处理、读响应，以及服务端读取和处理本身。

## 三、核心用法

### 1. 连接建立超时

```go
dialer := net.Dialer{Timeout: 3 * time.Second}
conn, err := dialer.DialContext(ctx, "tcp", addr)
```

输入：地址和连接级上下文。输出：连接或可判断的连接错误。现代 Go 代码优先让 `DialContext` 与调用方 context 关联，而不是只依赖一个全局常量。

### 2. 单次调用 deadline

```go
ctx, cancel := context.WithTimeout(parent, 800*time.Millisecond)
defer cancel()

var reply Reply
if err := client.Call(ctx, "User.Get", &req, &reply); err != nil {
	if errors.Is(err, context.DeadlineExceeded) {
		// 记录超时；是否重试要看方法是否幂等
	}
}
```

`defer cancel()` 用于释放上下文相关资源；调用方通常应把上游请求的 context 继续向下传递。

### 3. 服务端处理超时的正确边界

教学版本可以在服务端等待 `called` 与 timer 之间做选择：

```go
select {
case <-called:
	server.sendResponse(...)
case <-time.After(timeout):
	server.sendError(..., context.DeadlineExceeded)
}
```

但要明确：这只能限制“多久返回给客户端”，不能强行杀死已经运行的 Go 函数。真正可取消的服务方法需要接收并遵守 `context.Context`：

```go
func (s *Service) Work(ctx context.Context, req Request) (Reply, error) {
	select {
	case <-ctx.Done():
		return Reply{}, ctx.Err()
	case result := <-s.doWork():
		return result, nil
	}
}
```

## 四、核心原理

### 1. 超时是分层的，不是一个数字解决一切

```text
连接超时：多久连不上
请求写超时：多久写不出去
处理/等待超时：多久没有可用结果
响应读超时：多久读不完
总 deadline：这次调用从开始到结束最多多久
```

通常把总 deadline 作为用户可见的约束，再让底层阶段尊重它。每个阶段再设更短的独立 timeout，可能出现“总 deadline 还没到，内部先失败”的预期行为，需要记录清楚。

### 2. 取消不等于回滚

客户端超时后返回：

```text
本地等待结束
≠
远程执行已经停止
≠
远程副作用已经撤销
```

因此：

- 读操作通常比较容易安全重试；
- 创建订单、扣款、写入等操作必须有幂等键或去重机制；
- 超时错误不能简单等同于“服务端没有执行”。

### 3. 服务端处理超时的竞态

处理完成和 timer 到期可能几乎同时发生。响应必须只写一次：

```text
called 先到 → 写成功/业务错误响应
timer 先到 → 写超时响应
```

若超时分支写了一次，而后台函数完成后又写一次，客户端会收到两个同 Seq 响应，协议和业务语义都会混乱。需要用明确的状态或 channel 协调“一次响应”。

## 五、常见场景

- **必须设置总 deadline**：跨服务调用、数据库/缓存依赖、批量 fan-out。
- **可以用更长超时**：离线任务、明确由队列承载的异步工作；但仍需资源上限。
- **不适合盲目重试**：非幂等写操作、已经触发下游副作用的请求。
- **不应仅靠服务端 handler timeout**：它可能只控制返回，不会停止占用 CPU、锁和下游连接的工作。

## 六、踩坑点

1. **`context.WithTimeout` 不调用 cancel**：会延长 timer 和关联资源的生命周期。
2. **把超时错误包装成普通字符串**：上层无法 `errors.Is` 判断；应保留 cause 或 sentinel。
3. **超时后立刻无限重试**：会把故障放大为重试风暴。
4. **把 timeout 当作 cancellation**：没有 context 协作时，远端可能继续运行。
5. **服务端 timer 到期后仍写第二个响应**：违反一次请求一个响应的约定。
6. **连接级 `SetDeadline` 影响所有并发请求**：一条连接上的多个调用共享 socket，粗粒度 deadline 可能误伤其他请求。
7. **循环中反复使用 `time.After`**：高频定时逻辑更适合复用 `Timer/Ticker`，并在退出时 Stop。
8. **把 `context.Background()` 传遍业务代码**：会切断上游取消和 deadline。

## 七、项目中的实际使用

建议的错误层次：

```text
连接错误：dial/read/write/closed
协议错误：invalid magic/codec/frame too large
远程错误：服务方法返回的业务错误
取消错误：context.Canceled / context.DeadlineExceeded
服务发现错误：no available server / registry unavailable
```

上层据此决定：记录、降级、选择其他实例或重试。重试前必须回答：

1. 请求是否幂等？
2. 原调用是否可能已在服务端执行？
3. 新的 deadline 是否还足够？
4. 是否需要幂等键、退避和最大次数？

## 八、一句话总结

**超时让调用方及时止损，取消让工作有机会停止，错误分类让上层知道该记录、降级还是安全重试。**

## 九、核心问答

1. **客户端超时后，服务端一定没执行成功吗？**  
   不一定；客户端只是不再等待，服务端可能已执行、正在执行或尚未收到。

2. **为什么 handler timeout 不能等同于强制终止？**  
   Go 没有安全地强杀任意 goroutine 的机制；超时分支最多控制响应，需要 context 协作才能让业务提前退出。

3. **为什么写操作重试要谨慎？**  
   超时不说明远端未执行，重试可能造成重复扣款、重复创建等副作用。

4. **连接超时和调用超时有什么区别？**  
   连接超时发生在建立连接阶段；调用超时覆盖一次 RPC 的等待过程，可能包含发送、处理和读取。

5. **为什么要把 context 传到下游？**  
   上游取消或 deadline 到期时，下游可以尽早释放资源，避免无效工作继续扩散。

## 十、自测与答案

### 题目

1. 调用返回 `context deadline exceeded`，能否直接判断服务端没有执行？
2. 服务端超时响应已经发出，业务 goroutine 后来完成，应该再发成功响应吗？
3. 哪类 RPC 最适合自动重试？
4. 为什么 `context.WithTimeout` 后应 `defer cancel()`？

<details>
<summary>展开答案</summary>

1. 不能；它只说明本地 deadline 到期，远端可能已经执行或仍在执行。
2. 不应；一次调用应只有一个最终响应，后台工作要通过 context 或业务机制停止/收敛。
3. 具有幂等语义、错误可分类、deadline 足够且有退避上限的调用。
4. 及时释放 timer 和上下文关联资源，并在函数提前返回时主动取消派生 context。
