# 从教学版 Gee 到项目：推荐架构与验证清单

## 一、是什么

Gee 教程是一个很好的“框架机制实验”：它用少量代码把 HTTP 入口、路由、Context、分组、中间件、模板和 Recovery 串起来。

项目推荐写法则要额外考虑安全、超时、可观测性、测试、优雅关闭和长期维护。

## 二、为什么需要

教学实现故意简化了很多边界：老版本 Go 的模块组织、手写动态路由、按字符串前缀找组、`interface{}` 数据、直接 `ListenAndServe` 等。照搬会让项目出现错误路由、无限等待、错误响应不一致或静态文件泄露。

学习时要保留原理；落地时要把职责交给标准库或经过验证的组件。

## 三、核心用法

### 1. 普通项目的最小推荐骨架（⭐）

```go
mux := http.NewServeMux()

mux.HandleFunc("GET /healthz", healthz)
mux.HandleFunc("GET /api/v1/users/{id}", getUser)

handler := Recovery(AccessLog(mux))

srv := &http.Server{
	Addr:              ":8080",
	Handler:           handler,
	ReadHeaderTimeout: 5 * time.Second,
	IdleTimeout:       60 * time.Second,
}

log.Fatal(srv.ListenAndServe())
```

Go 1.22+ 的 `ServeMux` 已能处理方法模式、路径通配符和 `Request.PathValue`；如果项目使用更复杂的路由约束，再评估成熟第三方路由器或自研实现。

### 2. Handler 的推荐职责（⭐）

```text
Handler：解析 HTTP 输入、做边界校验、调用 service、选择响应
Service：业务规则、事务边界、权限所需的业务判断
Repository：数据库/外部存储访问
Middleware：横切能力，不承载具体业务流程
```

Handler 不要把 SQL、复杂业务状态机和模板循环全部揉在一起。

### 3. 输入输出契约

每个端点至少明确：

- method + path；
- path/query/header/body 的输入来源；
- body 的 JSON 结构和大小上限；
- 成功/失败状态码；
- Content-Type；
- 是否需要认证、幂等和超时。

## 四、核心原理

### 1. “框架统一”不等于“隐藏标准库”

好的框架抽象保留 HTTP 语义：method、状态码、Header、请求取消和超时都能被业务理解。抽象只减少重复，不应让开发者无法判断请求何时结束、响应何时提交。

### 2. 启动期配置，运行期只读

路由、模板、函数表和中间件链应在启动期构建并校验；请求期尽量只读。这样减少并发锁、数据竞争和“运行一半才发现配置错误”的情况。

### 3. 服务关闭也属于请求生命周期

收到 SIGTERM 后应停止接收新请求，等待已有请求在截止时间内完成，再关闭数据库、消息客户端等资源。只靠进程退出会丢请求、丢日志或截断响应。

## 五、常见场景

| 需求 | 推荐判断 |
|---|---|
| 简单 CRUD API | 先用 `http.ServeMux` 或成熟路由器 |
| 需要学习路由机制 | 实现 Gee Trie，但配套冲突、优先级、并发测试 |
| 服务端页面 | `html/template` + `embed.FS`/`ParseFS` |
| 大量静态资源 | 应用只提供受控路径，生产交给 CDN/网关 |
| 复杂认证授权 | 中间件做身份解析，Service 做资源级授权 |
| 长耗时下游调用 | 全链路使用 `r.Context()`，设置明确 timeout |

## 六、踩坑点

1. **没有服务超时**：慢客户端或慢下游可能长期占用连接和 goroutine。
2. **用 `http.DefaultServeMux` 隐式注册**：全局状态难测试，包初始化顺序也不透明；优先显式创建 `NewServeMux()`。
3. **JSON body 无大小限制**：应使用 `http.MaxBytesReader` 或等价策略保护内存。
4. **只返回 500，不区分错误类型**：客户端无法判断是参数、认证、冲突还是服务器故障。
5. **只用 URL 前缀授权**：必须结合身份、角色和资源所有权。
6. **注册完后仍修改 map**：并发读写会触发数据竞争。
7. **模板/静态文件从工作目录读取**：部署目录变化会导致线上找不到文件；可用 `embed.FS` 固化资源。
8. **错误日志没有 request ID、method、path、耗时**：排障无法串起一次请求。

## 七、项目中的实际使用

### 最小验证矩阵（⭐）

| 模块 | 至少验证 |
|---|---|
| Engine | 实现 `http.Handler`；未知路由返回 404 |
| Router | method 隔离；静态优先；`:param`/`*wildcard`；404/405 |
| Context | query/path/form/body 来源正确；Header 和 status 先后正确 |
| Group | 前缀边界；父子中间件不重复；顺序稳定 |
| Middleware | 前后顺序；Fail 截断；Recovery 捕获 panic |
| Template | FuncMap；模板名；转义；执行失败 |
| Static | 路径根目录；不存在文件；不能访问敏感文件 |
| Server | 超时；取消；优雅关闭 |

### 推荐的端到端最小项目

```text
GET  /healthz                 → 200 text/plain
GET  /api/v1/users/{id}       → 200 JSON / 404
POST /api/v1/users            → 201 JSON / 400
GET  /admin/audit             → Auth + Admin + Logger
GET  /panic                   → Recovery 后 500，日志含堆栈
```

每个端点都用 `httptest.NewRequest` 和 `httptest.NewRecorder` 测试，不需要先启动真实端口。

## 八、一句话总结

**Gee 用来理解框架如何生长，项目用标准库/成熟组件承接路由与服务边界，再用测试证明每条请求链。**

## 九、核心问答

1. **今天为什么还要学 Gee 的 Trie？**  因为它把路由匹配、优先级和参数提取的机制暴露出来；学习价值不等于生产上必须自研。
2. **Go 1.22+ `ServeMux` 改变了什么？**  支持 method pattern、路径通配符和 `PathValue`，覆盖了很多原来需要第三方路由器的基础场景。
3. **为什么路由/模板要启动期构建？**  把配置错误前移，运行期只读，降低锁和数据竞争，也让启动失败更明确。
4. **权限应该放在哪里？**  身份解析可在中间件；资源级授权必须结合业务数据在 Service/领域层再次判断。
5. **为什么 Handler 不应直接承担所有业务？**  HTTP 适配、业务规则和存储访问变化节奏不同，混在一起会难测试、难复用、难替换。
