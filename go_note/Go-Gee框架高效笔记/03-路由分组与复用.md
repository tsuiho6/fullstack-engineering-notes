# 路由分组与复用：把前缀变成权限、版本和中间件边界

## 一、是什么

路由组是带公共前缀、父子关系和中间件配置的一组路由。例如 `Group("/api").Group("/v1")` 共同构成 `/api/v1`。

Gee 把 `Engine` 也视为最顶层 `RouterGroup`，所有子组共享同一个 Engine 和 Router。

## 二、为什么需要

真实项目中，一组路由往往共享：

- URL 前缀：`/api/v1`、`/admin`；
- 认证规则：登录用户、管理员、第三方签名；
- 版本和资源约定；
- 日志、限流、CORS 等中间件。

如果逐条配置，容易漏配、错配，且改前缀要改很多地方。分组把“共同策略”集中到一个边界。

## 三、核心用法

```go
r := gee.New()

public := r.Group("")
public.GET("/healthz", health)

api := r.Group("/api")
api.Use(Auth())

v1 := api.Group("/v1")
v1.GET("/users/:id", getUser)
v1.POST("/users", createUser)
```

关键输入输出：

- `Group(prefix)` 输入前缀，输出共享 Engine 的新组；
- `group.GET(relative, handler)` 输入相对路径，注册完整路径 `group.prefix + relative`；
- `Use(mw...)` 把中间件绑定到组，不直接执行。

推荐的结构：

```go
type RouterGroup struct {
	prefix      string
	parent      *RouterGroup
	middlewares []HandlerFunc
	engine      *Engine
}
```

## 四、核心原理

### 1. 分组是“配置继承”，不是复制 Router

所有组共享同一个路由器；组只保存公共配置。注册时把相对 pattern 解析成完整 pattern，运行时再根据命中的路由决定中间件链。

这样做的好处是：路由表只有一份，分组不会造成请求分发的多套逻辑。

### 2. 父组策略如何作用到子组

可以有两种实现：

1. **注册时展开**：创建子组时复制父组的中间件列表。
2. **请求时收集**：沿父链或已注册组收集所有适用中间件。

教程采用“保存所有 groups，再按前缀扫描”的简化做法，适合演示；项目推荐显式保存组层级或在注册路由时生成最终链，减少运行时歧义。

### 3. 分组匹配必须是边界匹配

前缀 `/api` 的正确语义通常是 `/api`、`/api/xxx`，而不是 `/apianything`。因此应按路径段判断，或直接让路由注册结果决定组归属。

## 五、常见场景

| 分组 | 典型策略 | 是否适合 |
|---|---|---|
| 全局组 `/` | request ID、日志、Recovery | 适合全局一致策略 |
| `/api` | JSON 默认响应、CORS、限流 | 适合 API 共同策略 |
| `/api/v1` | 版本兼容、版本级鉴权 | 适合渐进演进 |
| `/admin` | 管理员权限 | 适合高风险边界 |
| 单个特殊路由 | 一次性业务规则 | 不必强行建组，直接 Handler/专用中间件更清楚 |

## 六、踩坑点

1. **把前缀当权限**：URL 前缀只是路由组织方式，不等于用户已授权；鉴权仍需验证身份、角色、资源归属。
2. **父子组中间件重复执行**：复制策略和运行时收集策略不能混用，否则会重复执行。
3. **组创建顺序影响中间件顺序**：要有稳定规则，并用测试验证全局 → 父组 → 子组 → Handler。
4. **相对路径拼接不统一**：`/api` + `users` 与 `/api` + `/users` 会产生问题；最好在注册时规范化。
5. **把 Engine 与 Group 生命周期混淆**：Engine 应拥有 Router 和组集合；Group 只是注册入口和策略容器。

## 七、项目中的实际使用

推荐以业务边界组织：

```text
Engine
├── global middleware
├── /healthz                 无鉴权
├── /api/v1                  用户认证
│   ├── /users
│   └── /orders
└── /admin                   管理员鉴权 + 审计日志
```

更重要的是把“谁能访问”放在中间件/服务层，而不是只凭组名判断。路由组负责组织入口，业务服务负责最终授权。

## 八、一句话总结

**分组把公共前缀和公共策略绑定到同一条边界上，但分组本身不是权限证明。**

## 九、核心问答

1. **为什么 Engine 可以直接拥有 RouterGroup 的能力？**  
   Engine 嵌入顶层 RouterGroup，天然拥有 `Group`、`GET`、`Use` 等注册方法，同时还持有 Router 和组集合。

2. **嵌套分组解决了什么问题？**  
   把 `/api`、`/v1` 等多层公共配置组合起来，子组继承父组边界和策略。

3. **为什么不能仅凭 `/admin` 前缀认定管理员？**  
   前缀只说明请求落在哪个路由组，未证明请求者身份、角色或资源权限。

4. **教程按所有组做 `HasPrefix` 扫描有什么局限？**  
   可能误判相似前缀、依赖组遍历顺序，并在运行期做不必要工作；生产代码应有明确的组归属。

### 题目

2. 设计全局、API、管理员三层中间件时，执行顺序应如何排列？
3. 为什么路由组共享一个 Router 比每组创建一个 Router 更容易维护？
4. `/api` 与 `/apianything` 的边界如何避免误匹配？

1. `/api/v1/users`。
2. 全局 → API → 管理员 → Handler；收尾时反向返回。
3. 路由查找、method/path 规则和 404/405 逻辑只有一份，避免多 Router 分发和配置漂移。
4. 按路径段匹配，或用路由注册时的明确组归属，不要只用字符串前缀。
