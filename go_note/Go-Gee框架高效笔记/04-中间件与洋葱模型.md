# 中间件与洋葱模型：让请求前后都能插入通用能力

## 一、是什么

中间件是包在 Handler 外层的请求处理函数，用来实现日志、鉴权、Recovery、限流、CORS、请求 ID 等非业务能力。

Gee 的关键设计是：中间件和业务 Handler 具有相同签名 `func(*Context)`，由 `Context.Next()` 把控制权交给链中的下一个函数。

## 二、为什么需要

如果没有中间件，日志、认证和错误处理只能复制到每个 Handler 中；复制会造成遗漏、顺序不一致和维护困难。

中间件的价值在于“一次定义，多处复用”，并且能同时覆盖请求前和请求后两个阶段。

## 三、核心用法

### 1. 中间件的最小形状（⭐）

```go
type HandlerFunc func(*Context)

func Logger() HandlerFunc {
	return func(c *Context) {
		start := time.Now()
		c.Next() // 交给下游
		log.Printf("%s %s %d %v", c.Method, c.Path, c.StatusCode, time.Since(start))
	}
}
```

`c.Next()` 前是“进入阶段”，之后是“退出阶段”。如果不调用 `Next()`，当前链会被截断。

### 2. Context 驱动的链（教学实现）

教程中的核心状态只有两项：`handlers []HandlerFunc` 保存当前请求的中间件和最终 Handler；`index int` 保存当前执行位置，初始化为 `-1`。`Next()` 每次先递增 index，再循环执行剩余函数。

典型链是 `[Logger, Auth, Handler]`：

```text
Logger 前
  Auth 前
    Handler
  Auth 后
Logger 后
```

### 3. 中止当前链

`Fail(code, msg)` 应完成两件事：把执行位置推进到链尾，阻止后续 Handler；写出唯一一份错误响应。输入是状态码和错误消息，输出是当前请求的错误响应。

## 四、核心原理

### 1. 为什么会形成“洋葱”

每个中间件在调用 `Next()` 前后都有代码；调用 `Next()` 相当于进入下一层，下一层返回后再回到当前层，因此调用栈天然形成嵌套结构。

若链为 `A → B → Handler`，执行顺序为：

```text
A-before → B-before → Handler → B-after → A-after
```

这正好适合计时、记录状态码、释放资源和统一收尾。

### 2. 顺序是行为的一部分

- Recovery 必须包住可能 panic 的下游；
- Auth 必须早于业务 Handler；
- Logger 若要拿到最终状态码，必须在 `Next()` 返回后记录；
- CORS 若要覆盖错误响应，不能只写在业务成功路径。

中间件不是简单列表，而是有顺序语义的控制流。

### 3. 全局、分组、路由级

推荐链：

```text
全局 → 父组 → 子组 → 路由级 → Handler
```

越外层，越适合通用能力；越内层，越适合局部策略。只对单个 Handler 有意义的逻辑，直接写在 Handler 往往更清楚。

## 五、常见场景

| 中间件 | 适合做什么 | 不适合做什么 |
|---|---|---|
| Logger | 记录 method/path/status/耗时/request ID | 记录密码、Token、完整敏感 body |
| Recovery | 隔离请求级 panic，返回 500 | 把所有普通错误都改成 panic |
| Auth | 校验身份、建立用户信息 | 只看 URL 前缀决定权限 |
| Timeout | 给下游传递截止时间 | 强行终止无法响应的任意 goroutine |
| CORS | 设置跨域策略 | 用 `*` 放开带凭据的生产接口 |
| Rate limit | 保护资源和入口 | 代替业务配额系统 |

## 六、踩坑点

1. **忘记 `Next()`**：下游 Handler 不会执行，请求可能无响应或保持默认状态。
2. **`Fail` 后仍调用 `Next()`**：可能重复写 body、改状态码，造成响应不确定。
3. **中间件顺序错误**：Recovery 放在链内但不包住 Handler，就抓不到 panic。
4. **StatusCode 未初始化或未记录**：Handler 直接 `Write` 时，Context 可能仍是 0；可用 ResponseWriter 包装器捕获隐式 200。
5. **把请求数据存入全局变量**：并发请求会互相覆盖；请求级数据放 Context，跨请求状态使用并发安全结构。
6. **在中间件中读取 body 后不恢复**：下游再读会得到空内容；需要明确 body 所有权或重置读取器。
7. **日志泄露敏感数据**：Authorization、Cookie、密码字段应脱敏。

## 七、项目中的实际使用

建议启动时显式组合链，并为顺序写测试：

```go
engine.Use(RequestID(), Recovery(), AccessLog())
api := engine.Group("/api")
api.Use(Auth())
```

一个合格的中间件测试至少验证：下游是否执行；前后顺序是否正确；`Fail` 是否阻止下游；下游 panic 能否被 Recovery 捕获；状态码、Header、body 是否只写一次。

## 八、一句话总结

**中间件是可组合的控制流：`Next()` 之前做前置，之后做收尾，顺序决定语义。**

## 九、核心问答

1. **为什么中间件要和 Handler 使用相同签名？**  因为它们可以放入同一条 handlers 链，框架只需一种调度机制。
2. **`Next()` 的前后代码分别处于什么阶段？**  `Next()` 前是当前层进入请求，之后是下游完成后的退出/收尾阶段。
3. **Recovery 为什么通常要放在全局外层？**  它需要包住尽可能多的下游代码，才能把请求内 panic 转为稳定的 500。
4. **鉴权放在 Router 前还是匹配后？**  通常先匹配到具体路由和分组，再执行相应权限中间件；全局基础策略可以更早执行。
5. **什么时候不该用中间件？**  逻辑只服务一个 Handler、没有复用价值且直接写更清楚时。

## 十、自测与答案

### 题目

1. `A`、`B`、Handler 组成链时，完整执行顺序是什么？
2. 一个鉴权中间件发现用户未登录后，为什么不能只返回 JSON 还继续执行 `Next()`？
3. Logger 为什么通常在 `Next()` 返回后再读取 `StatusCode`？
4. Recovery 放在 Handler 之后会有什么问题？
5. 全局、父组、子组、Handler 的推荐嵌套顺序是什么？

1. `A-before → B-before → Handler → B-after → A-after`。
2. 继续执行会让未授权请求进入业务代码，并可能重复写响应。
3. 因为最终状态码通常由下游 Handler 决定。
4. 它已经无法包住 Handler 的 panic，panic 会继续向上冒泡。
