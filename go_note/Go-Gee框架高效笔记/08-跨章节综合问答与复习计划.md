# 跨章节综合问答与复习计划：把七天内容串成一条请求链

## 一、是什么

跨章节复习不是重新读一遍，而是从“一个请求如何被处理”反推每个组件的职责、依赖和失败边界。

## 二、为什么需要

单章记忆容易变成 API 名词表；真正能迁移的能力是：面对一个新需求，知道该改 Router、Context、Group、Middleware、Handler 还是 Service，并能预判副作用。

## 三、核心用法：一张请求链检查表

对任意端点，按顺序回答：

1. **入口**：谁实现 `ServeHTTP`？服务如何启动和关闭？
2. **输入**：参数来自 path、query、header 还是 body？类型和大小限制是什么？
3. **匹配**：method/path 如何命中？静态规则和动态规则谁优先？
4. **分组**：该路由属于哪个 API/版本/权限组？公共前缀是否精确？
5. **链路**：哪些中间件先后执行？谁负责认证、日志、Recovery？
6. **业务**：Handler 调哪个 Service？Service 是否再次做资源级授权？
7. **输出**：状态码、Header、Content-Type、body shape 是什么？
8. **失败**：404、405、400、401、403、404、409、500 分别由谁产生？
9. **生命周期**：下游调用是否继承 `r.Context()`？超时和取消如何传播？
10. **测试**：能否用 `httptest` 验证成功、失败、并发和 panic？

## 四、核心原理：依赖关系

```text
http.Handler
  └─ Engine.ServeHTTP
       ├─ Context：统一请求/响应
       ├─ Router：method + path → handler + params
       ├─ Group：组织前缀和公共策略
       ├─ Middleware：包住下游并控制顺序
       └─ Handler：HTTP 适配并调用 Service
              └─ Service：业务规则与资源授权
```

依赖方向应尽量向下单向流动：Router 不负责业务，Middleware 不替代 Service，Context 不保存跨请求状态。

## 五、跨章节综合问答

### 1. 请求 `/api/v1/users/42?verbose=1` 的完整路径是什么？

先由 `http.Server` 调用 Engine 的 `ServeHTTP`；Engine 创建 Context；Router 按 method 和 `/api/v1/users/42` 匹配规则，提取 `id=42`；根据组收集全局/API/版本中间件；链调用到 Handler；Handler 从 `Param("id")` 取 42，从 Query 取 `verbose=1`，调用 Service；最终 Context 写 JSON 和状态码。

### 2. 为什么 Query 参数不应该参与 Trie 的 path 匹配？

Query 是路径之外的可选条件，适合过滤、排序、分页；同一资源路径可能有多组 query，不应因此生成大量路由节点。Router 只匹配 path，Handler/Context 再读取 query。

### 3. 如果 `/users/latest` 被当成 `id=latest`，应该查哪一层？

先查 Router 的静态与动态优先级；若静态规则已注册但仍被参数规则抢走，是 Trie 搜索顺序/回溯错误，而不是 Context 或 Handler 的问题。

### 4. 鉴权中间件返回 401，但业务 Handler 仍执行，最可能是什么原因？

鉴权失败后没有中止链，仍调用了 `Next()`；或 `Fail` 没有把执行位置推进到链尾。应测试“未授权请求的业务副作用为零”。

### 5. Logger 记录到状态码 0，说明哪里可能有问题？

Handler 可能直接 `Write` 导致 Context 没捕获隐式 200；也可能没有统一响应方法或 ResponseWriter 包装器。Logger 本身不应猜状态码，应从可靠的响应追踪层读取。

### 6. Handler panic 后客户端仍收到半截成功响应，Recovery 失效了吗？

不一定。Recovery 可能已经捕获 panic，但响应 Header/body 在 panic 前已提交，无法完整回滚。要么接受“已部分提交”的语义，要么使用缓冲响应，但要评估流式响应兼容性。

### 7. 为什么路由组能复用中间件，但不能替代资源授权？

组只能表达入口的组织和公共策略；“用户能否修改 id=42 对应资源”需要身份、资源所有权和业务规则，必须在 Service/领域层判断。

### 8. Gee 的 Context 与 `r.Context()` 应如何协作？

Gee Context 提供 `Param`、`Query`、`JSON` 等 HTTP 便利接口；`r.Context()` 作为下游数据库/RPC的取消和超时载体。二者分工，不互相替代。

### 9. 什么时候应该放弃自研 Router？

当需求只是常规 method/path/参数匹配、没有已测得的特殊性能或语义要求时；Go 1.22+ `ServeMux` 已覆盖基础能力，自研成本应由明确收益证明。

### 10. 如何判断一篇笔记是否真正学会？

能不看资料画出请求链；能手写最小 Engine、Router、Context 和 Middleware；能解释 404/405、静态/动态优先级、Next 顺序和 panic 边界；能为每个错误场景写出测试。

## 七、终局自测

### 题目

1. `Engine`、`Router`、`Context` 三者各自拥有哪一个不能互相替代的职责？
2. 如何解释中间件顺序 `Logger → Recovery → Auth → Handler` 的进入与退出？
3. `/api` 和 `/apianything` 的分组误匹配为什么会影响安全？
4. 一个 Handler 返回 JSON 时，至少要检查哪些输入输出和时序？
5. 生产服务除了教程七天内容，还必须补哪三类能力？

<details>
<summary>展开答案</summary>

1. Engine 接管统一入口；Router 负责匹配；Context 负责请求级 HTTP 状态和便利操作。
2. 进入：Logger → Recovery → Auth → Handler；返回：Handler → Auth → Recovery → Logger。Recovery 包住 Auth/Handler，Logger 最后拿最终状态。
3. 可能让不属于 API 组的路径获得认证、限流或其他策略，导致策略边界错误。
4. 输入来源/类型与校验、业务调用的 request context、Content-Type、状态码先于 body、JSON 编码错误处理，以及不重复写响应。
5. 至少是安全边界、生命周期与超时、可观测性与测试；生产还通常需要优雅关闭和资源治理。
