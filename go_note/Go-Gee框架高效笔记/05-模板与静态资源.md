# 模板与静态资源：完成服务端渲染的最小闭环

## 一、是什么

模板是“数据 + HTML 模板 → HTML 响应”的渲染机制；静态资源是 CSS、JavaScript、图片、字体等不需要业务计算的文件。

Gee 第六天把两者接入 Context：`HTML` 执行预先加载的 `html/template`，`Static` 把 URL 路径映射到文件系统。

## 二、为什么需要

模板把页面结构和业务数据分开，避免在 Handler 里拼接 HTML 字符串。静态资源服务让浏览器能加载页面依赖，否则 SSR 页面只有 HTML 骨架，样式和脚本无法访问。

但 SSR 不是默认最优解：前后端分离、纯 API、独立前端部署时，后端通常只返回 JSON。

## 三、核心用法

### 1. 使用 `html/template`（⭐）

模板函数必须在 Parse 前注册；模板应在启动期解析一次，执行阶段只传数据：

```go
//go:embed templates/*.html
var templateFS embed.FS

tmpl := template.Must(
	template.New("").
		Funcs(template.FuncMap{"upper": strings.ToUpper}).
		ParseFS(templateFS, "templates/*.html"),
)

func render(w http.ResponseWriter, name string, data any) error {
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	return tmpl.ExecuteTemplate(w, name, data)
}
```

输入：模板名和数据；输出：写入 `ResponseWriter` 的 HTML；模板引擎：`html/template`，不是 `text/template`。

### 2. 静态资源（⭐）

Go 1.22+ 可以直接基于 `fs.FS` 提供文件服务：

```go
//go:embed static
var staticFS embed.FS

sub, err := fs.Sub(staticFS, "static")
if err != nil {
	log.Fatal(err)
}

mux.Handle("GET /assets/",
	http.StripPrefix("/assets/", http.FileServerFS(sub)),
)
```

输入：URL 前缀和受控的 `fs.FS`；输出：文件内容、Content-Type 和缓存相关响应。嵌入文件时，文件根目录由 `fs.Sub` 明确限定。

### 3. 教程中的 Gee 写法如何理解

`Static("/assets", "./static")` 会注册 `/assets/*filepath`，命中后交给 `http.FileServer`。这段代码演示了“通配路由 + 文件服务器”的组合，不需要背诵每一行。

## 四、核心原理

### 1. 为什么使用 `html/template`

它会根据 HTML、属性、JavaScript、CSS、URL 等上下文进行自动转义，默认把动态数据当作不可信文本。直观含义：模板作者可以控制结构，用户数据不能直接变成可执行标签/脚本。

不要把不可信字符串强制转换成 `template.HTML` 等安全类型；那相当于绕过转义，必须只对经过严格验证的可信片段使用。

### 2. 模板解析与执行要分阶段

```text
启动期：读取模板 → 注册函数 → Parse → 失败则启动失败
请求期：选择模板名 → 传入数据 → Execute → 写响应
```

解析是配置错误，适合在启动期暴露；执行是请求级错误，需要返回 500 或统一错误页。

### 3. 静态文件映射的安全边界

安全做法是让文件服务器持有一个明确的根 `fs.FS`，并由路由前缀剥离 URL 前缀；不要把用户提供的 `filepath` 直接拼到任意系统路径后调用 `os.Open`。

## 五、常见场景

- **SSR 适合**：SEO 重要、首屏需要快速可见、页面结构相对稳定、后端掌握页面渲染。
- **JSON API 适合**：同一后端服务 Web、App、小程序等多种客户端，前端独立迭代。
- **静态资源交给 CDN 更适合**：生产环境资源量大、需要缓存/压缩/版本化时。
- **○ 了解即可**：模板热加载、主题系统、复杂组件化，超出 Gee 主干。

## 六、踩坑点

1. **用 `text/template` 渲染 HTML**：没有 HTML 上下文转义，可能导致 XSS。
2. **FuncMap 注册晚于 Parse**：模板解析时找不到函数，启动失败。
3. **每次请求 Parse 模板**：增加延迟和内存抖动；应启动期解析、请求期执行。
4. **模板名不一致**：`ParseFS` 后执行的 name 通常是文件名或定义名，需用 `Lookup`/测试确认。
5. **Execute 后才设置 Content-Type**：响应可能已提交，Header 修改无效。
6. **静态目录暴露过宽**：不要把项目根目录作为静态根，避免泄露配置、源码和密钥。
7. **错误时继续写成功页面**：模板执行失败后必须停止当前响应流程。
8. **忽略缓存策略**：生产静态资源应使用内容哈希文件名或明确 Cache-Control，避免旧资源和新 HTML 不匹配。

## 七、项目中的实际使用

推荐结构：

```text
web/
├── templates/
│   ├── layout.html
│   └── user.html
└── static/
    ├── app.css
    └── app.js
```

启动阶段：嵌入或读取模板/静态资源，校验所有模板可解析。请求阶段：Handler 只准备 view model，Context 负责选择模板和写响应。

若使用前后端分离，Gee 的 `HTML` 和 `Static` 可以完全不进入服务端；不要为了“教程功能齐全”给纯 API 项目增加 SSR 层。

## 八、一句话总结

**模板负责安全地把数据变成 HTML，静态文件负责提供页面依赖；解析在启动期，执行在请求期。**

## 九、核心问答

1. **为什么模板要用 `html/template` 而不是 `text/template`？**  因为前者按 HTML 上下文自动转义，能降低动态数据造成 XSS 的风险。
2. **为什么 FuncMap 必须在 Parse 前注册？**  模板解析阶段就要识别函数名；注册晚了模板无法构建。
3. **静态文件为什么要用 `fs.Sub` 或明确根目录？**  限制可访问范围，避免用户路径直接穿透到任意系统目录。
4. **模板解析错误应该在什么时候暴露？**  启动期；这是部署配置错误，不应等到线上首个请求才发现。
5. **什么时候不应该使用 SSR？**  后端只是多客户端 JSON 数据源，且页面由独立前端构建和部署时。
