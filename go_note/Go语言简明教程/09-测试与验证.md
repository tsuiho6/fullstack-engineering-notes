# 09 测试与验证

## 一、是什么

Go 自带测试框架；测试文件以 _test.go 结尾，通过 go test 发现和执行。测试让行为可以重复验证，而不是依赖手动记忆。

## 二、为什么需要

程序能编译不代表行为正确。测试把边界条件和预期固定下来，重构后仍可快速发现回归。

## 三、核心用法

表驱动测试适合多个输入共享同一断言逻辑：

~~~go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a, b int
        want int
    }{
        {name: "positive", a: 2, b: 3, want: 5},
        {name: "zero", a: 0, b: 4, want: 4},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := Add(tt.a, tt.b); got != tt.want {
                t.Fatalf("Add(%d, %d) = %d, want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
~~~

常用验证命令：

~~~sh
gofmt -w .
go test ./...
go test -race ./...
go vet ./...
go test -cover ./...
~~~

## 四、核心原理

- _test.go 文件可与被测包同包测试，也可用包名_test 从外部测试公开 API。
- t.Run 为子测试提供独立名称和筛选边界；t.Helper 能让失败位置指向调用者辅助函数处。
- 基础测试聚焦可观察行为，不要依赖实现细节或测试之间的执行顺序。
- 模糊测试从种子输入开始生成数据，检查程序对大量输入是否违反性质；Go 内置 fuzz 支持从 1.18 起提供。

## 五、常见场景

业务规则、错误边界、解析器和并发安全行为都应测试。性能目标用 benchmark 测量，不要凭直觉判断；端到端流程需要少量集成测试补足单元测试。

## 六、踩坑点

- 测试名要以 Test 开头并接大写字母，参数必须是 *testing.T。
- t.Fatal 只能在测试 goroutine 中使用；子 goroutine 应通过 channel/错误结果通知测试 goroutine。
- 测试不要依赖 map 遍历顺序、系统当前时区或真实网络服务，除非测试目标就是这些边界。
- 覆盖率高不等于断言有效；检查测试是否验证了真正重要的结果和错误路径。
- 并发测试应避免依赖 sleep 碰运气；使用同步原语和超时保护。

## 七、项目中的实际使用

先为核心业务规则写快速单元测试，再为数据库/网络边界添加可控集成测试；CI 执行 go test ./... 和 go vet ./...，并在并发代码改动后运行 race detector。Fuzz 和 benchmark 按风险与性能需求添加。

## 八、一句话总结

**测试不是证明所有情况绝对正确，而是把重要行为变成可重复检查的证据。**

## 十、自测与答案

1. 为什么要给失败输出 expected 和 actual？
2. 并发测试为什么不应只依赖 time.Sleep？
3. 覆盖率 100% 是否足以证明质量？

<details>
<summary>展开答案</summary>

1. 可直接看出行为偏差，加速定位失败用例。
2. 调度和机器负载会改变时序；应使用 channel、WaitGroup 等同步方式。
3. 不足；执行到代码不代表断言有意义，也不代表需求边界都被覆盖。
