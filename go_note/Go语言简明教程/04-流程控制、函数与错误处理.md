# 04 流程控制、函数与错误处理

## 一、是什么

流程控制决定语句何时执行；函数封装一个有输入、输出和职责边界的操作；error 是 Go 显式表达可预期失败的常规方式。

## 二、为什么需要

可读的分支和早返回能让成功路径突出、失败边界清楚；显式错误返回避免调用方误把失败当成功。

## 三、核心用法

~~~go
func loadName(id int) (string, error) {
    if id <= 0 {
        return "", fmt.Errorf("invalid id %d", id)
    }
    name, err := queryName(id)
    if err != nil {
        return "", fmt.Errorf("load name for id %d: %w", id, err)
    }
    return name, nil
}
~~~

哨兵错误用 errors.Is 判断；具体错误类型用 errors.As 提取：

~~~go
if errors.Is(err, ErrNotFound) {
    // 按“未找到”处理
}
~~~

## 四、核心原理

- if 可带短初始化语句，其变量作用域仅限该 if 及其分支。
- switch 默认不会贯穿到下一项；fallthrough 很少需要。
- 函数可以返回多个值；常见约定是结果在前，error 在最后。
- 用 %w 包装错误会保留因果链；用 errors.Is 判断错误链中是否包含目标，用 errors.As 查找目标错误类型。
- defer 在所属函数返回前执行，多个 defer 按后进先出；调用参数在注册 defer 时求值。

## 五、常见场景

业务校验失败、数据库/网络错误用 error 返回；panic 留给程序无法继续维持不变量的严重异常，不要把它当普通控制流。

## 六、踩坑点

- if err != nil 后应尽早处理或返回，不要静默丢弃错误。
- 错误信息应添加操作上下文，但避免重复堆叠相同描述或泄露凭证、个人数据。
- 比较包装后的错误值时用 errors.Is，不要直接 ==。
- defer 捕获的普通参数是注册时的值；闭包引用的变量则可能在返回前改变。
- 不要在每层都打印再返回同一个错误，否则日志会重复。

## 七、项目中的实际使用

在系统边界处把底层错误转换为业务可理解的结果；内部层用 %w 保留原因并补充当前操作。服务入口负责记录一次日志、映射协议状态码，避免把内部堆栈原样暴露给客户端。

## 八、一句话总结

**用早返回保持主路径清楚，用 error 表达可预期失败，用包装保留因果链。**

## 十、自测与答案

1. fmt.Errorf("...: %w", err) 相比 %v 多保留了什么？
2. defer f(x) 中 x 何时求值？
3. 哪一层更适合把内部错误转成 HTTP 状态码？

<details>
<summary>展开答案</summary>

1. 错误链关系，可供 errors.Is / errors.As 检查。
2. defer 注册时就求值参数；若 defer 的是闭包，则闭包内引用在执行时读取。
3. HTTP 处理边界层；底层包不应依赖 HTTP 表达业务错误。
