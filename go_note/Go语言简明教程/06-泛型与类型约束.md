# 06 泛型与类型约束

## 一、是什么

泛型允许函数和类型把一部分类型作为参数；类型约束规定这些类型参数可以是什么、能进行哪些操作。

## 二、为什么需要

当同一算法需要适用于多种类型时，泛型能避免复制几乎相同的代码，同时仍让编译器检查类型关系。它不是把所有值都降成 any。

## 三、核心用法

Go 1.18 起可定义泛型函数和类型：

~~~go
func Map[S ~[]E, E any, R any](items S, f func(E) R) []R {
    out := make([]R, 0, len(items))
    for _, item := range items {
        out = append(out, f(item))
    }
    return out
}

names := Map([]int{1, 2}, strconv.Itoa) // 输出 []string
~~~

类型集合约束可以限定支持的操作：

~~~go
type Number interface {
    ~int | ~int64 | ~float64
}

func Sum[T Number](values []T) T {
    var total T
    for _, value := range values {
        total += value
    }
    return total
}
~~~

## 四、核心原理

- 类型参数在编译期由调用处提供或推断；它不是运行时动态类型。
- 约束既限定允许的类型，也限定泛型代码可使用的操作。
- 空接口 any 表示运行时可以装任意值；泛型 T 则在一次具体调用中代表一个确定的类型。
- ~T 表示底层类型为 T 的类型集合；联合项用 | 表示可选类型集合。
- Go 1.27 起，具体类型的方法可以声明额外类型参数；但接口方法仍不能声明自己的类型参数。这是新语法，项目必须明确要求 Go 1.27 或更高版本。

## 五、常见场景

适合通用容器、排序/转换/过滤等数据算法、支持多个数值类型的纯函数。若行为差异是关键，或只涉及一个具体数据类型，具体类型或接口通常更清楚。

## 六、踩坑点

- 不要为了展示语法而把只服务于一种领域类型的函数泛型化。
- 约束不是运行时校验，也不能代替用户输入校验。
- 用 any 会失去类型信息；不要把泛型问题改写成类型断言和反射。
- 泛型方法是 Go 1.27 的新增语法；面向更旧工具链的项目不能使用。泛型函数与泛型类型仍可用于 Go 1.18+。
- 不要假定每个约束都能使用所有类型共有的运算；编译器只允许约束类型集合明确支持的操作。

## 七、项目中的实际使用

先写具体实现，出现至少两种真实类型且算法完全相同时，再评估泛型。保持约束尽量小、调用处类型推断直观；若代码需要大量显式类型参数才能读懂，重新评估抽象是否值得。

## 八、一句话总结

**泛型在编译期复用类型安全的算法；只有多个类型共享同一行为时才值得抽象。**

## 十、自测与答案

1. 泛型函数中的 T 是运行时任意类型，还是一次调用中确定的类型？
2. 约束 interface{ ~int | ~int64 } 大致允许哪些底层类型？
3. 一个只处理 User 的业务函数，需要仅为“通用”而改成泛型吗？

<details>
<summary>展开答案</summary>

1. 一次调用中确定的类型；可由实参推断，也可显式指定。
2. 底层类型是 int 或 int64 的类型，包括以这些类型为底层类型的定义类型。
3. 不需要。只有存在多种真实类型且算法相同时，泛型才带来净收益。
