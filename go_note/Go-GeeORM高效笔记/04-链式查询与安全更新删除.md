# 链式查询与安全更新删除：Where、Limit、Update、Delete、Count

## 一、是什么

链式查询是让 `Where`、`OrderBy`、`Limit` 等方法持续返回查询对象，通过累积条件，最后由 `Find`、`First`、`Update`、`Delete`、`Count` 统一执行。它本质上是一个带状态的 Query Builder。

## 二、为什么需要

SQL 本来就是多个有顺序的子句组合。若每个条件都写成独立 API，调用者要自己拼 SQL；若让终结方法接收所有参数，接口会迅速膨胀。链式 Builder 把“配置查询”和“真正执行”分成两个阶段。

## 三、核心用法

### 1. 查询

```go
var users []User
err := s.Model(User{}).
	Where("age >= ?", 18).
	OrderBy("age DESC, id ASC").
	Limit(20).
	Find(ctx, &users)
```

典型输出：

```sql
SELECT id, name, age
FROM users
WHERE age >= ?
ORDER BY age DESC, id ASC
LIMIT ?
```

参数：`[18, 20]`。

### 2. First

```go
var user User
err := s.Model(User{}).
	Where("id = ?", id).
	Limit(1).
	FindOne(ctx, &user)
```

`First` 不是“数据库天然有第一条”，而是把查询限制为 1 条；如果业务需要稳定结果，应同时指定唯一或确定性的 `ORDER BY`。

### 3. Update：显式字段、显式条件

```go
affected, err := s.Model(User{}).
	Where("id = ?", id).
	Update(ctx, map[string]any{
		"name": "Alice",
		"age":  20,
	})
```

推荐生成：

```sql
UPDATE users SET age = ?, name = ? WHERE id = ?
```

参数：`[20, "Alice", id]`。Set 字段应排序或按 Schema 顺序输出，避免 map 顺序导致不稳定。

### 4. Delete：默认保护无条件删除

```go
affected, err := s.Model(User{}).
	Where("id = ?", id).
	Delete(ctx)
```

项目推荐：没有 `WHERE` 时直接返回错误，除非调用者显式选择 `AllowAll()` 一类高风险 API，并在代码审查中可见。

### 5. Count

```go
count, err := s.Model(User{}).
	Where("age >= ?", 18).
	Count(ctx)
```

Count 复用同一组过滤条件，但通常不需要 `ORDER BY` 或 `LIMIT`；Builder 应明确哪些 Clause 对当前终结操作有效。

## 四、核心原理

### 1. 链式调用的本质

```text
Where     → 写入 WHERE Part，返回同一 Builder
OrderBy   → 写入 ORDERBY Part，返回同一 Builder
Limit     → 写入 LIMIT Part，返回同一 Builder
Find      → 按 SELECT, WHERE, ORDERBY, LIMIT 编译并执行
```

返回 `*Session` 只是教学版的最小写法。更稳妥的项目设计是 Builder 不可变，或每次链式调用复制状态，避免两个协程共享一份可变条件。

### 2. 条件叠加不等于字符串乱拼

如果调用：

```go
Where("age > ?", 18).Where("status = ?", "active")
```

Builder 应把两个条件和参数作为结构化数据保存，最终明确生成：

```text
WHERE age > ? AND status = ?
Args = [18, "active"]
```

直观含义：条件是数据结构，SQL 是最后的编译产物；不要在每次调用时破坏参数边界。

### 3. 更新与删除的安全不变量

对于写操作，至少建立以下不变量：

```text
Update/Delete 必须有明确目标模型
Update/Delete 默认必须有过滤条件
Update 的字段集合不能为空
所有值必须参数化
返回 RowsAffected，供业务判断影响范围
```

## 五、常见场景

- ⭐ 列表页：过滤、排序、分页。
- ⭐ 单条读取：主键条件 + 确定排序 + Limit 1。
- ⭐ 局部更新：只更新调用者明确给出的字段。
- ⭐ 批量清理：必须显式条件、分批、记录影响行数。
- △ 复杂布尔条件、子查询、JOIN：使用表达式 AST 或原生 SQL，别把字符串 DSL 无限扩展。

## 六、踩坑点

1. 无 `WHERE` 的 `Update`/`Delete` 可能影响整张表；这是 ORM 必须重点防护的事故类型。
2. `OrderBy("?", userInput)` 通常不能参数化标识符；排序字段应白名单映射，方向只允许 `ASC/DESC`。
3. 更新 map 为空时不能生成 `SET `；应直接返回参数错误。
4. 更新表达式 `count = count + 1` 与更新值 `count = ?` 不是同一语义；需要受控表达式能力。
5. `First` 没有稳定排序时，测试可能偶尔通过、线上顺序却变化。
6. 教学版 Session 的 Clause 在执行后清空；如果错误路径没有清理，下一次操作可能串入旧条件。
7. 链式对象若可变，不要跨 goroutine、跨请求复用。
8. `Count` 不应机械复用所有查询条件；`ORDER BY` 可能多余甚至在某些数据库中无效。

## 七、项目中的实际使用

建议把高风险操作做成可审计的 Repository 方法：

```go
func (r *UserRepo) Rename(ctx context.Context, id int64, name string) error {
	affected, err := r.q.Model(User{}).
		Where("id = ?", id).
		Update(ctx, map[string]any{"name": name})
	if err != nil {
		return err
	}
	if affected != 1 {
		return ErrNotFound
	}
	return nil
}
```

这样业务层不需要到处拼字段名，更新影响范围也能被检查。列表查询可以使用通用 Builder；高风险删除、权限相关更新应使用窄接口。

## 八、一句话总结

链式调用只是“延迟编译的查询状态”，真正的项目价值在于把条件、参数顺序和写操作安全不变量固定下来。

## 九、核心问答

### 1. Builder 的配置阶段和执行阶段为什么要分开？

配置阶段只积累结构化条件，执行阶段一次性确定 SQL 顺序、参数顺序和执行器，便于复用、测试和避免半成品 SQL。

### 2. 为什么 `OrderBy` 不能像年龄一样直接用占位符？

年龄是值，排序列名和方向是 SQL 语法标识符；驱动绑定参数通常只处理值。列名要走白名单映射，方向只允许有限枚举。

### 3. `Update(map)` 与 `Save(struct)` 的区别是什么？

`Update(map)` 表示调用者明确指定要改哪些列；`Save(struct)` 容易把零值、默认值和未修改字段混在一起，必须有清晰的全量覆盖语义。

### 4. 什么时候应该拒绝执行无条件 Delete？

默认所有业务路径都应拒绝；只有数据清理、测试重置等明确场景才允许显式授权，并配合权限与审计。

### 5. 为什么 Count 不应直接在已有 SQL 后面追加？

已有查询可能包含排序、分页、投影等只适用于返回行的部分；Count 应根据语义重新选择有效 Clause，复杂查询可能需要 `SELECT COUNT(*) FROM (...)`。
