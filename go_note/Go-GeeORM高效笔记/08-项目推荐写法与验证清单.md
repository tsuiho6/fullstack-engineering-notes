# 从教学 ORM 到真实项目：推荐写法与验证清单

## 一、是什么

GeeORM 教程适合用最少代码展示 ORM 的骨架；项目推荐写法是在这个骨架上补齐边界：上下文、错误传播、SQL 安全、可观测性、事务一致性、迁移纪律和测试。

## 二、为什么需要

教学代码往往刻意省略复杂情况，以便在一天内完成一个特性。直接复制到项目会把“为了说明原理而做的简化”误当成“生产默认值”。这份清单用于区分两者。

## 三、核心用法

### 1. 推荐的项目分层

~~~text
bootstrap
  └─ 打开 *sql.DB、Ping、连接池、关闭
migrations
  └─ 显式、版本化 schema 变更
repository
  └─ 单表 CRUD、结果映射、受控查询
service
  └─ 业务规则、事务边界、幂等、权限
model / dto
  └─ 数据形状，不承载整个业务流程
~~~

### 2. 一次写请求的标准流程

~~~text
请求入站
  → 解析并校验输入 DTO
  → Service 决定是否开启事务
  → Repository 使用同一个执行器
  → Hook 只做局部模型生命周期规则
  → 检查 RowsAffected / 返回值
  → 提交事务
  → 提交后再处理可靠外部事件
~~~

### 3. 代码契约：先写 shape，再写实现

| 操作 | 输入形状 | 输出形状 | 关键检查 |
|---|---|---|---|
| Insert | `T`/`*T` 或 `[]T` | affected rows / ID | 字段顺序、Hook、参数数量 |
| Find | `*[]T` | 填充 slice | 列顺序、NULL、rows.Err |
| First | `*T` | 1 个对象 | 条件、排序、未找到 |
| Update | 条件 + 字段 map | affected rows | 非空字段、必须有条件 |
| Delete | 条件 | affected rows | 默认禁止全表删除 |
| Transaction | `func(*Tx) error` | commit/rollback error | 所有操作使用同一 tx |
| Migrate | 版本脚本 | schema 版本 | 幂等、审计、数据校验 |

### 4. 最小集成测试示意

~~~go
func TestTransferRollsBack(t *testing.T) {
	// 1. 创建临时数据库和 accounts 表
	// 2. 插入初始余额
	// 3. 让第二步故意失败
	// 4. 查询余额
	// 5. 断言第一步也没有留下
}
~~~

对 ORM 来说，最有价值的测试不是只测“返回 nil”，而是检查最终数据库状态、影响行数和失败后的状态。

## 四、核心原理

### 1. 教学演示、原理核心、项目推荐三栏对照

| 主题 | 教学演示 | 原理核心 | 项目推荐 |
|---|---|---|---|
| 执行 API | `Exec/Query/QueryRow` | 写/单行/多行形状不同 | `ExecContext/QueryContext`，统一超时 |
| 日志 | 简易全局 logger | SQL 与错误要可观察 | 结构化日志，注意脱敏参数 |
| Schema | 每次反射解析 | 类型元数据可缓存 | 注册时校验，按类型缓存 |
| Clause | map 存子句 | SQL 顺序与参数同步 | 受控 AST/Builder，防注入 |
| Hook | `MethodByName` | 生命周期扩展点 | 接口优先，错误必须传播 |
| Transaction | Session 持有 `tx` | 执行器贯穿边界 | Service 持有边界，Repository 接收 tx |
| Migrate | struct 自动增删列 | schema 差异可计算 | 版本化、显式、可审计 |

### 2. 不要把 ORM 当成数据库抽象的全部

ORM 能抽象重复的 CRUD，但不能替你决定：

- 索引是否命中；
- JOIN 是否产生笛卡尔积；
- 事务隔离和锁等待；
- `NULL`、精度、时区和金额语义；
- 迁移是否会锁表或丢数据。

因此“会用 ORM”必须包含“能读它生成的 SQL，并能在必要时绕过它”。

## 五、常见场景

- ⭐ 后台 CRUD、列表分页、简单聚合。
- ⭐ 事务型写入：订单、库存、账户、审计。
- △ 代码生成、反射缓存、模型生命周期扩展。
- ○ 极复杂查询、报表、批处理、数据库特性：原生 SQL 或专用查询层。

## 六、踩坑点

1. 把 `*sql.DB` 的并发安全误认为所有 Session/Builder 都能并发复用。
2. 只测 SQL 是否执行，不测影响行数和最终数据。
3. 错误信息里直接打印密码、Token 或完整参数。
4. 为了“全自动”让 ORM 隐式创建/删除生产 schema。
5. 在 Repository 内部偷偷开启事务，导致上层无法组合多个 Repository 的原子操作。
6. 把复杂业务流程都塞到 Hook，形成隐式调用链。
7. 让通用 `Where(string)` 接受未经白名单处理的排序、列名和 SQL 片段。

## 七、项目中的实际使用

上线前至少完成以下闭环：

1. 启动：连接、Ping、迁移版本检查、关闭。
2. 读：参数绑定、目标 shape、NULL 处理、rows 关闭和错误检查。
3. 写：字段白名单、条件保护、影响行数、唯一约束错误映射。
4. 事务：成功提交、错误回滚、panic 清理、同一 tx 执行。
5. Hook：方法签名、调用时机、错误传播、批量语义。
6. 迁移：Up、兼容部署、数据回填、破坏性操作审批。

## 八、一句话总结

教学 GeeORM 让你看懂抽象是怎么长出来的，项目写法则要求每个抽象都能在失败、并发、升级和审计场景下保持正确。

## 九、核心问答

### 1. 为什么事务边界应该在 Service 而不是 Repository？

一个业务动作可能调用多个 Repository；Service 才知道哪些操作必须一起成功。Repository 只接收执行器并执行自身数据访问。

### 2. 为什么读写分离不能只替换一个 `*sql.DB`？

还要处理事务、写后读一致性、路由策略、故障切换、连接池和延迟；这属于高阶能力，不是 GeeORM 基础主干。

### 3. 为什么要区分 Model 与 DTO？

Model 反映持久化结构，DTO 反映接口输入输出；混用容易把密码、内部字段、关联数据和更新语义暴露出去。

### 4. 为什么复杂 SQL 不必强行 ORM 化？

ORM DSL 过度扩展会变成另一种难读语言；对复杂查询，显式 SQL、明确列投影和执行计划通常更可维护。

### 5. 如何判断一项功能该进入 ORM 核心？

看是否高频、跨项目重复、能被稳定抽象、不会隐藏重要数据库语义；否则作为原生 SQL、插件或业务层能力更合适。

## 十、自测与答案

### 题目

1. 一个列表接口最少应检查哪些查询契约？
2. 为什么要在 ORM 集成测试里故意制造失败？
3. 哪些行为适合 Hook，哪些适合 Service？
4. 一个 ORM 版本升级最容易遗漏哪三类问题？

<details>
<summary>答案</summary>

1. 输入参数绑定、排序白名单、分页边界、目标 shape、NULL、rows 关闭、错误与空结果语义。
2. 因为 ORM 的价值在失败时仍保持数据库正确；只测成功路径发现不了事务泄漏、错误吞掉和资源未关闭。
3. 默认值、局部校验、时间字段、轻量派生适合 Hook；跨表流程、权限、外部副作用和重试适合 Service。
4. SQL/参数顺序变化、数据库驱动/方言差异、迁移与旧代码兼容性；此外还有错误语义和资源生命周期。
