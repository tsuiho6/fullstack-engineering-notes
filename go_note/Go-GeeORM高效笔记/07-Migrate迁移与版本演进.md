# Migrate：从 struct 差异到安全的数据库版本演进

## 一、是什么

Migration 是对数据库 schema 的可追踪变更：增加/删除列、修改约束、创建索引、重建表等。GeeORM 第七天演示的是最小自动迁移：比较 struct 字段与现有表字段，只处理新增和删除，不处理字段类型变更。

## 二、为什么需要

代码模型会演进，数据库表也必须演进。没有迁移机制，就只能手动登录数据库改表，环境之间容易漂移；但“根据 struct 自动推断所有变更”又可能把重命名误判成删除 + 新增，造成数据损失。

## 三、核心用法

### 1. 教学版的最小差异

设：

~~~text
desired = struct 中的目标字段集合
actual  = 数据库当前字段集合
~~~

则：

\[
toAdd = desired - actual
\]

\[
toDrop = actual - desired
\]

直观含义：目标有、现有没有的列要增加；现有有、目标没有的列被视为待删除。这个集合差异只能回答“名字不同”，回答不了“这是改名还是删掉”。

### 2. 新增列

~~~sql
ALTER TABLE users ADD COLUMN age INTEGER;
~~~

新增列还要考虑默认值、是否允许 NULL、已有数据如何填充、索引和约束如何创建。

### 3. SQLite 删除列的教学方案

SQLite 在旧版本/特定约束下删除列不如新增列直接，常见重建步骤是：

~~~sql
CREATE TABLE users_new (...保留的列...);
INSERT INTO users_new (...) SELECT ... FROM users;
DROP TABLE users;
ALTER TABLE users_new RENAME TO users;
~~~

这只是原理演示；生产中还要迁移索引、触发器、外键、默认值、数据类型和约束，并放进事务或数据库支持的安全流程。

### 4. 项目推荐：版本化迁移

不要把“程序启动时扫描 struct 并自动删列”作为生产迁移策略。推荐提交明确的迁移文件：

~~~text
migrations/
  0001_create_users.up.sql
  0001_create_users.down.sql
  0002_add_users_age.up.sql
  0002_add_users_age.down.sql
~~~

应用启动或部署阶段执行“当前版本 → 目标版本”的有序迁移，并在数据库中记录已应用版本。

## 四、核心原理

### 1. Schema 迁移与数据迁移不是一回事

~~~text
Schema migration：增加列、索引、约束、表
Data migration：把旧数据转换成新语义
~~~

例如把 `full_name` 拆成 `first_name` 和 `last_name`，仅执行 `ADD COLUMN` 不足以完成业务迁移；还要填充数据、校验、切换读写、最终删除旧列。

### 2. “删列”是不可逆风险

struct 少一个字段可能代表：

- 真正删除字段；
- 字段重命名；
- 代码暂时不读取；
- 分支部署造成的版本不一致；
- 迁移脚本尚未执行。

自动化只能看到名字集合，无法可靠理解意图。因此项目迁移应把“删列/改名”写成明确的人类审阅步骤。

### 3. 可重复执行与版本记录

安全迁移通常需要：

~~~text
有唯一版本号
记录是否已应用
重复运行不会重复破坏
失败可诊断、可恢复
上线顺序兼容旧代码和新代码
~~~

直观记忆：Migration 是发布流程的一部分，不是模型反射的副作用。

## 五、常见场景

- ⭐ 新增可空列、创建索引、扩展表结构。
- ⭐ 兼容发布：先加列，再部署读新列的代码，最后切换写入。
- △ SQLite/测试环境快速生成表。
- ○ 复杂生产变更：在线索引、分片、海量数据回填、跨表重构，需要专门的迁移与运维方案。

## 六、踩坑点

1. 自动删列可能造成不可逆数据丢失。
2. 新增 `NOT NULL` 列没有默认值时，已有数据无法满足约束。
3. “删旧列 + 加新列”不等于“改名”，旧数据可能丢失。
4. 重建 SQLite 表时容易漏掉索引、外键、触发器和自增语义。
5. 迁移和应用同时发布时，旧代码可能无法识别新 schema；要设计向后兼容的过渡阶段。
6. 多实例同时启动并发跑迁移，需要锁或单独的部署迁移步骤。
7. 类型变更、精度变更、时区变更可能需要数据转换，不是简单 `ALTER`。
8. 迁移执行成功不等于数据迁移成功；要有行数、约束和业务校验。

## 七、项目中的实际使用

推荐流程：

1. 先写迁移脚本，再修改模型，或至少在同一个变更中同时审阅两者。
2. 在临时数据库执行 Up，检查 schema、索引、约束和数据。
3. 测试旧版本代码在过渡阶段是否还能工作。
4. 对大表把结构变更、历史数据回填、读写切换拆成多个可观察步骤。
5. 将 destructive migration（删列、删表、收紧约束）单独审核，不在普通启动流程里隐式执行。

## 八、一句话总结

自动迁移适合演示“如何发现差异”，生产迁移必须记录意图、版本和数据转换，尤其不能把字段消失自动解释成删列。

## 九、核心问答

### 1. 为什么 GeeORM 教学迁移只支持增删字段？

因为字段名集合差异容易演示；类型变更、改名、约束和关联需要更多数据库特定语义，800 行左右的教学实现无法可靠覆盖。

### 2. 为什么 struct 驱动的自动迁移不适合生产？

struct 只表达当前代码模型，不表达变更意图；改名和删除无法从最终状态区分，自动操作可能丢数据。

### 3. 新增非空列最容易漏掉什么？

已有行没有该列的值。通常需要先可空/带默认值添加，再回填和校验，最后再收紧约束。

### 4. 为什么迁移文件通常有 Up/Down？

Up 表示向前演进，Down 提供开发/测试环境的回退路径；生产回滚是否使用 Down 还要看数据损失和发布策略，不能机械执行。

### 5. Schema migration 和 data migration 有什么区别？

前者改变数据库结构，后者转换已有数据语义；复杂变更通常二者都需要。
