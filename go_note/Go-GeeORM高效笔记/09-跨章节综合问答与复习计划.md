# 跨章节综合问答与复习计划

## 一、总主干回忆图

~~~text
业务调用
  ↓
Service 决定事务边界
  ↓
Session / Query Builder 累积条件
  ↓
Schema 提供表、列、字段索引
  ↓
Dialect 提供数据库差异
  ↓
Clause 编译出 SQL + Args
  ↓
DBTX 选择 *sql.DB 或 *sql.Tx
  ↓
Exec / Query / Scan
  ↓
Hook 前后扩展
  ↓
错误 → 回滚；成功 → 提交
~~~

## 二、跨章节综合问答

### 1. 从 `s.Where(...).Find(&users)` 到数据库返回结果，完整因果链是什么？

`Where` 将条件和参数写入 Builder；`Find` 根据目标 `*[]User` 选择模型和 Schema；Clause 按固定顺序生成 SELECT SQL 与参数；Session 用当前 `DBTX` 查询；每行创建可寻址 `User`，按列顺序 `Scan`；执行 AfterQuery Hook；追加到 slice；检查 `rows.Err()` 并关闭资源。

### 2. 为什么 Schema、Clause、Session 三层必须分开？

Schema 是稳定元数据，Clause 是一次查询的可变描述，Session 是执行和资源上下文。分开后可以缓存 Schema、独立测试 SQL 生成、切换事务执行器，也避免每个 CRUD 方法重复处理反射和方言。

### 3. 如果用户传入一个不存在的排序列，应该在哪一层拒绝？

在查询构造/编译层根据 Schema 或白名单拒绝。排序列是标识符，不能把用户输入当值参数绑定，也不应等 SQL 执行后才发现。

### 4. 一个 Hook 返回错误，但 CRUD 不报错，说明哪条链断了？

Hook 调用层把错误只记录没有返回；CRUD 继续执行；事务层也就看不到错误。正确链是 `Hook error → CRUD return → Service error → rollback`。

### 5. 为什么事务和 Session 的关系不能只理解为“Session 多了一个 tx 字段”？

关键不是字段本身，而是所有数据库操作是否都通过 `tx` 执行，以及事务边界是否由业务动作统一管理。若任何一步绕过 tx，原子性就失效。

### 6. 为什么“结构体字段变化”同时关联 Schema、Migrate 和版本发布？

Schema 反映代码期望，Migrate 改变数据库实际结构，发布顺序决定旧/新代码能否在过渡期共同工作。只改 struct 不会自动让生产数据库安全演进。

### 7. 什么情况下 ORM 的抽象会妨碍正确性？

当它隐藏了锁、NULL、执行计划、复杂 JOIN、数据库特有语法、批量影响范围或迁移风险时。此时应降低抽象层，直接写受控原生 SQL。

### 8. 如何设计一个最小但不危险的 `Delete` API？

要求模型明确、条件非空、值参数化、影响行数可见；无条件删除默认返回错误；批量清理提供显式授权和审计，而不是复用普通删除入口。

### 9. `*sql.DB` 为什么适合全局共享，Builder 为什么不适合？

`*sql.DB` 是并发安全的连接池；教学 Builder 内含可变的模型、Clause、SQL 和参数。共享 Builder 会发生状态覆盖和条件串线。

### 10. GeeORM 这 7 天最值得迁移到其他框架的设计经验是什么？

先找稳定核心抽象，再隔离变化点；把构建与执行分开；让错误沿调用链传播；让资源生命周期显式；为高频扩展点预留接口；对危险自动化保留人工确认。

## 三、综合场景题

### 场景 A：创建订单并扣库存

需求：插入订单、扣减库存、写订单明细，任何一步失败都不能留下半成品。

应答框架：

1. Service 开启事务。
2. 所有 Repository 接收同一个 `*sql.Tx`/`DBTX`。
3. 扣库存用条件更新 `stock >= quantity`。
4. 检查每次 `RowsAffected`。
5. Hook 只做订单默认值/局部校验，不发送外部通知。
6. 成功提交后再发布可靠事件；失败回滚。

### 场景 B：User 增加 `Email` 字段

应答框架：

1. Schema 增加字段元数据和类型。
2. 写一个显式 migration：新增可空列或带安全默认值。
3. 部署兼容代码，回填历史数据并校验。
4. 需要时再加唯一索引/非空约束。
5. 不把 struct 自动删列/改列当成生产迁移。

### 场景 C：列表查询偶发数据错位

排查顺序：

1. SELECT 列顺序与 Scan 地址顺序是否相同。
2. Schema 字段顺序是否被 map 或反射缓存破坏。
3. `[]User`/`[]*User`/嵌套字段目标 shape 是否一致。
4. NULL 是否扫描到不支持 NULL 的 Go 类型。
5. rows 是否复用、是否并发共享了可变 Session。

## 四、推荐复习节奏

### 10 分钟快速回顾

只看 00 的主干图，口述：`DB → Schema → Clause → CRUD → Tx → Migrate`，并解释每个箭头传递的是什么。

### 30 分钟最小闭环

不看答案，手写：

1. `DBTX` 接口。
2. `Schema` 的字段列表。
3. `Clause.Build`。
4. `Find(*[]T)` 的反射形状。
5. `WithTx` 的回滚模板。

### 60 分钟工程复盘

任选一个真实 CRUD：画出输入/输出 shape，检查参数化、空结果、影响行数、事务、Hook、迁移和测试。
