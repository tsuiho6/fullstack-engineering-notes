# 跨章节综合问答与复习计划：用主动回忆把 GeeCache 串起来

> 目标：不看正文，能从一次请求出发解释所有关键分支。

## 一、总复习主线

先背这一条，不背零散 API：

~~~text
Get(group, key)
  → 本地 LRU 命中？
  → 否：singleflight 是否已有同 key 加载？
  → 一次加载内：一致性哈希选择 owner
  → 远程 owner：HTTP/Protobuf 获取
  → 远程失败或本机：Getter 回源
  → ByteView 复制并写入 LRU
  → 返回给调用方
~~~

每个组件只回答一个问题：

| 组件 | 它回答的问题 |
|---|---|
| LRU | 内存满了删谁？ |
| ByteView | 缓存值由谁拥有，能否被外部修改？ |
| Mutex | 多个 goroutine 如何安全访问结构？ |
| Group | 命中、回源、写回的主流程是什么？ |
| HTTPPool | 节点之间如何访问？ |
| 一致性哈希 | 这个 key 应该找哪个节点？ |
| PeerPicker/Getter | 选择和访问如何解耦？ |
| singleflight | 同 key 正在加载时，如何避免重复回源？ |
| Protobuf | 节点报文如何结构化并演进？ |

## 三、跨章节综合问答

### 1. 一次未命中的 key 完整经过哪些层？

先由 Group 查本地并发缓存；miss 后由 singleflight 合并同 key 的加载；一致性哈希决定 owner；若 owner 是远程节点则通过 PeerGetter 访问 HTTP/Protobuf；远程失败或 owner 是本机时调用 Getter；成功后复制成 ByteView、写回 LRU，再返回。

### 2. LRU、singleflight、分布式锁分别解决什么？

- LRU：容量淘汰；
- singleflight：同一进程内同 key 的 in-flight 调用合并；
- 分布式锁：多个进程/节点之间协调谁能执行某个临界操作。

三者不能互相替代。

### 3. 为什么仅仅给 map 加锁还不够？

LRU 还要维护链表顺序，Get 也会修改链表；此外，即使结构线程安全，多个 goroutine 仍可能同时 miss 并一起回源，需要 singleflight。

### 4. 节点增加时，为什么一致性哈希比取模更适合缓存？

取模的节点数变化会让几乎所有 key 改变归属；一致性哈希只改变新节点附近的局部区间，因此更多旧缓存仍然可复用。

### 5. 如果远程 peer 失败，为什么可以本地回源？什么情况下不能？

缓存是加速层，真值仍由本地可访问的数据源提供时，可以回退保可用性；如果不同节点的数据域、权限或租户边界不同，则不能无条件回退。

### 6. 为什么要把 group 纳入协议和 singleflight key？

同一个 key 字符串在不同 group 中可能代表不同数据。忽略 group 会导致远程取错缓存，或把不同数据错误合并。

### 7. 为什么 ByteView 要在输入和输出两端复制？

输入复制避免数据源之后复用/修改底层数组；输出复制避免调用方修改缓存内部数组。两端复制共同建立所有权边界。

### 8. 为什么 HTTP 客户端要复用 Client，而不是每次 http.Get？

复用 Client/Transport 能利用连接池和 keep-alive，并集中配置超时、代理和 TLS；每次新建客户端会丢失这些连接复用收益。

### 9. 为什么收到 HTTP 500 时不能直接把 body 当缓存值？

HTTP 状态码已经说明协议层失败；body 可能是错误文本，即使字节看起来合法，也不满足成功响应契约。

### 10. singleflight 能不能解决缓存雪崩？

不能完全解决。它只能按 key 合并同一时刻的重复加载；大量不同 key 同时过期时，每个 key 仍会各自回源，需要 TTL 抖动、分批刷新、限流和降级。

### 11. Protobuf 与 gRPC 的关系是什么？

Protobuf 是消息定义和序列化格式；gRPC 是 RPC 框架。可以用 HTTP 承载 Protobuf，不必生成 gRPC stub；真正使用 gRPC 时才需要服务代码生成和注册。

### 12. 一个“高命中率”的缓存可能仍然不健康吗？

可能。它可能出现远程错误被本地回退掩盖、热点 key 等待很长、回源耗时升高、错误值被缓存或节点负载倾斜。必须同时看回源、等待、错误、淘汰和负载指标。

## 四、综合场景题

### 场景 A：热点 key 第一次访问

现象：100 个请求同时访问同一个未命中 key。

正确判断：本地锁只保证 LRU 安全；singleflight 应把 100 次加载合并为 1 次；其余请求等待同一结果；成功后所有请求拿到同一份逻辑值，但对外返回的字节仍应是安全副本。

### 场景 B：owner 节点刚刚下线

现象：一致性哈希仍选出旧节点，远程请求超时。

正确处理：请求设置较短 peer timeout；记录 peer error；按策略本地回退或快速失败；拓扑更新后重建 ring；观察回源洪峰，必要时熔断/限流。

### 场景 C：新增节点后命中率下降

现象：不是所有 key 都迁移，但局部 key 大量 miss。

正确判断：这是一致性哈希的正常代价；检查新旧节点的 peer 列表、replicas 和 hash 实现是否一致；不要把“局部重映射”误认为“完全不失效”。

### 场景 D：新版本增加字段

现象：旧节点仍在运行，新节点发送了额外元数据。

正确处理：新增字段使用新编号；旧节点忽略未知字段；新节点为缺失字段提供合理默认值；滚动发布前做真实新旧版本互通测试。

## 五、最终自测

### 题目

1. 说出 GeeCache 从单机到分布式新增的三个关键能力。
2. 解释为什么 Get 命中也可能需要锁。
3. 画出远程 peer 失败后的控制流。
4. 给出一个能证明 ByteView 复制正确的测试。
5. 区分缓存雪崩、击穿、穿透，并各说一个治理手段。
6. 如果节点使用不同 replicas，会发生什么？
7. 为什么协议要限制响应体大小？
8. 什么时候应选择成熟缓存产品而不是继续扩展 GeeCache？

<details>
<summary>展开答案</summary>

1. LRU 容量淘汰、节点间通信与一致性哈希、singleflight 并发回源抑制；Protobuf 是后续协议优化。
2. LRU Get 会更新最近访问顺序，写了链表。
3. PickPeer → 远程请求 → 非 2xx/网络错误 → 记录错误 → 本地 Getter 回源或按策略失败 → 成功则写本地缓存。
4. 写入一份字节切片，修改原始切片后读取仍不变；修改第一次读取到的输出切片后，第二次读取仍不变。
5. 雪崩：大量 key 同时失效，可用 TTL 抖动；击穿：热点 key 失效并发回源，可用 singleflight；穿透：不存在 key 反复 miss，可用负缓存或布隆过滤器。
6. 同一个 key 在不同节点可能选择不同 owner，远程查找不稳定，命中率下降并增加回源。
7. 防止异常或恶意 peer 让客户端无限读取并消耗内存。
8. 当需求已经包含成熟产品提供的容量、TTL、淘汰、高可用、监控和故障恢复，而学习目标之外没有自研收益时。
