# 分布式节点与远程回源：先选 owner，再决定是否跨网络

> 优先级：⭐ 必须掌握

## 一、是什么

分布式节点层把“选择节点”和“访问节点”抽象成两个接口：

- PeerPicker：根据 key 找到应该访问的 peer；
- PeerGetter：从这个 peer 获取具体 group/key 的值。

Group 的 load 流程变成：

~~~text
本地 miss
  → PeerPicker 选节点
  → 如果是远程节点，PeerGetter 获取
  → 远程失败或 owner 是本机，回退本地 Getter
~~~

## 二、为什么需要

如果 Group 只会本地回源，所有节点都可能向数据库查同一个 key；如果把一致性哈希、HTTP 细节直接写进 Group，缓存主流程就会和具体传输协议强耦合。

接口的价值是让 Group 只知道“找谁”和“怎么拿”，不依赖 HTTP、Protobuf 或某个具体节点实现。

## 三、核心用法

### 1. 两个接口的最小形状

教学版可以是：

~~~go
type PeerPicker interface {
    PickPeer(key string) (PeerGetter, bool)
}

type PeerGetter interface {
    Get(group string, key string) ([]byte, error)
}
~~~

项目版推荐把请求上下文带进去：

~~~go
type PeerGetter interface {
    Get(ctx context.Context, group, key string) ([]byte, error)
}
~~~

输入：key 或 (ctx, group, key)；输出：一个 peer getter 和是否找到远程节点，或 []byte/error。

### 2. HTTPPool 的节点表

~~~go
type HTTPPool struct {
    self        string
    basePath    string
    mu          sync.RWMutex
    peers       *consistenthash.Map
    httpGetters map[string]*httpGetter
}
~~~

peers 负责 key → peer；httpGetters 负责 peer → 可复用的远程客户端。

### 3. 用全量列表重建拓扑

~~~go
func (p *HTTPPool) Set(peers ...string) {
    ring := consistenthash.New(defaultReplicas, nil)
    ring.Add(peers...)

    getters := make(map[string]*httpGetter, len(peers))
    for _, peer := range peers {
        getters[peer] = &httpGetter{
            baseURL: peer + p.basePath,
            client:  sharedHTTPClient,
        }
    }

    p.mu.Lock()
    p.peers = ring
    p.httpGetters = getters
    p.mu.Unlock()
}
~~~

先在锁外构建完整的新状态，再一次性替换，避免其他 goroutine 看到“环已更新但 getter 还没建完”的中间状态。

### 4. 选择远程 peer

~~~go
func (p *HTTPPool) PickPeer(key string) (PeerGetter, bool) {
    p.mu.RLock()
    defer p.mu.RUnlock()

    if p.peers == nil {
        return nil, false
    }
    peer := p.peers.Get(key)
    if peer == "" || peer == p.self {
        return nil, false
    }
    return p.httpGetters[peer], true
}
~~~

只在查表时持有读锁；真正的 HTTP 请求必须在解锁后执行。

### 5. Group 的远程优先、本地回退

~~~go
func (g *Group) load(ctx context.Context, key string) (ByteView, error) {
    if g.peers != nil {
        if peer, ok := g.peers.PickPeer(key); ok {
            value, err := g.getFromPeer(ctx, peer, key)
            if err == nil {
                return value, nil
            }
            g.logger.Printf("peer fetch failed: %v", err)
        }
    }
    return g.getLocally(ctx, key)
}
~~~

这里的因果顺序很重要：远程请求失败不能让整个缓存不可用，必须有清晰的本地回退路径。

### 6. 当前 HTTP 客户端写法

~~~go
type httpGetter struct {
    baseURL string
    client  *http.Client
}

func (h *httpGetter) Get(ctx context.Context, group, key string) ([]byte, error) {
    endpoint := h.baseURL + url.PathEscape(group) + "/" + url.PathEscape(key)
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, endpoint, nil)
    if err != nil {
        return nil, err
    }

    resp, err := h.client.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf("peer returned %s", resp.Status)
    }

    body, err := io.ReadAll(io.LimitReader(resp.Body, maxPeerBodyBytes))
    if err != nil {
        return nil, fmt.Errorf("read peer response: %w", err)
    }
    return body, nil
}
~~~

> 上面仍然沿用“简单 key 放在 path”的教学协议，因此应限制 key 字符集和长度。若 key 可包含 / 或任意二进制，改用 query/body/Protobuf，不要只靠字符串拼接。

## 四、核心原理

### 1. owner 与本机不是同一个概念

一致性哈希返回的是 owner。owner 如果是本机，直接本地回源；owner 如果是其他节点，才跨网络访问。这样一个 key 在拓扑稳定时会尽量固定落到同一个节点，减少重复回源。

### 2. 远程失败为什么要回退

缓存节点是加速层，不应轻易把短暂的网络故障放大成业务全失败。回退本地的代价是可能增加数据源压力，所以项目需要同时配合：

- peer 请求超时；
- 回退次数、耗时和错误指标；
- 熔断或临时摘除故障 peer；
- 数据源限流和保护。

### 3. 接口隔离了“缓存决策”和“传输实现”

~~~text
Group.load
  只依赖 PeerPicker/PeerGetter
       ↑
  HTTPPool + consistenthash + httpGetter
       ↑
  未来可以替换为 gRPC、Unix socket 或内存 fake
~~~

直观含义：分布式缓存的主流程保持稳定，协议替换不会重写 Group。

## 五、常见场景

- **适合**：缓存节点横向扩展、节点地址可配置、需要可测试的远程访问层。
- **不适合**：把节点发现、配置中心、故障检测全部塞进 Group；这些是拓扑/基础设施职责。
- **只回退本地的限制**：如果每个 API 进程都有独立缓存且 peer 选择不稳定，回退可能造成大量数据源流量，需要额外治理。

## 六、踩坑点

1. **在锁内发 HTTP 请求**：网络延迟会阻塞拓扑读写，甚至造成级联卡顿。
2. **只更新 ring，不更新 getter**：会得到 nil getter 或访问旧地址。
3. **节点地址格式不统一**：http://node:8001、尾部斜杠、大小写差异可能被当成不同 peer。
4. **把远程失败直接返回给业务**：丢失缓存层的降级价值；至少应评估本地回退。
5. **没有超时**：一个失联 peer 会拖住整个请求链。
6. **没有检查响应状态码**：错误正文可能被误当成缓存值。
7. **每次请求创建新的 http.Client**：浪费连接池，降低 keep-alive 复用。
8. **远程响应无限读取**：必须限制 body 大小，否则异常 peer 可造成内存压力。
9. **不同节点配置不一致**：同一 key 选择不同 owner，远程 miss 和回源会增多。

## 七、项目中的实际使用

推荐把拓扑配置当作“全量快照”管理：

~~~text
服务发现/配置中心 → peer 地址快照 → Set(peers...) → 原子替换 ring/getters
~~~

监控至少记录：本地命中、远程命中、远程错误、回退本地、Getter 回源、各阶段耗时。不要把 key 原文直接放进指标 label，否则高基数会反过来拖垮监控系统。

## 八、一句话总结

**一致性哈希决定“谁负责”，PeerGetter 决定“怎么拿”，远程失败时 Group 必须能回到本地回源。**

## 九、核心问答

1. **为什么要拆成 PeerPicker 和 PeerGetter 两个接口？**  
   一个负责选择节点，一个负责访问节点，便于替换算法和传输协议，也便于测试。

2. **为什么 PickPeer 返回后可以解锁再发请求？**  
   因为返回的是已准备好的 getter；网络操作不依赖拓扑锁，必须避免长时间持锁。

3. **远程失败回退本地会不会造成更大压力？**  
   会有这个风险，所以必须配合超时、熔断、回源限流和指标；回退是可用性策略，不是免费优化。

4. **为什么要构建新 ring 后一次性替换？**  
   避免并发读取拓扑的 goroutine 看到不完整的中间状态。

5. **节点间一致性哈希配置不一致会怎样？**  
   同一 key 在不同节点选择不同 owner，导致远程查找混乱、重复回源和命中率下降。

## 十、自测与答案

### 题目

1. 一个节点收到 key 后，什么条件下会调用远程 PeerGetter？
2. 为什么不能在 PickPeer 持有锁的同时完成 HTTP 请求？
3. 远程 503 时，本地回退成功；从用户体验看应算失败还是命中？
4. 如果 peer 地址列表发生变化，应该原地修改旧 ring，还是构建新 ring 后替换？为什么？

<summary>展开答案</summary>

1. 一致性哈希选出非空且不是本机的 peer，并且已存在对应 getter 时。
2. HTTP 延迟不可控，持锁会阻塞其他拓扑读取/更新，放大故障。
3. 对缓存层来说是本地回源成功；对远程 peer 来说是一次失败。两种指标都应记录。
4. 构建新 ring 和 getter 集合后一次性替换，状态更容易保持一致。
