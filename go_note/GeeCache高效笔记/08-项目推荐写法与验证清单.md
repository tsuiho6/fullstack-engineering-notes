# 项目推荐写法与验证清单：把教学版 GeeCache 变成可交付的最小方案

> 优先级：⭐ 必须掌握

## 一、是什么

教学版 GeeCache 用很少的代码展示核心机制；项目版要在这个主干外补齐输入边界、超时、协议安全、配置一致性、可观测性和测试。

推荐的最小分层：

~~~text
业务层：定义 key、数据编码、回源逻辑
缓存层：Group / ByteView / LRU / singleflight
路由层：一致性哈希 / owner 选择
传输层：HTTP 或 gRPC + Protobuf
治理层：超时、鉴权、限流、熔断、指标、优雅关闭
~~~

## 二、为什么需要

教程代码能证明“机制可行”，但不能直接证明“服务可上线”。最常见的隐患来自边界而不是主算法：

- 网络请求无超时；
- peer 返回错误却被当成缓存值；
- key/response 没有限长；
- 节点拓扑不一致；
- 缓存内部字节被外部修改；
- 回源失败被无限放大；
- 只有命中率，没有回源和错误指标。

## 三、核心用法

### 1. 推荐请求闭环

~~~text
业务请求
  → 校验 group/key 与调用上下文
  → 本地 LRU 查找
  → singleflight 按完整命名空间合并 miss
  → 一致性哈希选择 owner
  → 远程 Protobuf/HTTP 获取
  → 非本机失败时本地回源
  → 成功值复制后写入 LRU
  → 解码并返回业务对象
~~~

### 2. 每一层的输入输出

| 层 | 输入 | 输出 | 必查项 |
|---|---|---|---|
| 业务 key | 业务标识、租户、版本 | 稳定字符串或 bytes | 是否会碰撞，是否含敏感信息 |
| LRU | string + Value | Value/未命中 | 容量、所有权、淘汰回调 |
| Group | context + key | ByteView/error | 空 key、Getter 错误、写回 |
| 哈希环 | key + 全量 peer | owner | 空环、配置一致、节点变化 |
| PeerGetter | context + group + key | bytes/error | 超时、状态码、body 限制 |
| Protobuf | message / wire bytes | message / bytes | 字段编号、版本、解码大小 |

### 3. 当前项目推荐的客户端边界

~~~go
func (h *httpGetter) Get(ctx context.Context, group, key string) ([]byte, error) {
    ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
    defer cancel()

    req, err := newPeerRequest(ctx, group, key)
    if err != nil {
        return nil, err
    }
    resp, err := h.client.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK {
        return nil, fmt.Errorf("peer status: %s", resp.Status)
    }
    return io.ReadAll(io.LimitReader(resp.Body, maxPeerBodyBytes))
}
~~~

这里的 200ms 只是示例，不是通用答案；应根据业务延迟预算、下游能力和失败率压测决定。

### 4. 测试矩阵

| 组件 | 最小测试 |
|---|---|
| LRU | 命中提升、容量淘汰、更新大小、回调、空容量 |
| ByteView | 输入切片修改不影响缓存、输出切片修改不影响缓存 |
| cache | 并发读写、lazy init、race detector |
| Group | 空 key、命中不回源、miss 回源一次、回源错误不写入 |
| 哈希环 | 空环、固定映射、增删节点、虚拟节点分布 |
| HTTP handler | 路径错误、未知 group、Getter 错误、响应类型 |
| HTTP getter | timeout、非 2xx、body 上限、协议解码错误 |
| singleflight | 相同 key 只执行一次、不同 key 可并行、错误共享 |
| Protobuf | 往返、未知字段、新旧字段兼容、超大消息拒绝 |
| 集成 | 多节点取值、远程命中、本地回退、节点变更后仍可回源 |

## 四、核心原理

### 1. 缓存是加速层，不是数据源

任何缓存设计都应先回答：

~~~text
缓存失效时，谁提供真值？
远程节点失败时，是否还能回源？
回源也失败时，业务返回什么？
~~~

如果这些答案不清楚，继续调 LRU 或 protobuf 参数没有意义。

### 2. 正确性优先于命中率

命中率高但值错误，会比 miss 更危险。项目应优先保证：

- key 命名空间不会混淆；
- 值的所有权不会被外部修改；
- 远程错误不会伪装成成功值；
- 协议升级不会错解字段；
- 节点路由变更不会把请求送到错误数据域。

### 3. “本地回退”是策略，不是必然正确

如果每个节点访问的是同一个真值数据源，本地回退通常能保持可用；如果不同节点数据源不同或有租户隔离，错误回退可能返回不该返回的数据。回退前要确认数据域和权限边界。

## 五、常见场景

- **适合 GeeCache 思路**：读多写少、单 key 值相对小、允许短暂旧值或 miss、缓存节点可水平扩展。
- **需要扩展**：强一致读、复杂失效通知、大对象、写缓存、跨地域复制。
- **不建议直接自研**：已有成熟 Redis/Memcached/本地缓存库且需求只是普通缓存时，自研网络协议的维护成本可能更高。

## 六、踩坑点

1. **只验证“返回了值”**：还要验证值来源、状态码、协议版本和是否回源。
2. **把 group/key 原文放在高基数指标标签**：会造成监控系统压力。
3. **只设 HTTP client timeout，不设请求 context**：调用链取消无法及时传递。
4. **使用单一固定 TTL**：同一批 key 可能同时失效形成雪崩。
5. **只在 API 进程加 singleflight**：多个进程仍可能同时回源；要依靠稳定 owner 或分布式协调。
6. **把缓存错误和业务错误混成一个 500**：应区分 peer error、source error、invalid request 和 decode error。
7. **无优雅关闭**：节点下线时新请求仍会被路由过去，连接和 in-flight 请求处理不清楚。
8. **只测试单节点**：分布式问题通常出现在节点变更、网络失败、协议不兼容和并发尖峰。

## 七、项目中的实际使用

上线前至少具备：

- 明确的 cache key 规范：包含租户/版本/数据域，避免碰撞；
- 可配置的容量、replicas、超时和最大响应体；
- peer 拓扑的全量更新和版本号；
- 本地命中、远程命中、回退、回源、错误、淘汰等指标；
- go test -race、基准测试和多节点集成测试；
- peer 鉴权与网络隔离；
- 优雅关闭和节点摘除流程；
- 明确的 TTL/主动失效/负缓存策略；
- 文档化的 protobuf 字段演进规则。

## 八、一句话总结

**教学版证明算法能跑，项目版还要证明错误可控、值不乱、节点能换、协议能演进、问题能观测。**

## 九、核心问答

1. **为什么说缓存正确性优先于命中率？**  
   错误命中会返回错误数据并隐藏真值问题，通常比一次 miss 更难发现和恢复。

2. **为什么要把 key 的租户/版本信息纳入 singleflight key？**  
   否则不同数据域可能被错误合并，返回错误结果。

3. **远程 peer 失败时为什么不总是直接报错？**  
   缓存是加速层，若本地回源仍能提供真值，回退可以保住可用性；但要控制回源洪峰。

4. **什么时候不值得自研 GeeCache？**  
   需求只是普通缓存，成熟产品已经提供容量、过期、监控和高可用时，自研网络层的维护成本可能大于学习收益。

5. **项目上线前最容易遗漏的验证是什么？**  
   节点变更、peer 超时/非 2xx、协议版本不兼容、响应超大、并发 miss 和 race 检查。

## 十、自测与答案

### 题目

1. 一个远程 peer 返回 404，缓存层应把它当成什么？
2. 为什么“本地回退成功”仍然需要记录远程错误指标？
3. 测试中如何证明 ByteView 没有被外部切片修改？
4. 为什么同一 TTL 不应让所有 key 在同一时刻过期？
5. 哪些问题应由缓存层解决，哪些应交给治理层？

<details>
<summary>展开答案</summary>

1. 协议层或数据域错误，不能当成缓存值；是否回退要由策略决定。
2. 因为远程故障如果不记录会被回退掩盖，无法发现拓扑或网络正在恶化。
3. 写入后修改原始输入切片，再读取缓存；再修改读取到的输出切片，再次读取，内容都应保持不变。
4. 会产生大量 key 同时 miss，把回源流量集中到同一时间窗口，形成雪崩。
5. 缓存层负责命中、回源、写回、去重和协议适配；超时预算、鉴权、熔断、限流、指标和发布治理应由基础设施/治理层协同完成。
