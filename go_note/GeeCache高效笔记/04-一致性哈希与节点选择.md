# 一致性哈希：节点变化时，尽量少搬动 key

> 优先级：⭐ 必须掌握

## 一、是什么

一致性哈希把节点和 key 都映射到一个环上。对某个 key，从它的哈希位置沿顺时针找到的第一个节点，就是该 key 的 owner。

它的核心价值不是“哈希更一致”，而是：**节点加入或离开时，只让环上局部范围的 key 改变归属。**

## 二、为什么需要

最简单的分片方式是：

```text
owner = hash(key) % 节点数
```

当节点数从 N 变成 N-1，几乎所有 key 的取模结果都可能变化。缓存里原有数据仍在旧节点，新的请求大量 miss，可能同时打到数据库。

一致性哈希把“节点数”从取模公式里拿掉，换成环上的有序邻居关系，从而减少重映射。

## 三、核心用法

### 1. 最小数据结构

```go
type Hash func([]byte) uint32

type Map struct {
	hash     Hash
	replicas int
	keys     []uint32          // 已排序的虚拟节点 hash
	hashMap  map[uint32]string // 虚拟节点 hash → 真实节点
}
```

输入：真实节点名称、key。输出：一个真实节点名称，或空字符串表示没有节点。

### 2. 加入节点

```go
func (m *Map) Add(peers ...string) {
	for _, peer := range peers {
		for i := 0; i < m.replicas; i++ {
			virtual := strconv.Itoa(i) + peer
			h := m.hash([]byte(virtual))
			m.keys = append(m.keys, h)
			m.hashMap[h] = peer
		}
	}
	slices.Sort(m.keys)
}
```

每个真实节点对应多个虚拟节点。`replicas` 越大，环的采样越密，通常越能减轻数据倾斜，但初始化和内存成本也会增加。

### 3. 选择节点

```go
func (m *Map) Get(key string) string {
	if len(m.keys) == 0 {
		return ""
	}
	h := m.hash([]byte(key))
	i := sort.Search(len(m.keys), func(i int) bool {
		return m.keys[i] >= h
	})
	return m.hashMap[m.keys[i%len(m.keys)]]
}
```

`i == len(m.keys)` 时要回到 `keys[0]`，所以使用 `% len(m.keys)`。

> 如果项目需要兼容较老 Go 版本，可把 `slices.Sort` 换成 `sort.Slice`；原理不变。

## 四、核心原理

### 1. 环的映射

```text
hash space: 0 … 2^32-1，并首尾相连

        peer-A-2
      /          \
 key-x            peer-B-1
      \          /
        peer-A-1
```

key 只负责找“顺时针第一个虚拟节点”，虚拟节点再映射回真实 peer。

### 2. 为什么节点变化只影响局部

新增节点 P 时，它只会接管自己与前一个虚拟节点之间的那段区间；其他区间的顺时针第一个节点不变。删除节点时，它负责的区间交给下一个节点。

这不是严格的“只搬一小部分”保证：具体比例取决于 hash 分布、节点数量和 replicas，但相比取模，重映射范围显著更局部。

### 3. 虚拟节点解决什么问题

真实节点很少时，直接把节点放在环上容易出现大空段，导致某个节点接管大量 key。虚拟节点增加采样点，让每个真实节点在环上分布多次。

直观含义：虚拟节点改善的是**负载分布**，不是数据复制，也不是故障转移。

## 五、常见场景

- **适合**：分布式缓存、分片路由、节点变化频繁且希望减少缓存失效的场景。
- **不等于**：副本、持久化、强一致、故障自动恢复。
- **不一定适合**：需要严格按权重分配、节点异构明显的场景；应使用加权虚拟节点或成熟一致性哈希方案。

## 六、踩坑点

1. **把一致性哈希理解成“数据一致”**：它只描述 key 到节点的映射稳定性。
2. **没有虚拟节点就直接上线**：节点少时容易数据倾斜。
3. **碰撞覆盖**：两个虚拟节点可能 hash 相同，简单 `map[hash]peer` 会覆盖；教学实现通常忽略，生产需处理碰撞或使用更稳健实现。
4. **重复 Add 同一个 peer**：会重复加入虚拟节点；项目通常用 `Set` 重建整张环。
5. **所有节点的拓扑不一致**：不同 peer 列表或 replicas 会让同一个 key 在不同节点上选择不同 owner。
6. **没有处理空环**：`sort.Search` 前应先判断 `len(keys) == 0`。
7. **把哈希环当作负载均衡器的全部**：热点 key 仍可能压垮一个节点；需要热点保护、限流或复制。
8. **用 `int` 作为跨平台协议字段**：hash 本质是 `uint32`，实现内部用 `uint32` 更清楚，避免把平台整数宽度带入设计。

## 七、项目中的实际使用

推荐节点拓扑更新采用“构建新环 → 一次性替换”：

```text
收到全量 peer 列表
  → 新建 ring
  → Add 全部 peer
  → 原子/加锁替换当前 ring
```

这样比在旧环上边删边加更容易保证中间状态一致。测试至少覆盖：

- 固定 hash 函数下的精确映射；
- 节点增删后的局部变化；
- 空环；
- 重复节点；
- 大量随机 key 的负载分布。

## 八、一句话总结

**一致性哈希用“环上的顺时针邻居”替代“节点数取模”，虚拟节点负责把负载分散开。**

## 九、核心问答

1. **为什么 `hash(key) % N` 不适合节点频繁变化的缓存？**  
   N 一变，几乎所有 key 的结果都可能变化，旧缓存大面积失效。

2. **一致性哈希为什么需要虚拟节点？**  
   真实节点少时环上分布不均，虚拟节点增加采样点，降低数据倾斜。

3. **新增一个节点后，哪些 key 会改变归属？**  
   主要是新节点与其环上前驱之间的区间；其他区间的顺时针第一个节点不变。

4. **一致性哈希能否替代副本机制？**  
   不能。它主要决定 owner；副本需要额外的复制和一致性策略。

5. **为什么所有节点必须使用同一份 peer 列表和 replicas？**  
   否则相同 key 在不同节点上可能选出不同 owner，远程查找会失去确定性。

## 十、自测与答案

### 题目

1. 环上没有节点时 `Get` 应返回什么？为什么不能继续搜索？
2. `sort.Search` 返回 `len(keys)` 时为什么要取模？
3. 节点数从 3 变 4，为什么不是所有 key 都要迁移？
4. 虚拟节点数量是否越大越好？

3. 新节点只覆盖它插入位置对应的局部区间，其他 key 的顺时针第一个节点没有变化。
