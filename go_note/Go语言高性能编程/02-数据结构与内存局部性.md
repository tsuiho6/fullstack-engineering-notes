# 数据结构与内存局部性：少分配、少复制、少保留

> 对应原系列：字符串拼接、切片性能及陷阱、`for`/`range`、反射、空结构体、struct 内存对齐、数组与切片陷阱。

## 一、是什么

这组主题研究的不是“哪种语法更短”，而是数据在内存中的形状、复制与共享关系：

```text
类型与布局 -> 复制多少字节 -> 分配多少次 -> GC 与缓存成本
```

Go 中最需要建立的性能直觉是：**一个值是被复制、被共享，还是被间接访问；一段内存何时分配，何时仍被引用。**

## 二、为什么需要

高频服务中，以下小成本会被调用次数放大：

- 循环 `+` 拼接字符串，反复创建中间字符串。
- slice 不预留容量，扩容时复制已有元素。
- `range` 复制很大的 struct，却只使用其中一个字段。
- 小 slice 引用着巨大的底层数组，导致大块内存无法回收。
- 反射把编译期可确定的工作推迟到运行时。
- 结构体字段布局造成大量 padding，批量存储时浪费内存。

这些问题不能脱离场景判断；短字符串、低频路径和小批量数据可能根本不值得优化。

## 三、核心用法

### 1. 字符串拼接：循环构建用 Builder

```go
func joinParts(parts []string) string {
	var b strings.Builder
	for _, part := range parts {
		b.WriteString(part)
	}
	return b.String()
}
```

如果能估算最终字节数，使用 `Grow`：

```go
func joinPartsKnownSize(parts []string, size int) string {
	var b strings.Builder
	b.Grow(size) // size 是字节数，不是 rune 数
	for _, part := range parts {
		b.WriteString(part)
	}
	return b.String()
}
```

选择顺序：

| 场景 | 推荐 |
|---|---|
| 少量、固定、可读性优先 | `a + b` |
| 循环构建最终字符串 | `strings.Builder` |
| 构建二进制或需要 `[]byte` | `bytes.Buffer` / 预分配 `[]byte` |
| 已有 `io.Writer` | 直接 `io.WriteString` 或分段写出，避免先合成大字符串 |

注意：`len(string)` 是字节数；`Grow` 的输入也是字节数。中文等 UTF-8 文本不能把“字符数”直接当容量。

### 2. slice：先画出 `ptr/len/cap`

```text
slice = 指向底层数组的指针 + len + cap
```

批量追加时预留容量：

```go
func double(values []int) []int {
	out := make([]int, 0, len(values))
	for _, v := range values {
		out = append(out, v*2)
	}
	return out
}
```

`append` 的两种结果：

- 新长度不超过 `cap`：可能复用原底层数组。
- 超过 `cap`：分配新的底层数组并复制元素。

所以必须接住返回值：

```go
s = append(s, value)
```

需要断开底层数组共享时使用复制：

```go
small := slices.Clone(large[100:110])
```

删除元素后，如果元素包含指针或字符串等引用，及时清理被移出位置，避免旧引用继续保持对象存活。Go 新版本可使用 `slices.Delete`，但仍要理解它会修改原 slice 的底层数组。

### 3. `for` 与 `range`：看你是否需要值副本

小元素：

```go
for _, n := range nums {
	total += n
}
```

大结构体只访问字段：

```go
for i := range items {
	if items[i].Done {
		count++
	}
}
```

需要修改元素时也按下标：

```go
for i := range items {
	items[i].Done = true
}
```

因为 `for _, item := range items` 中的 `item` 是元素副本：修改 `item` 不会修改 slice 中的元素；如果元素很大，还会多一次复制。对 `[]*Item`，range 只复制指针，复制成本小，但指针跳转可能损害缓存局部性，不能简单断言“指针一定更快”。

### 4. 反射：边界使用，元数据缓存

反射适合通用序列化、ORM、插件和框架边界；业务热循环中优先用具体类型、泛型或代码生成。

```go
type Config struct {
	Name string `json:"name"`
}

var configType = reflect.TypeOf(Config{})

func newConfig() *Config {
	return reflect.New(configType).Interface().(*Config)
}
```

更推荐的项目策略：

1. 反射只做一次元数据解析。
2. 把字段索引、类型转换规则缓存起来。
3. 热路径使用缓存后的索引或生成的专用代码。
4. 数据模型稳定时，优先具体结构体和编译期检查。

### 5. `struct{}`：无数据载荷，不等于整个容器零成本

集合去重：

```go
seen := make(map[string]struct{})
seen["go"] = struct{}{}
_, exists := seen["go"]
```

有界信号量：

```go
sem := make(chan struct{}, 16)
sem <- struct{}{} // 占用一个名额
defer func() { <-sem }()
```

空结构体自身没有数据字段，但 map 的桶、slice 的指针和 channel 的管理成本仍然存在；它表达的是“只关心存在/信号”，不是“没有任何内存成本”。

### 6. 结构体内存对齐：先测，再决定是否重排

```go
type Compact struct {
	Size int64
	Kind int32
	Flag byte
}

func layout() {
	_ = unsafe.Sizeof(Compact{})
	_ = unsafe.Alignof(Compact{})
	_ = unsafe.Offsetof(Compact{}.Flag)
}
```

字段顺序可能改变 padding，尤其在“数量巨大、结构体密集存储、内存是瓶颈”的场景。对外协议、序列化格式和公开结构体不要为了省几个字节随意改字段顺序；先评估兼容性和实际收益。

## 四、核心原理

### 1. 复制成本与间接访问的权衡

```text
总成本 ≈ 复制字节数 × 次数 + 分配/回收成本 + 缓存未命中成本
```

直观含义：值传递可能复制更多字节，但数据连续、没有额外堆对象；指针传递复制的只是地址，却可能增加堆对象、GC 扫描和随机内存访问。不能只看“复制少了”这一项。

### 2. slice 的共享关系

```go
base := []int{1, 2, 3}
part := base[:2]
part[0] = 9 // base[0] 也变为 9
```

slice header 是按值复制的，但两个 header 可能指向同一底层数组。因此“函数参数按值传递”不代表元素修改不可见；而 `append` 可能更换底层数组，所以必须使用返回的新 header。

当把子 slice 交给长期缓存或异步任务时，应问两个问题：是否允许共享修改？是否会让大数组长期存活？必要时 `slices.Clone`。

### 3. 内存对齐与 padding

结构体大小不是字段大小简单相加：

```text
struct size = 字段占用 + 字段间 padding + 尾部 padding
```

直观含义：字段需要满足各自的对齐要求，整个结构体还要满足最大字段的对齐要求。对齐通常有利于硬件访问，但会增加空间；合理排序可减少 padding。

### 4. 反射的成本来自运行时不确定性

反射需要在运行时检查类型、字段、索引和值，并常伴随接口装箱或额外分配。它的价值是减少重复代码、支持未知类型；代价是失去部分编译期约束和优化机会。

## 五、常见场景

### 应该优先掌握

- API 响应、日志、SQL 或模板的批量字符串构建。
- 解析列表、批处理结果、队列和缓存中的 slice 所有权。
- 大对象数组或批量记录的遍历。
- 高并发序列化、临时 buffer 和 GC 压力。
- 内存占用敏感的索引、列式数据或大批量 struct。

### 不要为了性能强行使用

- 少量字符串拼接；直接 `+` 更清楚。
- 只有几十个元素、执行很少的路径；预分配和布局优化收益可能低于复杂度。
- 把所有 struct 改成 `*T`；这会改变所有权、nil 语义和 GC 行为。
- 把所有动态行为改成反射的缓存；如果业务模型稳定，具体类型通常更稳。

## 六、踩坑点

1. **把 `cap` 当成当前长度**：有效元素只有 `[0:len]`，`cap` 只是从起点可扩展的边界。
2. **丢掉 `append` 返回值**：可能导致调用方看不到新数组。
3. **子 slice 持有大数组**：小结果长期存活时，考虑复制出紧凑副本。
4. **range 修改无效**：修改的是值副本，应该按下标访问。
5. **只看 `[]*T` 的复制成本**：指针间接访问和堆分配可能更贵。
6. **误解 `struct{}`**：只省 value 的数据载荷，不会让 map/channel 没有管理成本。
7. **把 `unsafe.Sizeof` 当跨平台常数**：`int`、指针和对齐受架构影响。
8. **反射元数据每次重算**：在热路径中重复 `TypeOf`、字段查找和类型断言。
9. **把原文的 slice 扩容阈值当规则**：runtime 实现会随 Go 版本变化，依赖 `cap` 行为，不依赖具体倍率。
10. **把“内存更少”当“性能一定更好”**：更密集可能改善缓存，也可能增加计算或破坏可读性；必须测量。

## 七、项目中的实际使用

以批量生成 HTTP 响应为例：

```text
输入：[]Item
  -> 预估输出大小，必要时 builder.Grow
    -> 按下标遍历大 struct，避免复制
      -> 直接写入响应 writer，能流式输出就不合成巨型 string
        -> 统计 benchmark 的 ns/op、B/op、allocs/op
          -> 用 heap profile 检查是否保留了原始大 slice
```

代码评审的最小检查表：

| 检查项 | 问题 |
|---|---|
| 类型 | 元素是值还是指针？复制和缓存局部性哪个更重要？ |
| shape | `len`、`cap`、批次大小、是否可能为空？ |
| 所有权 | 返回值是否复用调用方底层数组？异步使用前是否需要 Clone？ |
| 生命周期 | 子 slice 是否会比大数组存活更久？ |
| 输出 | 是返回 `string`、`[]byte`，还是直接写入 `io.Writer`？ |
| 动态性 | 反射是否真的需要？元数据是否缓存？ |
| 架构 | 对齐优化是否值得引入 `unsafe`，是否影响协议兼容？ |

## 八、一句话总结

**数据性能的核心不是“选了哪个容器”，而是明确复制、共享、分配、对齐和生命周期。**

## 九、核心问答

1. **slice 和数组的根本区别是什么？**  
   数组长度属于类型且按值复制；slice 是 `ptr/len/cap` 描述符，元素通常位于共享底层数组。

2. **为什么函数接收 `[]T` 后能改元素，却不能保证外部长度增加？**  
   函数拿到的是 slice header 副本；它仍指向同一元素数组，但 `append` 可能返回新的 header 和底层数组，必须返回给调用方。

3. **什么时候 `range` 的值拷贝值得关注？**  
   元素是大 struct、循环次数高或需要修改原元素时；小标量通常无需为这点差异牺牲可读性。

4. **为什么指针传递不一定比值传递快？**  
   它少复制，但可能引入堆分配、GC 扫描、指针追踪和缓存未命中；只读小对象常常值传递更合适。

5. **反射的正确边界是什么？**  
   在框架、序列化、ORM 等通用边界使用；把元数据缓存起来，业务热路径优先具体类型、泛型或代码生成。

## 十、自测与答案

### 先独立作答

1. `s := make([]int, 0, 2)` 追加第 3 个元素时，发生了什么？
2. 为什么 `small := large[100:110]` 可能让 `large` 的整个底层数组继续存活？
3. 下面代码为什么不会把所有人的编号加 10？

```go
for _, person := range persons {
	person.ID += 10
}
```

4. `struct{}` 适合表示什么，不适合用来证明什么？
5. 什么时候可以考虑重排 struct 字段？

<details>
<summary>答案</summary>

1. 当前 `cap` 不够，runtime 会分配更大的底层数组并复制旧元素；返回的新 slice 必须接住。
2. 子 slice 的 header 仍指向大数组；只要子 slice 存活，大数组就可能不能回收。可用 `slices.Clone` 复制出小数组。
3. `person` 是 range 产生的元素副本；按 `for i := range persons { persons[i].ID += 10 }` 修改原元素。
4. 适合表达“只关心存在/信号、不需要数据”，如 set value 和 semaphore token；不代表 map、channel、桶和调度没有成本。
5. 结构体数量很大、内存成为瓶颈、布局不会破坏协议/序列化兼容，并且用 `unsafe.Sizeof` 与实际 profile 证明值得时。

</details>
