# 编译器优化与交付：读懂决策，避免手工对抗

> 对应原系列：减小二进制体积、逃逸分析、死码消除与调试模式；补充现代 Go 的 PGO。

## 一、是什么

编译器优化是 Go 在构建阶段自动完成的一组决策：内联、常量传播、死码消除、逃逸分析、链接裁剪，以及基于运行 profile 的 PGO。

开发者的主要工作不是手工指定“必须栈分配”或“必须内联”，而是：

1. 理解编译器为什么做出这个决策；
2. 用 `-gcflags=-m`、benchmark 和 profile 验证成本；
3. 通过清晰的数据流和构建配置帮助编译器，而不是猜测内部阈值。

## 二、为什么需要

同一段 Go 代码的差异可能来自两个层面：

- **运行时性能**：分配、GC、内联、调用、缓存和接口动态派发。
- **交付性能**：二进制体积、启动、调试能力、可复现性和发布安全。

把“去掉调试符号”“减少二进制体积”和“让服务变快”混为一谈，会得到错误结论：发布包可以更小，但业务热点仍然没有改变；指针可以减少复制，但堆分配和 GC 可能增加。

## 三、核心用法

### 1. 用逃逸分析验证，而不是凭感觉猜

```go
type Point struct {
	X, Y int64
}

func valueDistance(p Point) int64 {
	return p.X*p.X + p.Y*p.Y
}

func newPoint(x, y int64) *Point {
	return &Point{X: x, Y: y}
}
```

查看编译器报告：

```powershell
go test -gcflags=all=-m=2 ./...
```

常见“可能导致逃逸”的原因：

- 返回局部对象的指针，调用方在函数返回后仍要使用它。
- 闭包捕获局部变量，使变量生命周期超过当前函数。
- 值被装入接口，编译器无法证明其生命周期和具体表示。
- 分配大小过大或运行时才知道，不能安全放在当前 goroutine 栈上。

不要把报告中的每条 `escapes to heap` 当成错误；先问：分配是否在热路径？对象是否会大量短命？GC 和延迟是否真的受影响？

### 2. 值传递和指针传递：按语义与成本选择

```go
// 小、只读、值语义清晰：优先值传递
func Score(p Point) int64 {
	return p.X*p.X + p.Y*p.Y
}

// 需要修改原对象或对象很大：考虑指针
func Move(p *Point, dx, dy int64) {
	p.X += dx
	p.Y += dy
}
```

判断维度：

| 问题 | 更偏向值 | 更偏向指针 |
|---|---|---|
| 是否要修改调用方对象 | 否 | 是 |
| 对象大小 | 小 | 大 |
| 是否需要表达 nil/不存在 | 否 | 是 |
| 创建频率 | 高且短命时可避免额外堆对象 | 如果对象已长期存在，传指针复制更少 |
| 数据局部性 | 连续值更好 | 可能增加间接访问 |

这是默认判断，不是硬规则；最终以 benchmark 和 profile 为准。

### 3. 发布构建：体积、调试和可复现性分开决策

```powershell
# 生产构建常见起点：去本机构建路径，并去掉符号/DWARF
go build -trimpath -ldflags="-s -w" -o dist/app ./cmd/app
```

- `-trimpath`：从构建产物中去掉本地路径，改善可复现性和信息暴露边界。
- `-s` / `-w`：减小体积，但会损失符号和 DWARF 调试信息。
- 调试、故障定位或需要完整栈信息的构建，不要默认使用 `-s -w`。

二进制压缩工具（如 UPX）只在明确需要分发体积时评估，并验证：启动时间、内存、杀毒/签名、平台兼容、崩溃转储和回滚流程。它不是通用的运行时性能优化。

### 4. 构建标签：把调试能力变成编译期选择

```go
//go:build debug

package diag

func Enabled() bool { return true }
```

```go
//go:build !debug

package diag

func Enabled() bool { return false }
```

构建：

```powershell
go build -tags=debug ./cmd/app
go build ./cmd/app
```

两个文件必须提供相同 API；build tag 是构建变体，不应在运行时用大量 `if debug` 让生产代码承担调试分支。

### 5. PGO：把真实运行热点反馈给编译器

PGO 使用 CPU pprof 作为输入。推荐闭环：

```text
无 PGO 构建并发布
  -> 收集代表性生产 CPU profile
    -> 将 profile 命名为 main package 下的 default.pgo
      -> go build -pgo=auto ./cmd/app
        -> 重新发布、观察、继续收集
```

```powershell
go build -pgo=off -o dist/app-baseline ./cmd/app
go build -pgo=auto -o dist/app-pgo ./cmd/app
```

微 benchmark 只覆盖很小路径，通常不是整个服务 PGO 的好 profile 来源；真实流量或代表性集成 workload 更可靠。

## 四、核心原理

### 1. 逃逸分析的直观模型

```text
对象只在当前函数/当前栈生命周期内使用 -> 可能栈分配
对象需要跨函数返回、闭包或未知接口边界继续存活 -> 可能堆分配
```

直观含义：栈上的生命周期由函数帧自然结束，堆上的对象需要垃圾回收追踪。堆并不等于错误，指针也不等于快；它们只是改变了生命周期和访问成本。

### 2. 内联与死码消除

编译器会在适合时把小函数展开到调用点，并消除不可达或未使用的代码。内联不仅减少调用开销，还可能让常量传播、边界检查消除和逃逸分析看见更多上下文。

因此，“手工把代码写成一大段”不是可靠优化；复杂度可能让编译器和人都更难理解。

### 3. PGO 的核心公式

```text
源码 + 代表性运行 profile -> 针对热点的编译决策 -> 新二进制
```

直观含义：普通编译器只能根据静态代码猜哪些路径热；PGO 用真实运行频率帮助它把更多优化预算用在真正常走的路径上。profile 不代表生产行为时，收益可能很小，甚至优化了错误的路径。

## 五、常见场景

### 必须掌握

- 看到分配热点时，检查逃逸报告和 `allocs/op`。
- 需要发布小镜像或边缘程序时，评估 `-trimpath`、符号和压缩的取舍。
- 线上服务有稳定流量和 CPU profile 时，考虑 PGO。

### 理解即可

- 闭包捕获、接口装箱、局部大对象和调用边界如何改变生命周期。
- 链接器如何裁剪未使用代码；为什么反射和动态加载可能限制裁剪。
- build tags 如何给调试与生产提供不同实现。

### 不适合直接套用

- 把每个返回值都改成指针。
- 把 `fmt`、反射或接口看成绝对禁用项。
- 所有发布都用 `-s -w`，导致线上无法排查问题。
- 用不代表生产的微 benchmark 生成 PGO。

## 六、踩坑点

1. **把逃逸当 bug**：逃逸是编译器的实现选择，只有在成本被 profile 证明时才需要优化。
2. **把指针当快**：指针减少复制，却可能增加堆分配、GC、间接访问和缓存未命中。
3. **依赖逃逸阈值**：具体大小阈值是编译器实现细节，会随 Go 版本和架构变化。
4. **把 `fmt.Println` 的逃逸报告泛化**：接口和格式化路径可能制造额外成本，但真实业务要看调用频率和 profile。
5. **去符号后无法调试**：`-s -w` 应配合保留未裁剪构建、构建 ID 或外部符号归档。
6. **UPX 破坏交付链**：某些安全扫描、签名、崩溃转储和平台工具可能不接受压缩壳。
7. **PGO profile 过时或不代表生产**：profile 应定期更新，并覆盖主要工作负载。
8. **build tag API 不一致**：调试构建能编译不代表生产构建也能编译；两套实现要一起测试。
9. **把编译体积和运行内存混为一谈**：文件更小不等于 RSS 更低或吞吐更高。

## 七、项目中的实际使用

推荐使用三类构建产物：

| 构建 | 目的 | 是否去符号 |
|---|---|---|
| debug | 本地断点、完整栈、快速定位 | 否 |
| benchmark/profile | 性能实验、保留足够符号 | 通常否 |
| release | 分发、容器、生产运行 | 按诊断需求决定；可使用 `-trimpath` |

发布前清单：

1. 运行 `go test ./...` 和必要的 `go test -race ./...`。
2. 用代表性 workload 验证延迟、吞吐、内存和错误率。
3. 如使用 PGO，确认 profile 与主要流量相符，并记录来源日期。
4. 如使用 `-s -w` 或 UPX，保留可诊断构建和符号归档。
5. 对跨平台构建分别验证；不要把一个架构的体积和性能结论直接套到另一个架构。

## 八、一句话总结

**让编译器优化的前提是给它清晰代码和真实 profile；手工优化只在测量证明成本存在时介入。**

## 九、核心问答

1. **逃逸到堆一定比栈分配差吗？**  
   不一定。堆对象能表达跨函数生命周期；只有在高频、短命、造成明显 GC 或延迟成本时才值得优化。

2. **为什么大结构体有时传指针，有时传值？**  
   大对象复制成本高且需要修改时偏向指针；小而只读对象用值传递可能有更好的局部性和更少的堆分配。

3. **`-s -w` 主要解决什么问题？**  
   减少二进制体积，不是直接优化业务热点；代价是调试和符号信息减少。

4. **PGO 与 benchmark 的关系是什么？**  
   benchmark 是受控比较工具，PGO 的 profile 应尽量来自代表性真实 workload；用微 benchmark 驱动全服务优化通常不可靠。

5. **为什么 build tag 适合调试模式？**  
   调试实现可以在编译期被替换，生产二进制不承担调试分支；但两套实现必须保持相同 API 并分别验证。

## 十、自测与答案

### 先独立作答

1. 一个函数返回局部 struct 的指针，为什么对象可能逃逸？
2. 把 `func Sum(Point)` 改成 `func Sum(*Point)`，可能增加哪些成本？
3. 什么时候 `-s -w` 不应作为默认发布选项？
4. 为什么 PGO 应使用代表性生产 profile，而不是任意 benchmark profile？
5. 二进制体积减少了，为什么不能直接说明服务变快了？

<details>
<summary>答案</summary>

1. 函数返回后调用方仍需要该对象，生命周期超过当前栈帧，编译器可能把它放到堆上。
2. 可能引入堆分配、GC 扫描、指针追踪、nil 分支和缓存未命中；是否值得要看对象大小、频率和 profile。
3. 需要线上符号化崩溃、调试器或详细栈信息时；应保留一份带符号构建，发布裁剪要与诊断策略配套。
4. PGO 会把优化预算投向 profile 中的热点；微 benchmark 覆盖太窄，可能把全程序优化引向不重要路径。
5. 体积主要影响分发和启动等维度；运行时热点、I/O、锁、GC、下游和调度仍可能是主要成本。
