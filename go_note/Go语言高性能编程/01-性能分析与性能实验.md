# 性能分析与性能实验：先测量，再优化

> 对应原系列：benchmark 基准测试、pprof 性能分析。

## 一、是什么

- **Benchmark**：在受控环境中反复执行一段代码，比较每次操作的时间、内存分配和分配次数。
- **Profiling**：对运行中的程序采样，回答“时间、内存或等待主要花在哪里”。Go 的常用入口是 `runtime/pprof`、`net/http/pprof` 和 `go tool pprof`。

二者关系：benchmark 适合验证局部改动，profile 适合定位真实瓶颈；不能互相替代。

## 二、为什么需要

没有测量时，优化容易变成三种错觉：

1. 把最显眼的代码当成最耗时的代码。
2. 把一次运行的偶然波动当成稳定收益。
3. 只减少了某个指标，却把成本转移到锁等待、GC 或下游排队。

性能结论必须绑定**工作负载、硬件、工具链、指标和正确性**。不存在脱离场景的“绝对最快”。

## 三、核心用法

### 1. 最小 benchmark

```go
package join_test

import (
	"strings"
	"testing"
)

var result string // 防止编译器把结果判定为无用

func BenchmarkJoin(b *testing.B) {
	parts := []string{"go", "performance", "notes"}
	b.ReportAllocs()

	for b.Loop() { // Go 1.24+；低版本可用 for i := 0; i < b.N; i++
		var builder strings.Builder
		for _, part := range parts {
			builder.WriteString(part)
		}
		result = builder.String()
	}
}
```

关键输入输出：

- 输入：固定的 `parts`，避免把随机数据生成时间算进被测函数。
- 输出：写入包级 `result`，避免整个计算被消除。
- 指标：`ns/op` 看耗时，`B/op` 看每次分配字节，`allocs/op` 看每次分配次数。

常用命令：

```powershell
go test -run '^$' -bench '^BenchmarkJoin$' -benchmem -count=10 .
go test -run '^$' -bench '^BenchmarkJoin$' -cpuprofile cpu.pprof -memprofile mem.pprof .
go tool pprof -top cpu.pprof
go tool pprof -top mem.pprof
```

### 2. benchmark 的实验规则

- 测试前后使用相同代码版本、输入规模、机器状态和 `GOMAXPROCS`。
- 准备数据放在计时器外；必要时使用 `b.StopTimer()` / `b.StartTimer()`。
- 关注分布而不是一次数字；用 `-count` 重复，必要时用 `benchstat` 比较多次结果。
- benchmark 先验证正确性，再避免编译器消除结果；不要为了“好看”删掉真实的输出路径。
- 微 benchmark 只回答局部问题，不能直接预测端到端服务的 p99、吞吐和成本。

### 3. 在线服务启用 pprof

```go
import (
	"log"
	"net/http"
	_ "net/http/pprof"
)

func startDebugServer() {
	go func() {
		// 只绑定本机；生产环境应放在受控网络或独立诊断端口。
		if err := http.ListenAndServe("127.0.0.1:6060", nil); err != nil {
			log.Printf("pprof server stopped: %v", err)
		}
	}()
}
```

```powershell
# 30 秒 CPU profile
go tool pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'

# 当前存活对象的 heap profile
go tool pprof 'http://127.0.0.1:6060/debug/pprof/heap'

# 查看所有 profile
go tool pprof 'http://127.0.0.1:6060/debug/pprof/'
```

pprof 的选择：

| 现象 | 先看什么 | 回答的问题 |
|---|---|---|
| CPU 高、吞吐低 | CPU profile | 哪些调用路径消耗 CPU？ |
| 内存持续增长 | heap、allocs profile | 当前存活对象多，还是总分配频繁？ |
| goroutine 数量增长 | goroutine profile | 哪些 goroutine 卡在什么位置？ |
| CPU 不高但延迟高 | block、mutex、trace | 是否在锁、channel、定时器或调度上等待？ |
| 并发结构复杂 | execution trace | goroutine、GC、syscall 和调度如何交错？ |

block profile 和 mutex profile 默认不是完整启用的；启用它们会有额外成本，应在诊断场景打开并控制影响。

## 四、核心原理

### 1. 速度、吞吐和延迟不是同一个量

```text
吞吐量 ≈ 完成的操作数 / 时间
加速比 = 优化前耗时 / 优化后耗时
```

直观含义：加速比回答“单个工作单元快了多少”；吞吐回答“单位时间做了多少”；延迟回答“一个请求等多久”。并发、排队和下游资源会让三者发生偏离。

### 2. CPU profile 是采样，不是逐行计时

运行时周期性采样正在运行的 goroutine 栈，热点函数得到更多样本。它适合找“时间主要花在哪里”，但短暂、低频或被等待掩盖的路径可能样本不足。

### 3. heap 与 allocs 的问题不同

- `heap` 更接近当前仍存活的对象，适合看保留、缓存和疑似泄漏。
- `allocs` 关注程序历史上的分配活动，适合找分配热点。

因此“分配很多”不一定意味着“当前占用很大”，“当前占用很大”也不一定来自最近的分配。

## 五、常见场景

### 适合 benchmark

- 比较 `strings.Builder` 与重复 `+`。
- 比较预分配 slice 与不断扩容。
- 验证值传递、指针传递、反射和具体类型的差异。
- 验证一个算法或数据结构改动是否改变 `ns/op`、`allocs/op`。

### 适合 pprof/trace

- 线上 CPU 飙高、内存增长、goroutine 堆积。
- 单元 benchmark 看不出问题，但真实请求 p99 变差。
- 怀疑锁竞争、channel 阻塞、GC 或系统调用导致尾延迟。

### 不适合直接优化

- 只凭代码阅读认定某一行是瓶颈。
- 在没有代表性输入的微 benchmark 上做全局设计决策。
- 为了单一 `ns/op` 指标牺牲可读性、正确性或资源安全。

## 六、踩坑点

1. **把 setup 算进 benchmark**：数据生成、连接建立、文件读取应明确是否属于被测范围。
2. **结果被优化掉**：计算没有被观察时，编译器可能删除或简化它；用结果变量或 `b.ReportMetric` 等方式保证测量对象真实存在。
3. **只看平均值**：线上性能更应关注 p95/p99、错误率和资源上限。
4. **忽略分配**：两个实现 `ns/op` 相近时，`B/op` 和 `allocs/op` 可能决定高并发下的 GC 成本。
5. **把 pprof 端口暴露公网**：诊断端点包含运行时信息，应只绑定本机或放在受控访问面。
6. **把 profile 当成永久真理**：代码、流量、硬件和 Go 版本变化后，profile 需要更新。
7. **把 `go test -race` 当性能测试**：race detector 会改变运行时成本；它用于发现数据竞争，不用于比较吞吐。

## 七、项目中的实际使用

推荐把性能改动写成一条可审查记录：

```text
问题：订单接口 p99 从 40ms 升到 80ms
基线：同一流量回放，CPU 35%，mutex profile 显示 cache.Lock 等待
假设：读路径持有 Mutex 的时间过长
改动：缩短临界区；只在读多写少且 benchmark 证实后尝试 RWMutex
验证：功能测试 + race + 同一回放 + p99/吞吐/内存对比
结论：若收益只在微 benchmark 出现，不能直接宣称线上优化
```

标准闭环：

1. 先用服务指标判断是吞吐、延迟、内存还是错误率问题。
2. 用 pprof/trace 找到一到两个最可能的热点。
3. 为候选函数写可重复 benchmark，先固定输入和正确性。
4. 每次只改一个主要变量，记录 `ns/op`、`B/op`、`allocs/op`。
5. 回到真实 workload 做端到端回归；没有回归证据就保留为实验，不作为结论。

## 八、一句话总结

**Benchmark 证明局部改动，pprof 找到真实热点，最终结论必须由代表性 workload 和正确性回归共同确认。**

## 九、核心问答

1. **benchmark 与 pprof 的根本区别是什么？**  
   benchmark 在受控条件下重复一个局部操作，适合比较；pprof 从真实运行中采样，适合定位。

2. **为什么 benchmark 的 `ns/op` 下降，线上 p99 仍可能不变？**  
   该函数可能不是线上瓶颈，或线上主要时间花在排队、锁、I/O、网络、GC 和下游服务。

3. **heap profile 和 allocs profile 怎么选？**  
   查当前保留和疑似泄漏先看 heap；查“谁在频繁分配”先看 allocs。

4. **为什么测试 benchmark 时要报告 `allocs/op`？**  
   高频分配会增加 GC 和分配器压力；即使单次时间接近，分配差异也可能在并发下放大。

5. **什么时候应该停止优化？**  
   目标指标已达成、继续优化的收益低于复杂度和维护成本，或瓶颈已转移到更值得处理的环节时。

## 十、自测与答案

### 先独立作答

1. 为什么 benchmark 中的随机输入生成通常放在计时区间外？
2. 一个程序 CPU 使用率低但请求超时，优先看 CPU profile 还是 block/mutex/trace？为什么？
3. `B/op` 降低一定意味着 RSS 一定降低吗？
4. 为什么 pprof 端点不应默认监听 `0.0.0.0`？
5. 如果一次 benchmark 结果比基线快 20%，你还需要哪些证据？

<details>
<summary>答案</summary>

1. 随机数生成是准备成本，不属于被测函数；除非真实目标就是“生成随机输入并处理”的总成本。
2. 先看 block、mutex 或 trace，因为 CPU 低说明时间可能花在等待而非计算；具体仍需 profile 证据。
3. 不一定。分配器缓存、长期存活对象、其他路径和运行时内存都会影响 RSS；要做端到端和 heap 验证。
4. pprof 能暴露函数栈、goroutine 和内存信息；公网暴露会扩大诊断接口的攻击面。
5. 需要重复运行、相同输入和环境、正确性不变、分配指标、端到端 workload 和必要的回归 profile。

</details>
