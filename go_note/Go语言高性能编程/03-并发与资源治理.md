# 并发与资源治理：可控、可取消、可收尾

> 对应原系列：互斥锁与读写锁、goroutine 超时退出、channel 关闭、并发数量控制、`sync.Pool`、`sync.Once`、`sync.Cond`。

## 一、是什么

Go 并发的核心不只是 `go f()`，而是把任务的**启动、通信、等待、取消、共享状态保护和资源上限**设计完整。

```text
goroutine：执行
channel：传递数据/同步
WaitGroup：等待一组任务结束
context：传播取消/截止时间
Mutex/RWMutex：保护共享状态
semaphore/worker pool：限制并发资源
```

## 二、为什么需要

不受控的并发会把“处理更多任务”变成“同时占用更多资源”：

- goroutine 堆积，占用栈、调度和内存。
- 连接、文件句柄、数据库会话超过下游上限。
- 没有取消路径，超时返回后后台任务仍继续运行。
- channel 没有关闭或接收方提前退出，发送方永久阻塞。
- 共享 map/计数器无同步，结果错误或触发 race。
- 为了读多写少盲目使用 `RWMutex`，反而增加锁管理和缓存开销。

高性能并发的目标不是“goroutine 越多越好”，而是让资源使用与工作负载保持可预测关系。

## 三、核心用法

### 1. 请求级取消：context 向下传递

```go
func Handle(ctx context.Context, repo Repository) error {
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()

	return repo.Save(ctx)
}
```

规则：

- 函数需要取消或截止时间时，把 `context.Context` 作为第一个参数。
- 从上游 context 派生，不要在请求处理函数内部随意用 `context.Background()` 覆盖请求生命周期。
- `WithTimeout`/`WithDeadline` 返回的 `cancel` 总要 `defer cancel()`。
- 下游调用必须真正使用该 context；只传参数、不监听取消没有效果。

原文用 `time.After` + 无缓冲 `done` 演示超时后发送方卡死的陷阱，这个演示值得理解，但不应直接作为业务模板。项目代码优先让任务接收 context；在需要反复等待超时的低层循环中，使用可停止并复用的 `time.NewTimer`，避免无谓地创建定时器。

### 2. 固定 worker：把并发上限写进结构

```go
type Job func(context.Context) error

func Run(ctx context.Context, jobs <-chan Job, workers int) error {
	if workers < 1 {
		return errors.New("workers must be positive")
	}

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	errCh := make(chan error, 1)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				case job, ok := <-jobs:
					if !ok {
						return
					}
					if err := job(ctx); err != nil {
						select {
						case errCh <- err:
						default:
						}
						cancel()
						return
					}
				}
			}
		}()
	}

	done := make(chan struct{})
	go func() {
		wg.Wait()
		close(done)
	}()

	<-done // 先确认所有 worker 都已退出，再返回
	select {
	case err := <-errCh:
		return err
	default:
		return ctx.Err() // 正常完成时为 nil；父 context 取消时返回取消原因
	}
}
```

这是教学版骨架，项目中可以用 `golang.org/x/sync/errgroup` 简化“错误取消 + 等待”语义，但仍需自行决定并发上限、队列容量和下游背压。

### 3. 更简单的有界 semaphore

任务彼此独立、无需复用 worker 时，可以用 `chan struct{}` 限制 in-flight 数量：

```go
sem := make(chan struct{}, 16)
var wg sync.WaitGroup

for _, item := range items {
	item := item
	sem <- struct{}{} // 满了就阻塞，形成背压
	wg.Add(1)
	go func() {
		defer wg.Done()
		defer func() { <-sem }()
		process(item)
	}()
}
wg.Wait()
```

需要取消时，获取名额也应放入 `select`：

```go
select {
case sem <- struct{}{}:
	// 获得名额
case <-ctx.Done():
	return ctx.Err()
}
```

### 4. 锁：默认 Mutex，读多写少再评估 RWMutex

```go
type Cache struct {
	mu sync.Mutex
	m  map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	v, ok := c.m[key]
	return v, ok
}
```

只有当读操作确实占多数、读临界区足够长、多个读者能并行且 benchmark 证实收益时，才考虑：

```go
type ReadMostlyCache struct {
	mu sync.RWMutex
	m  map[string]string
}

func (c *ReadMostlyCache) Get(key string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.m[key]
	return v, ok
}
```

锁要保护的是不变量，不是某个字段本身；尽量缩短临界区，不要在锁内进行网络、磁盘或未知耗时调用。

### 5. channel 关闭：由知道“不再发送”的一方关闭

```go
func produce(out chan<- int) {
	defer close(out)
	for i := 0; i < 10; i++ {
		out <- i
	}
}

for value := range out {
	consume(value)
}
```

通道状态速记：

| 操作 | nil channel | 已关闭 channel | 未关闭 channel |
|---|---|---|---|
| 发送 | 永久阻塞 | panic | 可能阻塞/成功 |
| 接收 | 永久阻塞 | 立即返回零值，`ok=false` | 可能阻塞/成功 |
| 关闭 | panic | panic | 成功 |

多个发送者不要互相抢着关闭；需要由协调者等待所有发送者结束后统一关闭，或改用额外的 stop channel/context 表达停止。

### 6. `sync.Pool`：只复用临时对象

```go
var bufferPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func build(parts []string) string {
	b := bufferPool.Get().(*bytes.Buffer)
	b.Reset()
	defer bufferPool.Put(b)

	for _, part := range parts {
		b.WriteString(part)
	}
	return b.String()
}
```

使用前提：对象短命、创建频繁、可安全重置、池化收益由 benchmark 证明。不要把业务状态、连接、缓存条目放进 `sync.Pool`；GC 可以在任意时机清理池内容。

如果偶尔会生成超大 buffer，不要无条件放回池中，否则一次尖峰可能让池长期保留大块内存；项目代码应对 `Cap()` 设上限，超过上限就丢弃。

### 7. 单次初始化：优先用 OnceValue / OnceValues

无错误初始化：

```go
var loadConfig = sync.OnceValue(func() *Config {
	return readConfig()
})
```

需要返回错误：

```go
var loadConfig = sync.OnceValues(func() (*Config, error) {
	return readConfig()
})
```

它们表达的是“惰性、并发安全、只执行一次”。如果初始化失败后必须重试，就不能把失败结果永远封存在 `Once` 中，应设计显式状态机或可重置机制。

### 8. `sync.Cond`：多个等待者共享一个条件

```go
type Gate struct {
	mu   sync.Mutex
	cond *sync.Cond
	open bool
}

func NewGate() *Gate {
	g := &Gate{}
	g.cond = sync.NewCond(&g.mu)
	return g
}

func (g *Gate) Wait() {
	g.mu.Lock()
	defer g.mu.Unlock()
	for !g.open {
		g.cond.Wait()
	}
}

func (g *Gate) Open() {
	g.mu.Lock()
	g.open = true
	g.mu.Unlock()
	g.cond.Broadcast()
}
```

必须在锁保护下检查条件，并用 `for` 而不是 `if`；唤醒只表示“条件可能变化”，重新检查才安全。一个事件流或单次通知通常用 channel/context 更直观，`Cond` 适合共享条件和多个等待者。

## 四、核心原理

### 1. 并发控制 = 生命周期 + 资源上限

```text
最大并发数 ≠ CPU 核数
最大并发数应由：CPU、内存、下游连接、文件句柄、队列容量和目标延迟共同决定
```

直观含义：I/O 密集任务可以高于 CPU 核数，但不意味着可以无限增加；下游服务或文件句柄往往先成为瓶颈。

### 2. goroutine 只能协作退出

Go 没有安全的“从外部强杀任意 goroutine”机制。goroutine 必须自己从阻塞点返回：

- 监听 `ctx.Done()`。
- 输入 channel 关闭时返回。
- 发送结果使用可取消或不会永久阻塞的路径。
- 阻塞 I/O 使用支持 context 或 deadline 的 API。

### 3. 锁和 channel 的职责不同

```text
Mutex/RWMutex：共享状态的互斥访问
channel：值的所有权转移、通信和同步
context：取消、截止时间、请求范围
WaitGroup：等待完成，不传递业务结果
```

把这四种工具混成一种“并发工具”，是 goroutine 泄漏和死锁的常见来源。

## 五、常见场景

| 场景 | 推荐模型 |
|---|---|
| 请求下游数据库、HTTP、RPC | 从上游传 context，设置合理 deadline |
| 批量任务且需控制下游压力 | 固定 worker pool + 有界 jobs channel |
| 任务独立、只需要限流 | semaphore + WaitGroup |
| 共享 map/计数器 | Mutex 起步；读多写少再 benchmark RWMutex |
| 临时 buffer 高频创建 | 先减少分配；确认收益后 sync.Pool |
| 全局惰性初始化 | OnceValue/OnceValues |
| 一个状态变化唤醒多个等待者 | Cond + mutex + 条件循环，或广播 channel |

不适合：为了“并发”给纯计算任务随意开 goroutine；为了“高性能”把所有锁换成 channel；为了“复用”把长期对象放进 Pool。

## 六、踩坑点

1. **超时只让调用方返回**：子 goroutine 没有收到取消信号，仍可能阻塞在发送或 I/O。
2. **用 `time.Sleep` 等待完成**：睡眠不是同步；改用 WaitGroup、channel 或 context。
3. **忘记 `wg.Done()`**：使用 `defer wg.Done()` 覆盖所有返回路径。
4. **关闭责任不清**：发送到已关闭 channel 会 panic；接收方通常不关闭数据 channel。
5. **无界 goroutine**：goroutine 轻量不等于免费；并发上限要与外部资源容量匹配。
6. **锁内做 I/O**：放大临界区，造成所有读者/写者排队。
7. **RWMutex 迷信**：读少、临界区短或竞争结构复杂时，RWMutex 可能不如 Mutex。
8. **Pool 不 Reset**：复用对象残留旧内容，导致数据串写或保留大 buffer。
9. **Once 隐含失败语义**：初始化函数 panic 或返回错误后是否允许重试，必须显式设计。
10. **Cond 用 `if`**：被唤醒后条件可能仍不满足，必须循环检查。

## 七、项目中的实际使用

建议每个并发组件都附一张生命周期表：

| 阶段 | 明确答案 |
|---|---|
| 启动 | 谁创建 goroutine，创建多少个？ |
| 输入 | 谁发送，谁关闭，输入何时结束？ |
| 输出 | 谁接收，结果是否有序，错误如何传播？ |
| 取消 | 哪个事件触发 cancel，阻塞点如何响应？ |
| 共享状态 | 哪些数据共享，哪把锁或哪个 owner 保护？ |
| 资源 | 连接、文件、buffer、队列的上限是多少？ |
| 收尾 | 谁等待所有 goroutine，如何证明无泄漏？ |

最小验证命令：

```powershell
go test ./...
go test -race ./...
go test -run TestWorkerCancellation -count=20 ./...
```

测试不要只检查“结果正确”，还要检查：输入关闭能退出、父 context 取消能退出、单任务失败能取消其他任务、重复关闭不会发生、等待函数不会永久阻塞。

## 八、一句话总结

**并发性能的第一目标是生命周期完整、资源有界和退出可证明，第二目标才是减少锁或调度开销。**

## 九、核心问答

1. **WaitGroup、channel、context 分别解决什么问题？**  
   WaitGroup 等待完成，channel 传递值/同步，context 传播取消和截止时间；它们通常组合使用。

2. **为什么超时后子 goroutine 可能泄漏？**  
   调用方已返回，子 goroutine 仍可能在无缓冲 channel 发送、接收或阻塞 I/O 上等待；必须用 context、deadline 或可完成的发送路径让它自行退出。

3. **什么时候选择 RWMutex？**  
   读明显多于写、读临界区允许并行、共享状态访问频繁，并且 benchmark 证明收益时；默认先用简单正确的 Mutex。

4. **sync.Pool 是缓存吗？**  
   不是。它是可丢弃的临时对象复用池，不能依赖对象一定留在池中，也不能把业务状态当缓存存放。

5. **为什么 Cond 的 Wait 必须放在 for 中？**  
   唤醒只表示条件可能发生变化，重新获得锁后条件可能已被其他 goroutine 消耗或仍不满足，必须重新检查。

## 十、自测与答案

### 先独立作答

1. 一个任务处理器启动了 1000 个 goroutine，但下游数据库只能承受 20 个连接，问题在哪里？
2. 为什么发送方通常负责关闭 channel？
3. 如果 `ctx` 已取消，worker 仍可能继续处理一个任务吗？如何减少这种情况？
4. 什么时候 `sync.Pool` 反而可能让代码更难维护？
5. `sync.Once` 的初始化返回错误后，是否天然支持下一次重试？

<details>
<summary>答案</summary>

1. goroutine 数量没有反映下游容量，会造成连接排队、内存增长和尾延迟；应使用固定 worker 或 semaphore 限制 in-flight。
2. 发送方知道何时不会再发送；关闭是对接收方的结束信号，接收方不能再通过关闭表示“我收完了”，否则可能与其他发送者竞争关闭。
3. 可以。取消只在协作点生效；任务已经开始或内部不监听 context 时仍会继续。让每个任务接收 context，并在分段操作之间检查取消。
4. 当对象不是临时的、无法完全 Reset、需要稳定缓存命中、池化收益不明显或引入隐式所有权时；先 benchmark 再决定。
5. 不一定。`sync.Once` 的语义是执行一次；如果要失败重试，应显式设计状态与同步，不要假设 Once 自动重试。

</details>
