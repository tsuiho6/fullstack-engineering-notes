# 跨章节综合问答：把知识串成项目判断

> 使用方式：先只看问题，限时口答；答案不是背诵稿，而是检查是否抓住因果链。

## 一、综合问题

### 1. 一个 HTTP 请求启动 3 个 goroutine，客户端超时后仍有两个 goroutine 不退出，如何定位？

先检查三个 goroutine 的阻塞点：数据库/RPC 是否收到 `ctx`，channel 发送是否有 `ctx.Done()` 分支，结果聚合是否等待所有 worker。再看 goroutine profile 找相同阻塞栈，用 trace 判断它们是 I/O、channel 还是锁等待。修复时建立单一 cancel/errgroup 生命周期，并验证 goroutine 数回落。

### 2. 为什么 slice 传进函数能改元素，却改不了长度？

函数复制的是 slice header；header 内的 data 指针仍可能指向同一个底层数组，所以索引写入可见。但 append 修改的是函数内 header 的 len/ptr/cap，调用方只有接收返回值才获得新 header。

### 3. map 读取缺失 key 返回零值，为什么业务仍要判断 ok？

因为零值可能就是合法业务值。例如库存 0 与 key 不存在意义不同；`v, ok := m[k]` 才能区分。若 map 并发写，还需先解决同步问题，`ok` 不提供并发安全。

### 4. 为什么 interface typed nil 会让错误处理失效？

接口值由动态类型和值组成。nil 指针被装进 error 后，动态类型非 nil，所以 error != nil。返回错误前应直接返回 nil，或只在对象非 nil 时包装。

### 5. 什么时候用接口，什么时候用泛型，什么时候用反射？

- 接口：需要按行为解耦、运行时多态、依赖替换；
- 泛型：算法对类型形状相同，想保留静态检查和性能；
- 反射：框架边界处理编译时未知的类型。

先选能表达约束且可静态检查的工具，反射留在边界。

### 6. 为什么 channel 传递指针仍然可能有数据竞态？

channel 只拷贝指针值；发送方和接收方仍指向同一对象。对对象的后续读写若没有 happens-before，就仍是并发读写竞态。

### 7. “关闭 channel 会通知所有 receiver”为什么成立？

close 改变 channel 的关闭状态，接收操作在关闭且无缓冲值时返回零值和 `ok=false`；多个 receiver 都能观察这一状态。它适合广播停止信号，但只能有明确的单一关闭者。

### 8. 为什么 context cancel 后服务仍可能泄漏 goroutine？

取消只是关闭 Done；若 goroutine 卡在不可取消的 API、无 context 的 channel 发送、死循环或等待锁，它不会自动退出。修复需要让每个阻塞点可中断，并等待退出完成。

### 9. 为什么一次 `escapes to heap` 不足以证明性能问题？

它是编译器对某路径的分析结果，不包含业务频率、对象大小、存活时间和是否被内联等完整成本。必须在真实 benchmark、`-benchmem` 和 profile 中确认。

### 10. GOGC 调大是否一定降低延迟？

不一定。它可能减少 GC 频率和 CPU，但增加内存占用；如果容器逼近上限，反而可能触发更严重的回收或 OOM。延迟还可能由锁、调度、I/O 和下游服务造成。

### 11. GPM 模型如何解释“启动很多 goroutine 但 CPU 没变快”？

很多 goroutine 只是 runnable/waiting，真正同时执行的 Go 代码受 P/GOMAXPROCS 和 CPU 限制；CPU 密集任务超过可用并行度后，更多 G 只增加调度和内存成本。

### 12. 如何设计一个可取消、限并发、能返回首个错误的批处理器？

用 `errgroup.WithContext` 建立生命周期，固定 worker 或信号量限制并发；生产任务和 worker 都监听 ctx；首个错误触发取消；关闭任务 channel 的责任归生产/协调方；最后 `Wait` 确保所有 goroutine 退出。

## 二、综合小项目：可回顾的最小闭环

目标：从 `[]Job` 中并发处理任务，最多 8 个 worker；任一任务失败，取消其他任务；结果写入 slice，不能产生泄漏。

```go
func Run(ctx context.Context, jobs []Job) ([]Result, error) {
	g, ctx := errgroup.WithContext(ctx)
	q := make(chan Job)
	results := make(chan Result)

	for i := 0; i < 8; i++ {
		g.Go(func() error {
			for {
				select {
				case <-ctx.Done():
					return ctx.Err()
				case job, ok := <-q:
					if !ok {
						return nil
					}
					result, err := process(ctx, job)
					if err != nil {
						return err
					}
					select {
					case results <- result:
					case <-ctx.Done():
						return ctx.Err()
					}
				}
			}
		})
	}

	g.Go(func() error {
		defer close(q)
		for _, job := range jobs {
			select {
			case q <- job:
			case <-ctx.Done():
				return ctx.Err()
			}
		}
		return nil
	})

	all := make([]Result, 0, len(jobs))
	done := make(chan struct{})
	go func() {
		defer close(done)
		for r := range results {
			all = append(all, r)
		}
	}()

	err := g.Wait()
	close(results) // 真实项目应由明确的协调者在 worker 全部结束后关闭
	<-done
	if err != nil && !errors.Is(err, context.Canceled) {
		return nil, err
	}
	return all, nil
}
```

上面示例用于回忆结构，若需要生产可用版本，应进一步把“关闭 results 的协调责任”交给专门的 worker group，避免 `g.Wait()` 与结果聚合的时序设计不清。关键检查项：

- slice 是否预估容量、是否需要排序；
- results 是否有消费者；
- 每个发送/接收是否可被 ctx 打断；
- error 取消后所有 worker 是否退出；
- `process` 是否把 ctx 传给下游；
- 是否用 race、benchmark、goroutine profile 验证。
