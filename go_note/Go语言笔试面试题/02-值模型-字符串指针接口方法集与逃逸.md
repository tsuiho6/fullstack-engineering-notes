# 值模型：字符串、指针、接口、方法集与逃逸

> 本章解决一组看似分散、实际都在问“值如何表示和流动”的问题：指针、string/rune、slice/map、interface 比较、typed nil、方法集和逃逸分析。

## 一、是什么

Go 的参数传递始终是按值传递；区别只在于这个值本身可能是普通数据、地址、slice 描述符、map 引用或 interface 的动态值描述。理解“复制了什么、共享了什么”，比背“引用传递”更准确。

## 二、为什么需要

这些规则决定了：

- 函数修改参数后，调用方能看到什么；
- 一个字符串的长度到底按 byte 还是字符计算；
- 两个 interface 能否比较；
- nil 指针为什么装进 error 后不等于 nil；
- 指针 receiver 为什么在变量上能调用、在 map 元素上不能调用；
- 返回局部变量指针为什么不会悬空。

## 三、核心用法

### 1. 指针：共享可变对象，但参数仍然按值传递

~~~go
func increment(n *int) {
	*n = *n + 1
}

n := 1
increment(&n)
// n == 2
~~~

这里复制的是地址，不是对调用方变量本身做“引用传递”。如果函数要让 slice 的长度或底层数组变化传回去，必须返回新的 slice 描述符：

~~~go
func appendValue(values []int, v int) []int {
	return append(values, v)
}
~~~

slice 的核心形状可以记为：

~~~text
slice = data 指针 + len + cap
~~~

因此元素修改可能对调用方可见，但 append 可能分配新底层数组；不接返回值就可能丢失新描述符。

### 2. string、byte 与 rune

~~~go
s := "Go语言"
fmt.Println(len(s))        // 8：UTF-8 字节数
fmt.Println(len([]rune(s))) // 4：Unicode code point 数

for byteIndex, r := range s {
	fmt.Println(byteIndex, r)
}
~~~

- string 是只读的字节序列；
- byte 是 uint8，适合协议、文件和原始二进制；
- rune 是 int32 的别名，适合按 Unicode code point 处理；
- range 遍历 string 时，索引是字节位置，值是 rune；
- code point 数仍不一定等于用户看到的“字符数”，组合字符和字体渲染属于更高层问题。

多次拼接时优先使用 strings.Builder：

~~~go
var b strings.Builder
b.Grow(128)
for _, word := range words {
	b.WriteString(word)
}
result := b.String()
~~~

原理不是“+ 永远错误”，而是 string 不可变；在循环中反复创建新字符串可能产生更多拷贝。少量、固定次数拼接直接使用 + 更清楚。

### 3. map 查询与 nil

~~~go
value, ok := counts["go"]
if !ok {
	// key 不存在；value 可能仍是 int 的零值
}
~~~

读取 nil map 是安全的，写入 nil map 会 panic：

~~~go
var counts map[string]int
_ = counts["go"] // 安全，得到 0
counts["go"] = 1 // panic
~~~

写入前初始化：

~~~go
counts = make(map[string]int)
counts["go"] = 1
~~~

### 4. slice 比较

Go 不允许直接使用 == 比较两个 slice。当前项目中，元素可比较时优先使用 slices.Equal：

~~~go
if slices.Equal(got, want) {
	// 元素按顺序相等
}
~~~

slices.Equal 把 nil slice 和长度为 0 的非 nil slice 视为相等；如果业务必须区分“未提供”和“明确为空”，要单独检查 nil。

### 5. interface：动态类型 + 动态值

可以把 interface 想成一个便于理解的二元组：

~~~text
interface = dynamic type + dynamic value
~~~

它不是语言规范承诺的内存布局，但非常适合解释比较和 typed nil：

~~~go
type TaskError struct{}

func (*TaskError) Error() string { return "task failed" }

var p *TaskError = nil
var err error = p

fmt.Println(p == nil)   // true
fmt.Println(err == nil) // false
~~~

err 里已经有动态类型 *TaskError，只是动态值为 nil，所以 interface 本身不是 nil。

两个 interface 比较时，动态类型和动态值都要满足比较条件；如果动态值的类型不可比较，比较会 panic：

~~~go
var a any = []int{1}
var b any = []int{1}
_ = a == b // panic：slice 不可比较
~~~

所以 interface 可以比较，不等于“任意装入 interface 的值都能比较”。

### 6. 方法集与可寻址性

~~~go
type Counter struct {
	n int
}

func (c *Counter) Inc() {
	c.n++
}

c := Counter{}
c.Inc() // c 可寻址，编译器可视为 (&c).Inc()
~~~

但 map 元素不可寻址：

~~~go
m := map[string]Counter{"go": {}}
// m["go"].Inc() // 编译错误
~~~

项目中如果需要修改 map 中的对象，通常存指针：

~~~go
mp := map[string]*Counter{"go": {}}
mp["go"].Inc()
~~~

方法集记忆：

- T 的方法集包含 T receiver 的方法；
- *T 的方法集包含 T receiver 和 *T receiver 的方法；
- T 的变量如果可寻址，可以自动取地址调用 *T 方法；
- map 元素、常量和 interface 中存放的具体值不能按这种方式取地址。

### 7. 返回局部变量指针与逃逸分析

~~~go
func newCount() *int {
	n := 42
	return &n
}
~~~

这是安全的。编译器会通过逃逸分析决定 n 的存储位置；如果它的生命周期需要超过当前函数，编译器会让它以适合的方式继续存活。不要把“返回局部指针必然危险”当成 C/C++ 规则套过来。

逃逸分析是编译器优化实现，不是业务代码可依赖的内存布局承诺。需要观察时可以用编译器诊断参数，但不能据此写出依赖某个版本栈/堆细节的逻辑。

## 四、核心原理

### 1. 可变性决定共享风险

值复制只复制外层描述；如果描述里包含指向底层数据的指针，多个副本仍可能共享同一数据。因此 slice、map、channel 要特别关注所有权、并发访问和生命周期。

### 2. interface nil 的关键是“类型槽是否为空”

普通 nil interface 可以理解为 dynamic type 和 dynamic value 都为空；装入 nil 指针后，dynamic type 已经存在，所以与 nil 比较为 false。

直观记忆：**指针值为 nil，不代表装它的接口也为 nil。**

### 3. 方法调用有两个门槛

第一关是方法集：这个静态类型是否拥有该方法。第二关是可寻址性：如果需要把 T 自动转成 *T，接收者必须是可寻址的。很多“变量能调用、map 元素不能调用”的差异都来自第二关。

### 4. GC 与逃逸不要混为一谈

逃逸分析决定某个对象怎样分配和存活；GC 决定不可达对象何时被回收。返回局部指针安全，是生命周期和编译器保证的问题，不是“手动 free”或“马上 GC”的问题。

## 五、常见场景

- ⭐ 请求、配置、领域对象：用具体 struct，必要时用指针 receiver 修改状态。
- ⭐ JSON、文本、协议：区分 string、[]byte 和 rune。
- ⭐ 多实现边界：用小 interface；不要用 any 逃避建模。
- ⭐ map 中的可变对象：使用 map[K]*T，或取出值、修改后再写回。
- ⭐ 测试切片结果：用 slices.Equal；先决定 nil 与空 slice 是否语义相同。
- △ 性能排查：用逃逸诊断、benchmark 和 profile 验证，不凭“指针一定慢”下结论。

## 六、踩坑点

1. append 之后不接返回值，导致新底层数组和新 len 没传回。
2. 把 len(string) 当成人类字符数。
3. 直接写 nil map。
4. 用 interface 比较装有 slice、map、func 的动态值，触发 panic。
5. 把 typed nil error 当成 nil error。
6. 误以为 T 永远不能调用 *T 方法，忽略了变量可寻址时的自动取址。
7. 试图修改 map[K]T 的元素字段；改用 map[K]*T 或写回完整值。
8. 把 reflect.DeepEqual 的 nil/空语义与 slices.Equal 混为一谈。
9. 把 Go 普通代码的类型检查写成 shape、dtype、device；这些是张量或特定计算库的概念，Go 应检查类型、len、cap、nil、所有权和并发访问。

## 七、项目中的实际使用

一个 API 层常见的数据流可以这样设计：

~~~text
输入 bytes/string
    -> 解析为具体 struct
        -> 业务层用具体类型和 error
            -> 外部存储通过小 interface 注入
                -> 并发任务只传递明确类型的结果
~~~

如果存储接口返回 error，外层应保留底层身份：

~~~go
if err := store.Save(ctx, task); err != nil {
	return fmt.Errorf("save task %d: %w", task.ID, err)
}
~~~

不要把所有输入先转成 any 再在运行时断言；这会失去编译期的类型约束，也让错误更晚出现。

## 八、一句话总结

**值传递看外层是否共享底层数据，字符串看 byte/rune，接口看动态类型与动态值，方法调用看方法集与可寻址性。**

## 九、核心问答

### 1. Go 是值传递还是引用传递？

始终是值传递。指针传递的是地址副本，slice 传递的是描述符副本，map 传递的是指向同一 map 数据的值；“看起来能改到外面”来自共享底层对象，不是改变了传参规则。

### 2. interface 可以比较吗？

可以，但只有当动态值可比较时才安全；两个 interface 还要有相同的动态类型和值。装入 slice、map、func 后使用 == 可能 panic。

### 3. 为什么 typed nil error 不等于 nil？

接口里有动态类型 *T，虽然动态值是 nil，但接口的类型槽非空，所以 error != nil。

### 4. 为什么返回局部变量指针安全？

编译器会分析生命周期，必要时让对象在函数返回后继续存活。Go 不会让一个已经失效的局部变量地址直接暴露给调用方。

### 5. T receiver 和 *T receiver 如何选择？

需要修改对象、对象较大或想统一使用指针语义时用 *T；小而不可变、明确值语义时可用 T。混用时要检查方法集是否仍满足目标接口。

## 十、自测与答案

### 先独立作答

1. 为什么函数接收 []int 后能改元素，却不能保证外部 slice 的 len 改变？
2. len("Go语言") 与 len([]rune("Go语言")) 分别表示什么？
3. 判断下面三个表达式的结果：p == nil、err == nil、err == p。

~~~go
var p *TaskError
var err error = p
~~~

4. 为什么 m["go"].Inc() 可能无法编译，而 map[string]*Counter 可以？
5. 如何区分“nil slice”和“空但已初始化 slice”？
