# 最小项目闭环与综合复习

> 面试题的终点不是答出定义，而是把定义转成一次可运行、可测试、可取消、可维护的项目改动。本章把前四章压缩成一个待办任务闭环。

## 一、是什么

最小闭环是：明确数据模型，处理输入，返回 error，隔离外部依赖，管理并发任务生命周期，用测试和构建命令验证结果。

它不是一个完整生产系统，而是一条足够小、能覆盖核心机制的练习路径。

## 二、为什么需要

零散背题容易出现“每题都会，但不会组合”的问题：

- 会 error，却把错误字符串当状态；
- 会 interface，却为单一实现设计过多抽象；
- 会 channel，却没有关闭和取消策略；
- 会 defer，却把资源释放拖到错误的函数层级；
- 会写测试，却依赖 map 遍历顺序或 goroutine 输出顺序。

最小闭环的价值是把“解释、写出、判断、避坑”放进一次真实流程。

## 三、核心用法

### 1. 先定义数据和不变量

~~~go
type Task struct {
	ID    int
	Title string
	Done  bool
}

var ErrNotFound = errors.New("task not found")

func (t *Task) Complete() error {
	if t.Done {
		return errors.New("task already completed")
	}
	t.Done = true
	return nil
}
~~~

这里的规则是：

- Title 不能为空；
- ID 用于定位；
- Done 是明确状态；
- 已完成任务不能再次完成。

先写不变量，后面 error、测试和并发策略才有判断标准。

### 2. 用具体类型表达业务，用小 interface 隔离外部系统

~~~go
type Store interface {
	Save(context.Context, Task) error
	Find(context.Context, int) (Task, error)
}

func CompleteTask(ctx context.Context, store Store, id int) error {
	task, err := store.Find(ctx, id)
	if err != nil {
		return fmt.Errorf("find task %d: %w", id, err)
	}
	if err := task.Complete(); err != nil {
		return fmt.Errorf("complete task %d: %w", id, err)
	}
	if err := store.Save(ctx, task); err != nil {
		return fmt.Errorf("save task %d: %w", id, err)
	}
	return nil
}
~~~

这里 interface 的边界是存储系统，不是 Task 本身。调用方依赖它真正需要的行为，测试时可替换为内存实现。

### 3. 以可观察行为写测试

~~~go
func TestTaskComplete(t *testing.T) {
	tests := []struct {
		name     string
		task     Task
		wantErr  bool
		wantDone bool
	}{
		{name: "complete", task: Task{Title: "learn"}, wantDone: true},
		{name: "already done", task: Task{Done: true}, wantErr: true},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			task := tt.task
			err := task.Complete()
			if (err != nil) != tt.wantErr {
				t.Fatalf("error = %v, wantErr = %v", err, tt.wantErr)
			}
			if task.Done != tt.wantDone {
				t.Fatalf("Done = %v, want %v", task.Done, tt.wantDone)
			}
		})
	}
}
~~~

测试关注输入、输出、错误语义和状态变化，不锁死内部实现。

### 4. 并发闭环用“有界 + 可取消 + 可等待”

~~~text
任务来源
    -> 有界 worker 数
        -> jobs channel
            -> worker select(ctx.Done(), jobs)
                -> 结果 / 第一个错误
                    -> cancel
                        -> Wait
~~~

不要把“启动更多 goroutine”当成吞吐量方案；先定义最大并发数、背压、错误传播和取消策略。

### 5. 用命令验证，而不是只看一次输出

~~~powershell
gofmt -w .
go test ./...
go test -race ./...
go vet ./...
go build ./...
~~~

这些命令的角色不同：

- gofmt：统一格式；
- go test：验证行为；
- -race：检查已覆盖路径上的数据竞争；
- go vet：发现部分可疑代码；
- go build：确认可构建交付。

## 四、核心原理

### 1. 依赖关系比题目顺序重要

推荐的知识依赖是：

~~~text
作用域 / 类型
    -> 函数返回值 / error
        -> struct / method / pointer
            -> interface / typed nil
                -> goroutine / channel / context
                    -> test / race / build
~~~

上游概念没有稳定，后面的题只能靠记忆。例如不懂值传递，就会把 interface nil、方法集和 map 元素不可寻址混成“奇怪规则”。

### 2. 教学演示、原理和项目写法要分开

| 层次 | 目的 | 典型例子 |
|---|---|---|
| 教学演示 | 把一个规则变得可见 | 打印 defer 输出、用小程序比较 nil |
| 原理 | 解释为什么 | 作用域、动态类型、方法集、阻塞条件 |
| 项目推荐 | 让系统可维护 | 显式初始化、错误包装、context、测试 |

面试回答可以从原理开始，但落到项目时必须补上生命周期、错误、测试和边界。

### 3. 判断一个设计是否闭环

对任意函数或 goroutine，依次问：

1. 输入的类型和形状是什么？这里的形状指参数个数、len/cap、是否 nil；Go 普通代码没有统一的 dtype/device。
2. 成功输出是什么？
3. 失败如何表达？
4. 谁拥有并修改数据？
5. 是否会阻塞？谁让它继续？
6. 谁负责清理、关闭、取消和等待？
7. 如何用测试证明边界行为？

## 五、常见场景

- ⭐ 小型 HTTP/CLI 服务：具体 struct + error + 小 interface + table-driven test。
- ⭐ 外部存储或网络调用：context 贯穿调用链，错误用 %w 保留根因。
- ⭐ 批量处理：有限 worker，明确 channel 关闭方和取消条件。
- ⭐ 面试复习：先遮住答案主动回忆，再用最小代码验证。
- ○ 性能优化：没有 benchmark 或 profile 时，不要仅凭 escape、Builder 或 GOMAXPROCS 的直觉改代码。

## 六、踩坑点

1. 业务函数用 panic 表示普通输入错误。
2. 为了“面向接口”而给每个 struct 预先设计接口。
3. 任务失败后只 Wait，不 cancel 其他任务。
4. 用 Sleep、打印顺序或 goroutine 数量猜测并发正确性。
5. 只测成功路径，不测 nil、空值、重复调用、超时、取消和关闭。
6. 用 map 的随机遍历顺序作为输出或测试依据。
7. 把测试中的实现细节当成公共行为，导致后续重构无法进行。

## 七、项目中的实际使用

### 最小目录

~~~text
todo/
├── go.mod
├── task.go
├── store.go
├── task_test.go
└── cmd/todo/main.go
~~~

### 推荐工作流

1. 先写 Task、不变量和固定错误。
2. 写纯业务函数：完成任务、查找任务、校验输入。
3. 为成功、失败、重复操作和零值写表驱动测试。
4. 需要隔离外部存储时，再在调用方定义小 Store 接口。
5. 引入并发前，先写同步版本；并发只解决明确的吞吐或等待问题。
6. 引入 worker 后补上 context、WaitGroup、channel 关闭和错误传播。
7. 执行 test、race、vet、build，最后再做性能测量。

### 自检矩阵

| 能力 | 读者应该能回答 |
|---|---|
| 能解释 | 为什么 typed nil 不等于 nil？为什么 map 元素不能取地址？ |
| 能写出 | 带 error 的函数、小 interface、可取消 worker、表驱动测试 |
| 能判断 | 什么时候用 slice、map、struct、interface、channel、mutex |
| 能避开 | nil map 写入、append 丢返回值、:= 遮蔽、channel 泄漏、错误字符串分支 |

## 八、一句话总结

**把题目串成项目：具体数据 + 明确 error + 小接口 + 可收尾并发 + 可重复测试，才算真正掌握。**

## 九、核心问答

### 1. 为什么接口通常由使用方定义？

使用方最清楚自己需要哪些行为；小接口能减少耦合，也更容易用内存实现测试。实现方只负责提供方法，不必预先声明 implements。

### 2. 为什么 WaitGroup、channel、context 不能互相替代？

WaitGroup 等待，channel 通信并同步，context 取消和传递截止时间。一个任务可能同时需要三者。

### 3. 如何选择 slice 和 map？

需要顺序、批量遍历和追加时用 slice；需要按 key 高频查找、去重或计数时用 map。两者都需要时，明确谁是事实来源，避免双份状态失同步。

### 4. 如何判断是否该引入 interface？

看是否存在外部边界、多实现、替换需求或测试隔离点。只有一个内部实现且没有变化迹象时，具体类型往往更简单。

### 5. 如何判断并发设计是否完成？

不仅要能启动，还要能说明等待、通信、关闭、取消、错误传播、共享状态保护和所有退出路径。

## 十、自测与答案

### 先独立作答

1. 设计一个 FindTask 函数：找不到时如何让调用方稳定判断，同时保留任务 ID 上下文？
2. 什么时候 map[string]*Task 比 map[string]Task 更适合？
3. 一个 worker 处理任务时发生错误，如何停止其他 worker？
4. 为什么不能只用 go test 不用 go test -race？
5. 把一个“能运行的 demo”变成项目代码，至少要补哪些内容？

<summary>答案</summary>

1. 定义 ErrNotFound，返回 fmt.Errorf("find task %d: %w", id, ErrNotFound)，调用方用 errors.Is。
2. 需要原地修改对象、避免反复复制，或需要通过指针 receiver 调用方法时；同时要管理 nil 指针和生命周期。
3. 创建可取消 context；第一个错误触发 cancel，其他 worker 在阻塞点监听 ctx.Done()，最后 Wait 等待全部退出。
4. 普通测试不一定覆盖出竞态；-race 会在运行覆盖路径时插入检测，能发现很多普通测试看不出的并发问题。
5. 补数据不变量、错误语义、资源清理、外部依赖边界、并发退出策略、边界测试和可重复构建验证。
