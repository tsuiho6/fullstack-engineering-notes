# 表单、认证、授权与环境变量

> 优先级：⭐ 第二阶段必须掌握：表单、环境变量、认证和授权边界。

## 一、是什么

表单负责收集用户输入；认证确认用户是谁；授权确认用户能做什么；环境变量为不同环境提供配置和秘密。

四者经常一起出现，但不能混为一谈：

~~~text
表单输入 → 服务端校验 → 认证身份 → 授权资源 → 执行读写
~~~

## 二、为什么需要

浏览器输入是不可信的，登录状态也不等于拥有所有权限。数据库连接串、AI API Key 和会话密钥不能进入浏览器或 Git 仓库。

## 三、核心用法

表单提交的最小流程：

~~~tsx
<form action={saveNote}>
  <label htmlFor="title">标题</label>
  <input id="title" name="title" required />
  <button type="submit">保存</button>
</form>
~~~

服务端再次校验：

~~~ts
'use server';

export async function saveNote(formData: FormData) {
  const title = String(formData.get('title') ?? '').trim();
  if (title.length < 2) {
    return { ok: false, message: '标题至少两个字' };
  }

  const session = await getSession();
  if (!session) {
    return { ok: false, message: '请先登录' };
  }

  await db.note.create({
    data: { title, authorId: session.userId },
  });
  return { ok: true };
}
~~~

环境变量：

~~~text
.env.local
DATABASE_URL=private-value
AI_API_KEY=private-value
NEXT_PUBLIC_SITE_NAME=学习资料库
~~~

只有以 NEXT_PUBLIC_ 开头的变量才会被打包给浏览器，因此这个前缀不是“安全标记”，而是“公开变量标记”。

## 四、核心原理

认证和授权：

- Authentication：你是谁？
- Authorization：你能访问或修改什么？

推荐把授权逻辑放在数据访问层或写入函数附近，而不是只放在页面按钮显示逻辑中：

~~~ts
export async function getNoteForUser(noteId: string) {
  const session = await verifySession();
  const note = await db.note.findUnique({ where: { id: noteId } });

  if (!note || note.authorId !== session.userId) {
    return null;
  }
  return note;
}
~~~

环境变量通常从 .env* 加载。私密变量只在服务器使用；公开变量会在构建阶段内联到客户端包，不能放密码、数据库连接串或模型密钥。

## 五、常见场景

- 后台系统：认证用户并按角色授权。
- 笔记编辑：验证用户是作者或管理员。
- AI 应用：模型 API Key 只在服务器使用。
- 表单：客户端改善体验，服务器完成最终校验。
- 多环境：本地、预览和生产使用不同数据库和密钥。

## 六、踩坑点

- 只依赖 required、disabled 或前端按钮隐藏。
- 把认证成功误当成有权访问所有资源。
- 将 DATABASE_URL 或 AI_API_KEY 写成 NEXT_PUBLIC_。
- 把 .env.local 提交到 Git。
- 在 Client Component 中读取私密环境变量。
- 在 layout 做一次登录判断后，认为所有 Server Action 都安全。
- 自己从零实现密码加密和完整会话系统，却没有理解 cookie、过期、CSRF 和会话撤销。

## 七、项目中的实际使用

短期学习不需要先造一个完整认证系统。建议：

1. 先用官方课程理解登录、会话和受保护路由。
2. 项目中使用成熟认证库处理会话和 Provider。
3. 自己负责业务授权：作者、管理员、组织成员。
4. 把 verifySession 和数据访问封装在服务器模块。
5. 每个 Server Action 和 Route Handler 都再次检查权限。

环境变量按用途分组：

~~~text
数据库、会话密钥、模型密钥 → 服务器私密变量
站点名称、公开分析 ID       → NEXT_PUBLIC_ 变量
~~~

## 八、一句话总结

认证回答“你是谁”，授权回答“你能做什么”，环境变量决定“秘密放在哪里”。

## 九、核心问答

### 1. 前端表单校验有用吗？

有用，但只用于即时反馈和减少无效提交；安全校验必须在服务器再次执行。

### 2. 为什么登录用户仍然需要授权检查？

登录只证明身份，不证明他拥有当前资源或当前操作权限。

### 3. NEXT_PUBLIC_ 代表什么？

代表允许被打包到浏览器的公开配置，不代表安全。

### 4. 自己实现认证和使用认证库如何选择？

学习原理可以实现最小流程；生产项目优先使用成熟认证库，并理解它的会话和授权边界。

## 十、自测与答案

1. 用户修改笔记前，服务器至少验证什么？
2. AI API Key 应放在哪里？
3. 为什么客户端隐藏删除按钮仍然不安全？
4. 预览环境和生产环境为什么不能共享同一数据库密钥？

<summary>参考答案</summary>

1. 用户身份、笔记是否存在、用户是否拥有该笔记或具备管理员权限、输入是否合法。
2. 服务器私密环境变量中，不能使用 NEXT_PUBLIC_ 前缀。
3. 用户可以构造请求直接调用服务器接口或 Server Action。
4. 防止测试数据、权限和密钥相互污染，也避免预览代码影响生产数据。
