# 数据获取、缓存与重新验证

> 优先级：⭐ 必须掌握；△ 深入缓存 API：先掌握数据流与失效判断，再按版本学习缓存细节。

## 一、是什么

数据获取是从数据库、后端服务或第三方 API 读取数据；缓存是复用已经生成的数据或结果；重新验证是在数据变化后让旧结果失效并生成新结果。

可以把一次读取记成：

~~~text
数据来源 → 读取位置 → 新鲜度策略 → 加载反馈 → 错误处理 → 写入后的失效方式
~~~

## 二、为什么需要

如果每次请求都重新访问慢数据库，页面会慢；如果永远使用旧数据，用户又会看到过期内容。Next.js 的学习重点不是背默认值，而是能根据业务明确回答“这份数据允许旧多久”。

## 三、核心用法

Server Component 中直接调用服务器数据函数：

~~~tsx
import { getNotes } from '@/app/lib/data';

export default async function NotesPage() {
  const notes = await getNotes();
  return <NoteList notes={notes} />;
}
~~~

对 fetch 数据设置时间重新验证：

~~~ts
const response = await fetch('https://example.com/api/notes', {
  next: { revalidate: 60 },
});

const notes = await response.json();
~~~

未启用 Cache Components 时，可以给 fetch 结果添加标签：

~~~ts
const response = await fetch('https://example.com/api/notes', {
  next: { tags: ['notes'] },
});
~~~

写入后如果由 Server Action 触发，并要求当前用户立即看到新值：

~~~ts
import { updateTag } from 'next/cache';

export async function updateNote(id: string, title: string) {
  'use server';
  await db.note.update({ where: { id }, data: { title } });
  updateTag('notes');
}
~~~

如果是 Route Handler、Webhook，或允许 stale-while-revalidate：

~~~ts
import { revalidateTag, revalidatePath } from 'next/cache';

export async function refreshNotes() {
  revalidateTag('notes', 'max');
  revalidatePath('/notes');
}
~~~

如果项目启用了 Cache Components，缓存函数可以显式声明寿命和标签：

~~~ts
import { cacheLife, cacheTag, updateTag } from 'next/cache';

export async function getNotes() {
  'use cache';
  cacheLife('hours');
  cacheTag('notes');
  return db.note.findMany();
}

export async function updateNote(id: string, title: string) {
  'use server';
  await db.note.update({ where: { id }, data: { title } });
  updateTag('notes');
}
~~~

updateTag 适合 Server Action 中的 read-your-own-writes；revalidateTag('notes', 'max') 适合允许旧内容短暂存在、后台重新生成的场景；revalidatePath 适合按路径失效。Cache Components 需要按当前 Next.js 版本确认配置和可用 API。

## 四、核心原理

### 1. 缓存和渲染不是一回事

页面是否静态、动态或流式，和某个数据请求是否可缓存有关，但不是完全相同的概念。不要只看到 async 就判断页面一定动态，也不要只看到 fetch 就假设一定缓存。

### 2. 时间失效和事件失效

| 方式 | 含义 | 适合 |
| --- | --- | --- |
| 时间重新验证 | 一段时间后允许生成新数据 | 新闻、榜单、低频变化内容 |
| 标签失效 | 数据变化时按标签刷新 | 笔记、商品、用户资料 |
| 路径失效 | 让某个页面路径重新生成 | 页面范围明确的写入 |
| 立即失效 | 写入者马上看到自己的新数据 | read-your-own-writes |

### 3. 缓存必须和权限绑定

用户私有数据不能被错误地缓存成所有用户共享的结果。涉及 cookies、headers、用户身份或个性化查询时，要先确认缓存边界和数据隔离。

## 五、常见场景

- 公开笔记内容：按时间或标签缓存。
- 后台编辑后的列表：写入后按 notes 标签失效。
- 用户个人资料：根据身份隔离，谨慎缓存。
- 实时数据：不要为了性能强行使用长缓存。
- 第三方 API：在服务器读取，避免把密钥放到浏览器。

## 六、踩坑点

- 只调用 revalidatePath，却没有理解真正的数据缓存来源。
- 写入成功但页面仍显示旧列表，忘记让对应标签或路径失效。
- 把包含用户身份的数据放进公共缓存。
- 以为客户端刷新一定会绕过服务器缓存。
- 使用当前版本新缓存 API 时，忽略项目配置和 Next.js 版本。
- 并行页面读取同一数据时，没有抽取统一的数据访问函数。

## 七、项目中的实际使用

学习资料库可以把数据访问集中在 app/lib/data.ts：

~~~ts
import 'server-only';

export async function getNote(slug: string) {
  return db.note.findUnique({ where: { slug } });
}

export async function listNotes(query: string) {
  return db.note.findMany({
    where: { title: { contains: query } },
    orderBy: { updatedAt: 'desc' },
  });
}
~~~

写入函数集中在 app/lib/actions.ts，并在数据库写入成功后执行与数据对应的失效操作。这样页面、元数据和相关列表可以复用同一数据边界。

## 八、一句话总结

缓存不是“让页面更快”的口号，而是对数据允许多旧、何时失效以及谁能看到的明确承诺。

## 九、核心问答

### 1. revalidateTag 和 revalidatePath 如何选择？

知道数据标签时优先按标签失效，粒度更精确；只知道页面路径或页面范围明确时使用路径失效。

### 2. 为什么写入之后必须重新验证？

因为读取结果可能来自缓存。数据库已经更新，不代表此前生成的页面或数据结果自动变新。

### 3. 公开内容和用户私有内容的缓存判断有何区别？

公开内容可以共享缓存；私有内容必须按用户或会话隔离，不能把一个用户的结果复用给另一个用户。

### 4. 学习缓存时最不应该背什么？

不应死记某个版本的所有默认值；应该掌握显式设置新鲜度、写入后失效和验证数据隔离的方法。
