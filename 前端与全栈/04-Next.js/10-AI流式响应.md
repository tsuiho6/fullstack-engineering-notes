# AI 流式响应

> 优先级：△ 原理先掌握；项目阶段再深入具体 AI SDK 版本。

## 一、是什么

AI 流式响应不是等模型完整生成后一次性返回，而是服务器生成一小段就发送一小段，客户端边接收边展示。

最小链路：

~~~text
Client Component 输入
    ↓
Route Handler / 服务器函数
    ↓
模型 Provider
    ↓
ReadableStream / SSE
    ↓
客户端逐段更新消息
~~~

## 二、为什么需要

模型响应可能持续数秒甚至更久。一次性等待会让用户看到长时间空白；流式能降低首字节和首个内容的等待感，并支持取消、重试和实时状态。

## 三、核心用法

先理解原生 Web Stream：

~~~ts
export async function GET() {
  const encoder = new TextEncoder();
  const stream = new ReadableStream({
    async start(controller) {
      controller.enqueue(encoder.encode('第一段\n'));
      await new Promise((resolve) => setTimeout(resolve, 300));
      controller.enqueue(encoder.encode('第二段\n'));
      controller.close();
    },
  });

  return new Response(stream, {
    headers: { 'Content-Type': 'text/plain; charset=utf-8' },
  });
}
~~~

在真实 AI 项目中，通常让模型 SDK 负责生成流，让 Route Handler 返回 SDK 规定的响应格式。以 AI SDK 为例，服务器负责调用 streamText 和返回 UI message stream，客户端使用 useChat 订阅并管理消息状态。

概念结构：

~~~ts
// app/api/chat/route.ts
export async function POST(request: Request) {
  const body = await request.json();
  const result = streamText({
    model: modelProvider,
    prompt: body.prompt,
  });
  return result.toUIMessageStreamResponse();
}
~~~

~~~tsx
// app/chat/chat-panel.tsx
'use client';

const { messages, sendMessage, status, stop } = useChat();
~~~

具体 AI SDK API 会随版本变化，学习重点是“服务器生成流、协议传输、客户端增量渲染”，不要把某个版本的导入路径当成 Next.js 永久 API。

## 四、核心原理

### 1. 普通请求与流式请求

普通请求：

~~~text
请求 → 等待完整结果 → 一次性响应
~~~

流式请求：

~~~text
请求 → 响应头 → chunk 1 → chunk 2 → chunk 3 → 结束标记
~~~

客户端必须知道如何拼接、解析和结束一条消息。文本流适合简单内容；带事件或结构化数据时，需要明确协议，例如 SSE 或 UI message stream。

### 2. loading 与 streaming

loading.tsx 负责页面还没有准备好时的占位；AI streaming 负责响应已经开始后持续更新内容。二者可以同时存在，但解决的是不同时间段的问题。

### 3. 取消与错误

用户离开页面或点击停止时，客户端应中止请求；服务器和模型 Provider 需要正确处理断开。流已经发送一部分后，错误通常不能再修改已发送的 HTTP 状态码，只能发送错误事件或让客户端显示失败状态。

## 五、常见场景

- 聊天对话。
- 流式摘要和翻译。
- 代码生成。
- Agent 的步骤和工具状态。
- RAG 检索过程中的引用或进度数据。

## 六、踩坑点

- 把模型 API Key 放入 Client Component。
- 用 Server Action 代替所有需要持续响应的流式接口。
- 只处理成功文本，不处理错误、停止、超时和重复提交。
- 多条消息同时发送却没有消息 ID。
- 流式输出 Markdown 时没有考虑未闭合语法和渲染闪烁。
- 生产平台或反向代理缓冲响应。
- 没有限制输入长度、调用频率和输出成本。
- 将模型输出当成可信 HTML 直接渲染。

## 七、项目中的实际使用

学习资料库可以做一个“AI 笔记助手”：

1. Client Component 收集问题。
2. Route Handler 校验请求和用户身份。
3. Server 端读取相关笔记，不把数据库凭证暴露给浏览器。
4. 模型生成流式回答。
5. 客户端显示 submitted、streaming、ready、error 等状态。
6. 完成后把会话摘要或消息持久化到 PostgreSQL。

先实现纯文本流，再加入结构化数据、工具调用、引用和消息持久化。

## 八、一句话总结

AI 流式响应的本质是把“完整结果”拆成可持续传输的协议，并让客户端正确处理增量、结束、失败和取消。

## 九、核心问答

### 1. 为什么 AI 流式接口通常放在 Route Handler？

它需要接收请求并持续返回 HTTP 响应流，Route Handler 提供清晰的服务器接口。

### 2. AI SDK 是 Next.js 内置能力吗？

不是。Next.js 提供服务器运行和流式响应基础，AI SDK 是可选的模型和 UI 流协议工具。

### 3. 为什么 API Key 必须在服务器？

浏览器代码和请求可被用户查看，暴露密钥会导致滥用和费用风险。

### 4. 流式响应为什么需要协议？

客户端必须区分文本片段、消息结束、错误、工具调用和状态事件，不能只靠字符串猜测。
