# React 项目闭环

> 优先级：⭐

## 一、是什么

一个可维护的 React 页面，至少要形成这条闭环：

~~~text
数据模型
→ 组件树
→ Props 与 State
→ 用户事件
→ 数据更新
→ loading / error / empty / success
~~~

## 二、为什么需要

只会写静态组件还不能完成真实项目。真实页面必须处理数据来源、状态变化、表单、错误和用户反馈。

## 三、核心用法

以学习资料列表为例：

~~~text
NotesPage
  ├─ SearchForm
  ├─ RequestState
  │   ├─ Loading
  │   ├─ Error
  │   ├─ Empty
  │   └─ NoteList
  │       └─ NoteCard
  └─ NoteEditor
~~~

数据流：

~~~text
NotesPage 持有查询和请求状态
→ SearchForm 通过事件提交关键词
→ 请求模块返回 Note[]
→ NoteList 接收 notes
→ NoteCard 通过 onSelect / onDelete 发出事件
~~~

## 四、核心原理

组件职责可以分成：

| 类型 | 职责 |
| --- | --- |
| 展示组件 | 接收 Props 并渲染 UI |
| 容器组件 | 持有状态、请求数据和协调事件 |
| Hook | 复用状态逻辑 |
| 请求模块 | 处理网络和响应错误 |
| 类型模型 | 描述跨模块数据契约 |

不要让一个组件同时负责所有事情。

## 五、常见场景

- 列表和详情页。
- 搜索和筛选。
- CRUD 页面。
- 登录表单。
- AI 对话界面。

## 六、踩坑点

1. 只处理成功状态，不处理 loading 和 error。
2. 把请求、表单、列表和弹窗全写在一个组件里。
3. 把派生数据重复存进 State。
4. 列表 Key 不稳定。
5. 忽略请求竞态和组件卸载。
6. 为了复用过早抽象，导致 Hook 和组件难以理解。

## 七、项目中的实际使用

推荐最小实践：

1. 先用本地数组完成静态列表。
2. 加入 Props 和事件。
3. 加入 State 和表单。
4. 加入 loading、error、empty。
5. 把请求逻辑抽成模块或 Hook。
6. 用 TypeScript 检查数据边界。
7. 再接入 Next.js 和真实 API。

这样每一步都能运行和验证，不会把问题全部堆到最后。

## 八、一句话总结

React 项目不是组件数量越多越好，而是数据、状态、事件和副作用边界足够清楚。

## 九、核心问答

### 1. 展示组件和容器组件有什么区别？

展示组件主要渲染 Props；容器组件负责状态、请求和事件协调。

### 2. 为什么先用本地数组再接 API？

先验证组件树和交互，再引入异步和错误变量，便于定位问题。

### 3. AI 对话页面最少需要哪些状态？

消息列表、输入内容、发送中状态、错误状态，以及必要的取消和重试状态。

### 4. 什么时候应该抽自定义 Hook？

同一套状态逻辑出现多次，或逻辑本身已经形成清晰概念时。
