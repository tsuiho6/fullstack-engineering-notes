# React 跨章节综合问答

这篇不是新知识，而是把前面各篇串成一条能够解释、写出和判断的主线。复习时优先回答问题，再回到对应章节查漏。

## 一、核心依赖关系

~~~text
JSX 与组件
    ↓
Props 与单向数据流
    ↓
State 与事件
    ↓
条件渲染、列表、表单
    ↓
状态提升、Context、Reducer
    ↓
Effect 与 Ref
    ↓
自定义 Hooks 与异步 UI
    ↓
React + TypeScript
    ↓
可维护的页面闭环
~~~

每一层都建立在前一层之上：

- 不理解组件，就无法判断状态应该放在哪里。
- 不理解 Props 和单向数据流，就容易把组件之间的通信写乱。
- 不理解 State 和渲染，就会把派生数据、请求逻辑错误地塞进 Effect。
- 不会处理加载、错误和空状态，页面只能在“有数据”和“报错”之间切换。
- 不会用 TypeScript 表达 Props、事件和异步数据，React 项目会失去类型边界。

## 二、跨章节核心问答

### 1. React 组件到底在做什么？

组件接收 Props，读取 State，返回描述 UI 的 JSX。可以先用下面的模型理解：

~~~text
UI = f(Props, State)
~~~

Props 和 State 变化后，React 重新调用组件函数并计算新的 UI。组件函数本身应该保持纯净，不要在渲染过程中修改外部数据或执行请求。

对应笔记：[组件心智模型与学习路线](./00-组件心智模型与学习路线.md)

### 2. Props、State、普通变量分别什么时候用？

| 数据 | 来源 | 改变后是否触发重新渲染 | 典型用途 |
| --- | --- | --- | --- |
| Props | 父组件传入 | 父组件重新渲染并传入新值 | 配置、数据、回调 |
| State | 组件内部拥有 | 是 | 用户输入、展开状态、请求状态 |
| 普通变量 | 当前一次函数调用 | 否 | 临时计算、格式化结果 |
| Ref | 组件内部持有 | 否 | DOM、定时器、上一次值 |

一个判断方法：如果数据变化后界面必须更新，优先考虑 State；如果只是跨渲染保存但不需要更新界面，才考虑 Ref。

对应笔记：[Props 与数据流](./02-Props与数据流.md)、[State 与事件](./03-State与事件.md)、[Effect 与 Ref](./06-Effect与Ref.md)

### 3. 为什么不能直接修改 State？

React 需要通过设置 State 的动作知道“可能有新的 UI”。直接修改对象或数组，只改变了旧引用内部的内容，既可能不触发正确更新，也会破坏 React 对快照和不可变数据的判断。

推荐创建新值：

~~~tsx
setItems((items) =>
  items.map((item) =>
    item.id === id ? { ...item, done: !item.done } : item
  )
);
~~~

直观记忆：State 是“下一次渲染的输入”，不是可以随意改写的普通变量。

对应笔记：[State 与事件](./03-State与事件.md)

### 4. 为什么列表必须使用稳定的 Key？

Key 用来表示列表项的身份，使 React 能判断哪些项是原来的、哪些项被删除、哪些项被移动。稳定的业务 ID 通常比数组下标更可靠。

不推荐：

~~~tsx
items.map((item, index) => <Row key={index} item={item} />);
~~~

推荐：

~~~tsx
items.map((item) => <Row key={item.id} item={item} />);
~~~

如果列表会插入、删除、排序或过滤，使用下标可能导致输入框状态和列表项错位。

对应笔记：[渲染、列表与表单](./04-渲染列表表单.md)

### 5. 子组件需要修改父组件数据时怎么办？

React 默认沿父组件到子组件传递数据。子组件不能直接修改父组件的 State，父组件应把回调函数作为 Props 传下去：

~~~tsx
function List({ items, onDelete }: {
  items: Item[];
  onDelete: (id: string) => void;
}) {
  return items.map((item) => (
    <button key={item.id} onClick={() => onDelete(item.id)}>
      删除
    </button>
  ));
}
~~~

这形成“数据向下、事件向上”的单向数据流，数据所有权仍然清晰。

对应笔记：[Props 与数据流](./02-Props与数据流.md)

### 6. 状态提升、Context 和 Reducer 怎么选择？

可以按问题范围选择：

| 问题 | 优先选择 |
| --- | --- |
| 两个兄弟组件需要共享少量状态 | 状态提升 |
| 深层组件需要读取稳定的共享依赖 | Context |
| 状态转换很多，事件和规则需要集中管理 | Reducer |
| 需要跨页面、缓存、服务端同步或复杂数据生命周期 | 再评估专门的数据方案 |

Context 解决“怎么把值传到深层组件”，不自动解决状态建模、缓存和服务端同步。Reducer 解决“状态如何根据动作转换”，也不等于全局状态管理。

对应笔记：[状态提升、Context 与 Reducer](./05-状态提升Context与Reducer.md)

### 7. Effect 和事件处理函数有什么区别？

- 事件处理函数：由用户动作直接触发，例如点击、提交、输入。
- Effect：在渲染提交后，把 React 状态同步到外部系统，例如请求、订阅、DOM API、定时器。

例如，提交表单请求应由提交事件触发；页面根据某个 ID 变化自动订阅外部数据，才适合使用 Effect。

不要为了计算派生值而写 Effect：

~~~tsx
// 不必要：fullName 可以在渲染期间直接计算
const fullName = firstName + ' ' + lastName;
~~~

对应笔记：[Effect 与 Ref](./06-Effect与Ref.md)

### 8. 为什么异步页面至少要区分加载、错误、空数据和成功？

“请求还没完成”“请求失败”“请求成功但没有数据”“请求成功且有数据”是四种不同状态。只显示一个 loading 布尔值，通常无法表达错误和空结果。

最小状态模型：

~~~ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; data: T };
~~~

在 success 状态下再根据数据长度展示空状态或内容，可以避免多个布尔值互相矛盾。

对应笔记：[自定义 Hooks 与异步 UI](./07-自定义Hooks与异步UI.md)

### 9. React + TypeScript 最重要的类型边界是什么？

优先把组件输入、事件输入和异步数据建模清楚：

~~~tsx
type SearchFormProps = {
  initialKeyword?: string;
  onSubmit: (keyword: string) => void;
};

function SearchForm({ initialKeyword = '', onSubmit }: SearchFormProps) {
  const [keyword, setKeyword] = useState(initialKeyword);

  function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    setKeyword(event.target.value);
  }

  return (
    <form onSubmit={(event) => {
      event.preventDefault();
      onSubmit(keyword.trim());
    }}>
      <input value={keyword} onChange={handleChange} />
      <button type="submit">搜索</button>
    </form>
  );
}
~~~

推荐先建立业务类型，再让 Props、State、请求结果和回调复用这些类型。不要用 any 把边界抹掉。

对应笔记：[React 与 TypeScript](./08-React与TypeScript.md)

## 三、最小项目闭环：一个可搜索的笔记列表

假设要做一个“学习笔记列表”页面，建议按下面顺序实现：

### 第一步：先建立类型和静态组件

~~~ts
type Note = {
  id: string;
  title: string;
  summary: string;
  tags: string[];
};
~~~

先用静态数组渲染 NoteList 和 NoteCard，确认组件边界、Props 和 Key 都清楚。

### 第二步：加入受控搜索表单

- SearchForm 拥有输入框的临时 State。
- 提交时通过回调把字符串传给页面组件。
- 页面组件根据关键词计算或请求结果。

### 第三步：加入异步状态

- 页面或自定义 Hook 管理 loading/error/success。
- 成功但数组为空时渲染 Empty 状态。
- 请求失败时提供重试动作。

### 第四步：明确状态所有权

- 搜索关键词如果影响整个页面，放在页面组件。
- 仅用于输入框暂存的值，可以留在 SearchForm。
- 列表数据和请求状态放在页面或 useNotes 中。
- 卡片展开详情等局部交互状态留在 NoteCard。

### 第五步：再拆自定义 Hook

当页面中请求和状态逻辑变复杂时，再抽成：

~~~ts
const { data, status, error, retry } = useNotes(keyword);
~~~

不要为了“看起来高级”提前把所有代码都抽成 Hook。抽取的目标是复用逻辑和降低页面复杂度，而不是隐藏组件结构。

完整页面结构可参考：[项目闭环](./09-项目闭环.md)

## 四、综合自测

1. 一个值会影响 UI，但它既不是 Props，也不是 State，可能有哪些原因？
2. 为什么“根据 State 计算出的值”通常不应该再存一个 State？
3. 列表使用下标作为 Key，在什么情况下会出错？
4. Context 和状态提升分别解决什么问题？
5. 一个搜索请求被连续触发两次，第一次请求后返回，为什么可能覆盖第二次结果？
6. 什么时候用 Ref，什么时候用 State？
7. 受控输入框至少需要哪些输入输出关系？
8. 一个 React + TypeScript 组件最少应该明确哪些类型边界？

<details>
<summary>参考答案</summary>

1. 可能是普通变量、派生值、Ref 或者数据根本没有放在正确的状态所有者中。先判断它是否需要触发重新渲染。
2. 两份状态会产生同步问题。只保留源数据，在渲染期间根据源数据计算派生值。
3. 当列表插入、删除、排序、过滤或组件内部有输入状态时，下标可能让 React 把旧组件实例复用到错误的数据上。
4. 状态提升把共享状态放到共同父组件；Context 让深层组件读取共享依赖，减少逐层传 Props。
5. 网络响应返回顺序不等于请求发起顺序。需要取消旧请求、使用请求标识或在提交结果前检查它是否仍然有效。
6. 需要更新界面用 State；只需跨渲染保存值或操作 DOM、定时器等外部对象用 Ref。
7. 输入框的 value 来自 State，onChange 把用户输入写回 State，提交时由回调输出规范化后的值。
8. 至少明确 Props、事件参数、State 类型和异步返回数据类型；必要时再补充 children、Ref 元素类型和联合状态。

</details>

## 五、进入 Next.js 前的检查清单

- 能解释 JSX 为什么是 JavaScript 的语法扩展。
- 能独立写出带 Props、State 和事件的函数组件。
- 能用稳定 ID 渲染列表，并说明为什么不能随便用下标。
- 能完成受控表单和提交处理。
- 能判断状态应该放在当前组件、共同父组件还是 Context 中。
- 能区分事件处理函数、Effect 和 Ref。
- 能实现 loading、error、empty、success 四种异步 UI。
- 能用 TypeScript 写 Props、事件、状态和请求结果。
- 能完成一个小型的“搜索 + 列表 + 错误重试”页面。

达到这些标准后，就可以把 Next.js 当作 React 应用框架继续学习。Next.js 的路由、服务端渲染、Server Components、数据请求和部署属于下一层，不应反过来打乱 React 基础主线。

## 六、一句话总结

React 的核心不是记 API，而是围绕“数据从哪里来、谁拥有它、变化后如何渲染”建立单向、可追踪的 UI 数据流。
