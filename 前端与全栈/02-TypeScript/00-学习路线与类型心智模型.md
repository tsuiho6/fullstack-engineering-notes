# TypeScript 学习路线与类型心智模型

> 优先级：⭐

## 一、是什么

TypeScript 是 JavaScript 的静态类型检查器。它在代码运行前检查类型关系，最终仍然编译或转换为 JavaScript 执行。

最重要的边界：

~~~text
TypeScript：检查开发者写的代码
JavaScript 运行时：真正接收和执行数据
~~~

## 二、为什么需要

TypeScript 主要解决大型 JavaScript 项目中的“数据关系不清”：

- 函数接受什么参数不清楚
- API 返回结构变化后很难发现
- 重构时不知道哪些调用方会受影响
- 组件 Props 和状态容易传错

但 TypeScript 不能自动验证运行时输入。服务器返回的数据、用户提交的表单和外部 JSON 仍然需要运行时校验。

## 三、核心用法

### 类型推断优先

~~~ts
const count = 0
const names = ['Alice', 'Bob']
~~~

TypeScript 可以推断 count 是 number、names 是 string[]。不需要给所有变量重复写类型。

### 显式描述边界

~~~ts
type User = {
  id: string
  name: string
}

function renderUser(user: User): string {
  return user.name
}
~~~

输入：满足 User 结构的对象；输出：字符串。

### 类型只存在于开发阶段

~~~ts
type User = {
  id: string
}

const user: User = { id: 'u1' }
~~~

类型注解不会在 JavaScript 运行时自动检查，也不会替代数据校验。

## 四、核心原理

### 1. 结构类型系统

TypeScript 主要比较对象的结构，而不是名义上的类型名称：

~~~ts
type Point = { x: number; y: number }

const position = { x: 1, y: 2, label: 'origin' }

function printPoint(point: Point) {
  console.log(point.x, point.y)
}

printPoint(position)
~~~

直观理解：只要一个值至少满足需要的结构，就可以在对应位置使用。

### 2. 类型宽窄

类型可以从宽变窄：

~~~text
unknown
  ↓ 类型缩小
string | number
  ↓ 再次缩小
string
~~~

类型越窄，能安全使用的操作越多；类型越宽，越需要先判断。

### 3. any、unknown、never

| 类型 | 含义 | 项目态度 |
| --- | --- | --- |
| any | 放弃这部分类型检查 | 尽量避免 |
| unknown | 不知道具体类型，使用前必须检查 | 外部输入首选 |
| never | 不可能出现的值 | 穷尽检查和异常函数 |

## 五、常见场景

- API 响应和请求参数。
- React Props 和状态。
- 数据库记录和领域模型。
- 工具函数和公共库。
- 重构大型项目。

## 六、踩坑点

1. TypeScript 通过编译不代表运行时数据一定正确。
2. 类型断言不是校验，只是告诉编译器“相信我”。
3. any 会污染后续类型推断。
4. 为了消除报错到处加 as，通常是在隐藏真实问题。
5. 类型越复杂不代表设计越好，优先表达业务不变量。

## 七、项目中的实际使用

外部输入分两步：

~~~text
未知数据
→ 运行时校验
→ 可信的领域类型
→ 业务函数
~~~

例如 API 响应不要直接断言为 User，而应该先检查必要字段，再把结果交给业务代码。

## 八、一句话总结

TypeScript 负责让代码关系清楚，但不负责替你验证运行时世界；边界输入必须先校验，再进入业务类型。

## 九、核心问答

### 1. TypeScript 类型会在运行时存在吗？

通常不会。类型主要用于开发期检查，最终代码运行在 JavaScript 环境中。

### 2. 为什么 unknown 比 any 更安全？

unknown 可以接收任意值，但使用前必须经过类型缩小；any 会直接关闭后续检查。

### 3. 什么是结构类型？

类型兼容主要看值是否具备需要的结构，而不是看它是否显式声明继承某个类型。

### 4. TypeScript 能保证接口返回数据正确吗？

不能。接口数据来自运行时，必须配合校验逻辑。
