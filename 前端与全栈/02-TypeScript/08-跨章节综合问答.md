## 二、核心综合问答

### 1. TypeScript 能否保证 API 响应符合接口类型？

不能。接口只在编译期描述预期，API 响应是运行时数据，必须进行校验。

### 2. 为什么 unknown 是外部输入的合理起点？

它承认数据类型未知，同时要求代码在使用前完成缩小或校验。

### 3. 什么时候用联合类型，什么时候用泛型？

联合表示一个值可能属于几个固定分支；泛型表示一套逻辑适用于多种类型，并保持输入输出关系。

### 4. 为什么 React 请求状态适合用可辨识联合？

状态是互斥的，status 标签能表达当前分支，并让 data 或 message 在对应分支中自动可用。

### 5. 为什么函数参数和返回值是类型设计的重要边界？

它们是模块之间传递数据的地方。边界越清楚，调用错误越早暴露，内部实现也越容易替换。

### 6. 为什么类型工具不会改变运行时对象？

Pick、Omit、Partial 等只改变编译器看到的类型，不会在 JavaScript 中添加、删除或复制字段。

### 7. 为什么 strictNullChecks 很重要？

它迫使代码正视 null 和 undefined，减少“以为一定有值但运行时没有”的错误。

### 8. 为什么不能为了通过编译到处使用 as？

as 只是告诉编译器跳过某个检查，过度使用会隐藏数据模型错误。

## 三、综合代码题

### 题目 1：为一个列表请求建模

要求：

- 成功时有 data
- 失败时有 message
- loading 时不能读取 data

<details>
<summary>查看参考答案</summary>

~~~ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }
~~~

</details>

### 题目 2：安全读取对象属性

要求：传入对象和合法键，返回对应值类型。

<details>
<summary>查看参考答案</summary>

~~~ts
function getProperty<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key]
}
~~~

</details>

### 题目 3：处理未知 JSON

要求：只有确认是字符串后才调用 trim。

<details>
<summary>查看参考答案</summary>

~~~ts
function normalize(value: unknown) {
  if (typeof value !== 'string') {
    return null
  }

  return value.trim()
}
~~~

</details>

## 四、进入 React 前的检查

你应该能够：

- 给函数参数和返回值建立合理类型。
- 区分 any、unknown 和类型断言。
- 使用联合类型表达有限状态。
- 用类型缩小处理不同分支。
- 用泛型保持输入和输出关系。
- 看懂 type-only import。
- 解释 strictNullChecks 和 noImplicitAny 的意义。
- 设计输入模型、领域模型和视图模型。

如果某项不会，不需要重新阅读全部 Handbook，只回到对应章节写一个十行以内的实验。
