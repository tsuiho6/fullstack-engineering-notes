# 项目闭环：类型安全的 API 与表单

> 优先级：⭐

## 一、是什么

类型安全的项目闭环，是把外部输入、运行时校验、业务类型、函数边界和 UI 状态连接起来，而不是只给变量写几个类型注解。

## 二、为什么需要

真实项目中的数据来自用户输入、URL 参数、API 响应、数据库和第三方 SDK，这些数据都可能不可信。

只写 TypeScript 类型而不做运行时校验，仍然会在生产环境出错。

## 三、核心用法

### 领域类型

~~~ts
type Note = {
  id: string
  title: string
  content: string
}

type CreateNoteInput = {
  title: string
  content: string
}
~~~

### 请求状态

~~~ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }
~~~

### 业务函数

~~~ts
async function createNote(input: CreateNoteInput): Promise<Note> {
  const response = await fetch('/api/notes', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(input),
  })

  if (!response.ok) {
    throw new Error('创建失败')
  }

  return response.json() as Promise<Note>
}
~~~

上面的断言只适合作为教学演示或已由可靠 schema 保证后的边界。真实项目应在这里进行运行时校验。

## 四、核心原理

推荐的数据流：

~~~text
外部 unknown
→ 运行时校验
→ 领域类型
→ 业务函数
→ UI 状态
~~~

输入模型和输出模型分离：

~~~text
CreateNoteInput：用户可以提交什么
Note：服务端最终保存和返回什么
NoteViewModel：页面真正需要显示什么
~~~

这样可以减少数据库结构、API 结构和 UI 结构之间的耦合。

## 五、常见场景

- 表单提交。
- CRUD 页面。
- AI 请求和流式消息。
- 数据库记录转换。
- 登录和权限状态。

## 六、踩坑点

1. 类型断言不是运行时校验。
2. 接口类型和数据库类型不一定相同。
3. 不要把 loading、error、data 分成互相矛盾的多个布尔值。
4. API 错误也应该有明确的结构。
5. 表单输入通常是字符串，不能直接当成 number 或 Date。
6. 机密字段不能因为有类型声明就暴露到客户端。

## 七、项目中的实际使用

一个合理的项目边界：

~~~text
form.tsx
  负责收集输入和显示校验错误
api/notes.ts
  负责请求和 HTTP 错误
schemas/note.ts
  负责运行时数据校验
lib/notes.ts
  负责领域操作
types/note.ts
  负责共享类型
~~~

TypeScript 类型用于让模块之间的契约清楚；运行时校验用于保护真实边界。

## 八、一句话总结

类型安全不是把 any 改成 interface，而是让不可信输入经过校验后，沿着清晰的数据模型进入业务和 UI。

## 九、核心问答

### 1. 为什么 CreateNoteInput 和 Note 要分开？

输入由用户提供，Note 可能包含服务端生成的 id、时间和权限字段，两者生命周期和可信程度不同。

### 2. 为什么多个布尔值不适合表示请求状态？

它们可能组合出互相矛盾的状态；可辨识联合可以保证状态互斥并自动缩小。

### 3. 类型断言什么时候相对合理？

在运行时事实已经由可靠机制保证、而 TypeScript 无法推断时可以局部使用；不能把它当成校验工具。

### 4. 表单输入为什么不能直接当数字？

浏览器输入通常先以字符串存在，需要显式解析、校验和处理空值。
