# 哈希表

## 一、是什么

哈希表用哈希函数把键映射到桶，再保存“键 → 值”的关系，使按键查找、插入和删除在平均情况下接近 `O(1)`。Go 的 `map[K]V` 已经提供了成熟实现，刷题通常只使用它，不手写底层桶。

## 二、为什么需要

如果只有切片，判断一个值是否出现过要扫描 `O(n)`；哈希表把“是否存在、出现几次、对应哪个位置”变成按键查找。它是刷题中把双重循环降为单次扫描的第一工具。

## 三、核心用法

### ⭐ 集合：只关心存在性

```go
seen := make(map[int]struct{}, len(nums))
for _, x := range nums {
    if _, ok := seen[x]; ok {
        // x 已出现
    }
    seen[x] = struct{}{}
}
```

**形状**：`int → 空值`；读操作返回 `(value, ok)`，`ok` 表示键是否真的存在。

### ⭐ 计数表

```go
freq := make(map[int]int)
for _, x := range nums {
    freq[x]++ // 缺失键读取为 0，因此可直接自增
}
```

字符串按 Unicode 字符统计：

```go
freq := make(map[rune]int)
for _, r := range s {
    freq[r]++
}
```

### ⭐ 两数之和：边查边存

```go
func twoSum(nums []int, target int) []int {
    pos := make(map[int]int, len(nums)) // 值 -> 下标
    for i, x := range nums {
        if j, ok := pos[target-x]; ok {
            return []int{j, i}
        }
        pos[x] = i
    }
    return nil
}
```

**关键因果**：当前值 `x` 需要的补数是 `target-x`；先查后存可以避免把同一元素重复使用。

### ⭐ 映射与多值映射

```go
last := make(map[string]int)        // key -> 一个值
groups := make(map[string][]string) // key -> 多个值

last[name] = i
groups[signature] = append(groups[signature], word)
```

### △ 自定义可比较键

数组和字段全可比较的结构体可以作为键：

```go
type Point struct{ X, Y int }

visited := make(map[Point]struct{})
visited[Point{X: 1, Y: 2}] = struct{}{}
```

切片、`map`、函数不能直接作为键；需要把它们编码成字符串、数组或结构体。

## 四、核心原理

### 1. 哈希与桶

```text
bucketIndex = hash(key) mod bucketCount
```

直观含义：哈希函数把任意键转换成整数，再定位到有限个桶；理想情况下每个桶中的键数量很小，因此查找接近常数时间。

### 2. 冲突不可避免

不同键可能映射到同一桶，这叫哈希冲突。常见处理思路是链式法、开放寻址或其变体；当装载过高时需要扩容并重新分布。

刷题要记住的是结果：

| 操作 | 平均 | 极端最坏 | 说明 |
|---|---:|---:|---|
| 查找/插入/删除 | `O(1)` | 可能退化到 `O(n)` | 依赖哈希分布和实现 |
| 遍历全部键值 | `O(n)` | `O(n)` | 与桶数量无关地要看所有元素 |
| 扩容 | 均摊 `O(1)` 插入 | 某次可能较慢 | 总成本摊平 |

### 3. 为什么哈希表不是有序表

哈希表优化的是按键定位，不维护键的大小关系或插入顺序。直观含义：它适合回答“这个键对应什么”，不适合回答“所有键按大小排列”。需要有序查询时考虑排序、平衡树或堆。

## 五、常见场景

- **去重/访问标记**：`map[T]struct{}`。
- **频次统计**：字符、数字、类别计数。
- **补数/配对**：两数之和、差值匹配、前缀和频次。
- **索引定位**：值到最后位置、字符串到 ID、节点到状态。
- **记忆化**：状态键到答案；键要能稳定表示完整状态。
- **图遍历**：节点 ID 到是否访问、网格坐标到访问状态。

不适合的场景：

- 需要按键排序或范围查询；
- 需要稳定遍历顺序；
- 键无法合理编码或哈希成本很高；
- 只需顺序扫描一次，建表反而增加内存。

## 六、踩坑点

1. **`nil map` 读安全、写不安全**：声明后写入前要 `make`。
2. **零值和不存在不是一回事**：`m[k]` 可能得到 `0`、`false` 或 `nil`，需要判断 `ok`。
3. **不要依赖 map 遍历顺序**：输出、测试和业务逻辑都不应假设它稳定。
4. **键必须可比较**：`map[[]int]int` 编译错误；二维坐标可用 `struct{r,c int}`。
5. **两数之和要先查后存**：否则相同下标可能被当成答案。
6. **计数的默认零值很方便，但删除要显式**：`delete(m, k)`，不能把值设成零来表示不存在。
7. **`make(map[K]V, n)` 只是容量提示**：不是长度为 `n`，不能按下标访问。
8. **哈希表换空间换时间**：若输入规模很大，要把额外 `O(n)` 空间纳入判断。
9. **并发写 map 不安全**：LeetCode 单线程通常不用管；工程并发场景用锁或并发容器设计。

## 七、项目中的实际使用

项目中要先明确 key 的身份和生命周期：

```go
type User struct {
    ID int
}

type UserIndex struct {
    byID map[int]*User
}

func NewUserIndex(capacity int) *UserIndex {
    return &UserIndex{byID: make(map[int]*User, capacity)}
}
```

如果一个实体既需要按 ID 查找，又需要按时间顺序淘汰，单独一个 map 不够，要组合 map 与链表；如果需要按范围查找，则不要把哈希表硬套成排序结构。

## 八、一句话总结

**哈希表把“按键找答案”从扫描变成平均常数时间，但它不保证顺序，也不消除空间代价。**

## 九、核心问答

1. **为什么两数之和可以从 `O(n²)` 降为 `O(n)`？**
   - 对每个 `x`，用 map `O(1)` 查找补数 `target-x`，每个元素只处理一次。
2. **为什么 `map[K]V` 还要返回 `ok`？**
   - 值类型有零值，单看 `m[k]` 无法区分“键不存在”和“键存在但值为零”。
3. **哈希表和二叉搜索树都能查找，怎么选？**
   - 只需按键精确查找选哈希表；需要有序、前驱后继或范围查询才考虑树。
4. **为什么 map 遍历不能用来生成稳定 API 输出？**
   - 哈希表不维护顺序；要稳定输出必须显式收集并排序。
5. **哈希冲突会让所有操作必然变成 `O(n)` 吗？**
   - 不会。冲突只影响特定分布；平均复杂度依赖实现、装载因子和哈希函数。

## 十、自测与答案

### 题目

1. 为什么 `var m map[int]int; m[1]++` 会 panic，而 `fmt.Println(m[1])` 不会？
2. 用 map 写“第一个重复元素”的扫描逻辑，应该在什么时候标记已见？
3. 如何用可比较键表示网格坐标 `(r,c)`？
4. 为什么把值设为 0 不能替代 `delete(m, key)`？
5. 题目要求返回按字典序排列的 map 结果，应该增加什么步骤？

<details>
<summary>答案</summary>

1. 读 nil map 会返回零值；写入需要实际桶，nil map 没有可写存储。
2. 先检查 `seen[x]`；若已存在就返回；否则再写入 `seen[x] = struct{}{}`。
3. `type Point struct{ r, c int }`，使用 `map[Point]struct{}`。
4. 值为零的键仍然存在；`delete` 才会移除键，使 `ok=false`。
5. 把键取到切片中，调用 `sort.Ints` 或 `sort.Strings`（或自定义排序），再按排序后的键输出。
